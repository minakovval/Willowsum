## Призначення

Сесії імпорту, зіставлення колонок, перевірки, відкат.

Домен каталогу ARC-01: Імпорт. Реліз, з якого модуль у каталозі: PoC.

Партії імпорту (IMP-01@PoC b, рядок 39 плану хвилі 2): створення партії, завантаження одного чи багатьох файлів (multipart,
на потоці, під одним бюджетом запиту), оригінали лише через `file-storage` (вид «виписка»), підписані посилання ≤ 15 хв на
оригінал, стани партії (IMP-19@PoC п. 5) і «не вдалося розібрати», коли відхилено всі файли (п. 6). Записи аудиту — через
чергу модуля (ADR-0015) з щоденним поверненням мертвих завдань. За прапорцем випуску `data.import`. «Скасувати», «Видалити»
незастосованої партії з оригіналами і щоденне прибирання незастосованих партій через 30 днів від останньої дії (п. 12, п. 20,
IMP-19 п. 6; частина 2 рядка 39). Розбір рядків — рядок 40.

Перегляд партії (IMP-05@PoC частина 2, рядок 42): перевірки кожного прийнятого файлу з розбору (file-parsers `StatementChecks`;
масковані значення — лише «…» і 4 останні символи) з розривом історії відносно останньої застосованої виписки того самого
рахунку в просторі (п. 3: застосування завершене, не «в процесі»; найпізніший кінець періоду, потім остання дія партії); рішення (п. 10) для рядка, групи
«потребує перегляду» / «потребує уточнення» (файл чи партія), прочитання суми з «застосувати до файлу» (п. 7: прочитання з
більшою кількістю знаків, ніж у валюті, — 422 `READING_TOO_PRECISE`), порядок дня й місяця, підтвердження позначок, «Так, це
правильний рахунок» (п. 4), вибір залишку при розбіжності контрольних сум (п. 2: `update` / `keep`); готовність до
застосування (п. 11) з відмовами «Підтвердіть рахунок», «Потрібні уточнення», «Потрібен перегляд рядків», «Не підтверджені
позначки» і планом для кожного файлу. Застосування партії — наступний зріз: воно викликає `readiness`.

Крок розбору (IMP-01@PoC п. 5, п. 6, п. 9, п. 10, п. 15, п. 21; IMP-19@PoC п. 4, п. 5; рядок перед 44–46): «Розібрати» ставить
партію «в обробці» й кладе в чергу модуля одну важку задачу на кожен прийнятий файл (ARC-04 п. 5: воркер виконує не більше
своєї межі важких задач, а парсер — не більше 2 воркерів розбору водночас). Задача читає оригінал (file-storage `read`), розбирає
його в ізольованому воркері (file-parsers) з обраним рецептом або рецептом простору, знайденим за відбитком формату, і з
обраним рахунком; відкривач поля прив'язки береться лише тоді, коли настала черга воркера. Розібрані рядки (читання, аналіз,
рядки-події) запечатуються ключем простору (`sealBytes`, призначення `parse:<id розбору>`), як оригінали у file-storage;
перевірки — `recordChecks` з розривом історії (масковані значення перевіряються ще раз на межі, #637 п. 3). Печатка прив'язана до файлу й розбору (`parse:<id файлу><id розбору>`); розбір понад
32 МіБ як UTF-8 відхиляється з `CORRUPTED`; годинна стеля рахується під рекомендаційним замком простору. Останній файл
переводить партію в «розібрано», «потребує перегляду» (є відхилений файл, файл без рахунку, позначка, уточнення чи
непідтверджений знак) або «не вдалося розібрати» (відхилено всі). Книги Excel поки відхиляються з `FORMAT_NOT_PARSED`.

## Власні таблиці

Схема `import_sessions`; міграції — `adapters/db/migrations/NNNN_slug.sql`.

- `batches` — партія: назва (необов'язкова, ≤ 120), стан (8 станів IMP-19 п. 5), хто створив, версія, час створення й
  останньої дії; `deleting_at` — позначка видалення (крок 1 з 3: позначка, оригінали, рядки): позначена партія «не знайдена».
- `batch_files` — файл партії за порядком: прийнятий — id оригіналу у file-storage, формат і розмір; відхилений — лише код
  причини. Назва файлу очищена так само, як у file-storage. Байтів у базі немає.
- `file_checks` — перевірки прийнятого файлу (jsonb), рахунок (id з accounts, без зовнішнього ключа), його валюта,
  запропонований рахунок, розрив історії й попередня виписка; ключ `(household_id, batch_id, batch_file_id)` → `batch_files`
  тримає рядок при файлі своєї партії (так само `decisions` з файлом); `decisions` — рішення за слотами (`row:…`, `reading:…`,
  `date-order:…`, `group:…`, `flag:…`, `account:…`, `balance:…`; `batch` — уся партія). Обидві йдуть разом з партією.
- `batch_files.content_sha256` — SHA-256 байтів прийнятого файлу (від file-storage; IMP-04 п. 3), частковий індекс за
  простором і відбитком; `batch_applications` — збережений результат застосування партії (п. 7; лічильники, без тексту
  рядків), один на партію, іде разом з партією (`0006_applications.sql`); `in_progress` і `from_state` — крок
  застосування почався, і стан, у який повертає відмова (`0008_apply.sql`); `attempt_id` — спроба застосування, частковий
  індекс застосувань «в процесі» за часом початку для відновлення (`0009_apply_attempts.sql`); `rolled_back_by`,
  `rolled_back_at`, `rollback` — відкат партії (режим, лічильники, id залишених транзакцій; `0010_rollbacks.sql`).
- `file_parses` — розбір прийнятого файлу (`0007_file_parses.sql`): id розбору (новий на кожен запит), обраний і застосований
  рецепт, збіг формату, рахунок, стан (`pending` / `parsed` / `failed`), код відмови, версія рушія, кількість рядків і
  `rows_sealed` — розібрані рядки, запечатані ключем простору (у відкритому вигляді в базі їх немає); іде разом з партією.
- `jobs`, `outbox_events` — черга модуля (ARC-04, міграція платформи дослівно); `idempotency_keys` — ключі ідемпотентності
  маршруту створення (ARC-07).
