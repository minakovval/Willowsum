# Модуль accounts

**Створено:** 2026-11-13 · **Оновлено:** 2026-11-14 (FIN-01@PoC b: «Гроші разом» і список рахунків — серверна частина)

Картка модуля (ARC-01). Робота з модулем починається з неї; оновлюйте її в тому ж PR, що й інтерфейс.

## Призначення

Рахунки, мультивалютні контейнери, субрахунки.

Домен каталогу ARC-01: Гроші. Реліз, з якого модуль у каталозі: PoC.

Залишку модуль не зберігає: кожна валюта рахунку (субрахунок) має свій рахунок журналу, а «Початковий залишок» — подія
журналу (FIN-01 п. 7; баланс на дату — сума проводок). Умови кредиту й кредитної картки — у модулі `liabilities`.

## Публічний інтерфейс

`index.ts`:

- `accountsModule` — опис модуля з маршрутами (прапорець випуску і ключ функції `accounts.manual`; простір — лише
  сесії, ідентифікатора простору в запиті немає; рахунок іншого простору — 404 як неіснуючий):
  - `POST /v1/accounts` (`createAccount`, дозвіл `household.data.write`, `Idempotency-Key`) — форма «Новий рахунок»
    плоско: `kind`, `name` (1–80), `institution` (`name` 1–100, `country` ISO 3166-1 alpha-2), `balance` (`amount` —
    додатне десяткове з не більше знаків, ніж у валюти; для поточного рахунку може бути від'ємним; для картки й кредиту —
    борг), `currency`, `balanceDate`, `extraCurrencies` (лише поточний, до 10 валют разом), `number` (останні 4 символи,
    IBAN з перевіркою ISO 13616 або номер рахунку 5–34 символи; повний номер платіжної картки — 400
    `card_number_not_allowed`), `note` (до 1 000), за типом — `annualRate` (0–100, два знаки; для кредиту обов'язкова),
    `depositOpenedOn`, `depositMaturesOn`, `creditLimit`, `gracePeriodDays` (0–365), `monthlyPayment` (кредит, > 0).
    Поле іншого типу — 400, а не мовчазне відкидання; поля «Власники» немає (невідоме поле — 400). Дубль — 409
    `ACCOUNT_DUPLICATE`, нічого не записано. → 201 рахунок (як `GET`).
  - `GET /v1/accounts/{accountId}` (`getAccount`, дозвіл `household.data.read`) — рахунок: тип, група (`cash`, `credit`),
    назва, установа, номер лише як `last4` і `••1234`, власники з частками, залишок на сьогодні з журналу по кожній валюті
    (борг — зі знаком мінус), для депозиту — нараховане (`accrual`: сума без округлення, дні, днів до закінчення,
    `matured`), для картки — ліміт, пільговий період, борг і доступно, для кредиту — ставка, платіж і борг.
  - `GET /v1/accounts/summary` (`getAccountsSummary`, дозвіл `household.data.read`; учасник з областю — 404, «Рахунки»
    закриті політикою видимості за замовчуванням) — лише активні рахунки: `moneyTogether` («Гроші разом», FR 18: усі
    готівкові рахунки і кредитні картки зі знаком мінус, без кредитів; `total` у валюті профілю без округлення або null,
    якщо курсу немає в жодної валюти — ніколи 0; `approximate`, `staleRateCount`, `unavailableCount`; `rate` — джерело і
    найраніша дата використаного курсу, «курс НБУ на <дата>»; `breakdown` — на кожну валюту сума в оригінальній валюті,
    еквівалент, дата курсу і `percent` — цілі відсотки, що разом дають 100, найбільший еквівалент першим), `credit`
    (`cardDebt`, `loanDebt` — додатна заборгованість у валюті профілю, FR 19), `sources` (`import`, `manual`, FR 21).
  - `GET /v1/accounts` (`listAccounts`, той самий дозвіл і 404 для учасника з областю) — сторінка рахунків (`pageQuery`,
    `pageOf`; порядок — додавання, потім id), `group` (`cash`, `credit`), `includeClosed` («Показати закриті», FR 22): на
    рядок — тип, група, назва, установа, `••1234`, стан і дата закриття, джерело, `updatedOn` (найпізніша дата залишку),
    `inProfileCurrency` у валюті профілю, `currencies` (кожен субрахунок у своїй валюті й у валюті профілю з датою курсу), картка —
    ліміт, борг, доступно; кредит — ставка, платіж, борг.
  - `POST /v1/accounts/duplicate-check` (`findDuplicateAccount`, дозвіл `household.data.write` — учасник з областю не може
    промацувати рахунки поза нею) `{ institution, number, currencies }` → `{ duplicate: { accountId, institution,
    maskedNumber } | null }` — для «Такий рахунок уже є: <установа> ••1234» і «Відкрити наявний».
- `createAccountsServices({ ledger, liabilities, keys, fx, audit, clock, newId })` → `AccountsServices` — порти маршрутів
  (`src/api.ts` → `ctx.services`; `main.ts`): `createLedger`, `createLiabilities`, `createSpaceKeys` модуля household
  (тип `NumberSeal`, поле `accounts.number` — `NUMBER_FIELD`), `createFxReporting` модуля fx-rates (на тому ж годиннику),
  журнал аудиту, годинник («сьогодні» залишків — дата UTC; «сьогодні» курсу — київська дата fx-rates).

Залишки списку й «Гроші разом» — `balanceAt` журналу на сьогодні лише для рахунків журналу, на які вказують субрахунки
простору (рішення ведучого, #210): службові рахунки журналу і сироти невдалого створення не підсумовуються й не
показуються. Валюта профілю — `REPORTING_CURRENCY` модуля fx-rates (EUR для кожного простору в PoC, ACC-06). Конвертація й
позначка «приблизно» (курс старший за 3 календарні дні, VAL-04) — `FxReporting.total`, без власного правила; кожен
підсумок — один запит курсів. Закриті рахунки не входять у жоден підсумок і в кількості «Джерела даних».
- `createAccountsErasure(db)` → `AccountsErasure` (див. «Власні таблиці»).
- `ACCOUNT_KINDS`, `groupOf`, `maskedNumber`, `parseAccountNumber`, `depositAccrual`, типи `AccountKind`, `AccountGroup`,
  `AccountView`, `DepositAccrual`.

Створення рахунку — у транзакції модуля під замком створень простору (два однакові запити не проходять перевірку дубля
обидва): перевірка форми (умови кредиту й картки — `checkTerms` модуля liabilities) і дубля → запечатаний номер →
рахунок, субрахунки з рахунками журналу (`openAccount`, власник `accounts`/ідентифікатор субрахунку, тип `asset` або
`liability`), Owner 100 % → на кожну валюту подія `opening-balance` на її дату (ключ `accounts.opening:<субрахунок>`;
нульовий залишок події не має) → зобов'язання для кредиту й картки → запис аудиту `accounts.account`/`create` (номер
замаскований журналом, у відкритому вигляді лише `numberLast4` = `••1234`; нотатка замаскована). Журнал, зобов'язання й
аудит — транзакції інших модулів, закомічені раніше: збій відкочує рахунок, але може лишити рахунок журналу, запис чи
зобов'язання без рахунку (ідентифікатори лише цієї спроби, ніде не показуються); атомарна передача — з подіями (ARC-04).

## Власні таблиці

Схема `accounts`; міграції — `adapters/db/migrations/NNNN_slug.sql`. Усі таблиці — під політикою простору.

| Таблиця | Що |
| --- | --- |
| `accounts` | Рахунок: тип, назва, установа (назва, країна, ключ порівняння для дубля), `number_last4` і `number_sealed` (`ws1.…`, ключ простору, ARC-06 п. 2), нотатка, ставка ощадного й депозиту, дати депозиту, дата відкриття, стан (`active`, `closed` з датою), джерело (`manual`, `import`) |
| `subaccounts` | Валюта рахунку: позиція (0 — основна), рахунок журналу, дата початкового залишку |
| `account_owners` | Власники з частками й датами дії; тригер обмеження під час коміту: сума часток на кожну дату ≤ 100 %; перевірка йде під advisory-блокуванням рахунку (`0003`), тож два одночасні записи не проходять обидва |
| `idempotency_keys` | Ключі ідемпотентності маршруту створення (ARC-07 п. 4, `platform/http/idempotency-keys.sql` дослівно) |

Ключі до `accounts` у `subaccounts` і `account_owners` перевіряються під час коміту (DEFERRABLE).

Видалення простору (NFR-12@PoC п. 3): `createAccountsErasure(db)` → `eraseHousehold(householdId)` — усі рахунки простору
з субрахунками, власниками і ключами ідемпотентності, однією транзакцією ролі модуля; викликає лише `data-erasure`.

Синтетичні дані: `synthetic.ts` (3 поточні рахунки з одним субрахунком і власником 100 % кожен, 2 ключі ідемпотентності на
простір; номери — лише останні 4 символи).
