# Модуль liabilities

**Створено:** 2026-11-13 · **Оновлено:** 2026-11-15 (ARC-04: запис аудиту після коміту, задача `liabilities.hand-off`, #252 п. 3, #263; FIN-12@PoC b: «Кредит» ↔ «Кредитна картка»; FIN-12@PoC e: історія умов з датами, `changeTerms`, #244 п. 7)

Картка модуля (ARC-01). Робота з модулем починається з неї; оновлюйте її в тому ж PR, що й інтерфейс.

## Призначення

Кредити, застава, графіки платежів.

Домен каталогу ARC-01: Активи. Реліз, з якого модуль у каталозі: PoC.

Зараз (FIN-01@PoC): умови зобов'язання рахунку модуля `accounts` — кредиту («Кредит»: іпотека, споживчий, автокредит,
кредитна лінія, позика) зі ставкою і щомісячним платежем і кредитної картки з лімітом і пільговим періодом. Борг — часовий
ряд у журналі (залишок рахунку журналу); власники з частками — рахунку (`accounts.account_owners`). Окремого інтерфейсу
зобов'язань у PoC немає.

## Вимоги

FIN-01@PoC п. 2, 3 (поля кредиту й картки), 5 (обов'язкові ставка і платіж), 16 (ліміт і доступно), AC8, AC13 (доступно =
ліміт − борг), AC18; бізнес-правило «зобов'язання — першокласна сутність». FIN-12@PoC п. 4, 5, AC10, AC12 (умови в
«Реквізитах», що діють з дати зміни; «Кредит» ↔ «Кредитна картка»). Далі: графік платежів і поділ платежу
(п. 26, AC19–AC21), застава.

## Публічний інтерфейс

`index.ts`:

- `liabilitiesModule` — опис модуля (маршрутів немає: зобов'язання створює `accounts`).
- `createLiabilities(db, audit)` → `Liabilities`, де `db` — `ModuleDatabases.for("liabilities")`; кожен виклик прив'язаний
  до одного простору:
  - `register(householdId, { actorAccountId, accountId, terms })` → `{ kind: "registered", liability }` або
    `{ kind: "invalid", issues }` — одне зобов'язання на рахунок; повтор повертає наявне й нічого не пише. Запис аудиту
    `liabilities.liability`/`create` (ставка, платіж, ліміт, пільговий період) — після коміту (див. «Передача аудиту»).
  - `forAccount(householdId, accountId)` → `Liability` або null (рахунок іншого простору — null).
  - `changeKind(householdId, { actorAccountId, accountId, kind })` → `{ kind: "changed" | "unchanged", liability }` або
    `{ kind: "not-found" }` — «Кредит» ↔ «Кредитна картка» (FIN-12@PoC п. 5): тип і умови, які новий тип може мати
    (`termsAsKind`: у кредиту немає пільгового періоду, у картки — щомісячного платежу; ставка й ліміт лишаються); той
    самий тип — нічого не записано. Чи є в рахунку транзакції, перевіряє `accounts`. Запис аудиту
    `liabilities.liability`/`update` (кожне змінене поле до й після) — після коміту (див. «Передача аудиту»).
  - `changeTerms(householdId, { actorAccountId, accountId, change, validFrom })` → `{ kind: "changed", liability,
    validFrom }`, `{ kind: "unchanged", liability }`, `{ kind: "not-found" }` або `{ kind: "invalid", issues }` —
    «Реквізити» (FIN-12@PoC п. 4, AC10; рішення власника 2026-11-13): ставка і щомісячний платіж кредиту, кредитний
    ліміт картки (`CHANGEABLE_TERMS`; null очищає лише ліміт), що діють з `validFrom` (сьогодні того, хто викликає;
    ніколи не раніше вже записаної зміни). Попередні умови лишаються в історії (`termsHistory`); кредит з обома
    умовами втрачає «Додайте ставку і платіж». Ті самі умови — нічого не записано. Запис аудиту
    `liabilities.liability`/`update` (змінені умови до й після і `validFrom`) — після коміту.
  - `termsHistory(householdId, accountId)` → періоди `{ validFrom, terms }` (`validFrom` null — від реєстрації; за
    датою, потім у порядку запису; останній діє зараз) або null; `termsOn(householdId, accountId, date)` → умови,
    що діяли на дату, або null.
- `createLiabilities(db, audit, clock?)` — `clock` датує в історії умови після зміни типу (UTC; типово годинник процесу).
- `createLiabilitiesWorkerQueue(db, audit)` → `WorkerQueue` — черга модуля для воркера (`src/wiring.ts`, `workerQueues`);
  `createLiabilitiesHandOffRecovery(db, households)` → `run()` — щоденне повернення в чергу задач `dead`
  (`liabilities.hand-off-recovery`, до очищення черги; WARN `liabilities.hand_off_requeued`); `HAND_OFF_JOB`.
- `createLiabilitiesErasure(db)` → `eraseHousehold(householdId)` → `{ liabilities, jobs }` — видалення зобов'язань простору
  і рядків черги (NFR-12@PoC п. 3), лише для `data-erasure`.
- `checkTermsChange(terms, change)` — перевірка зміни умов «Реквізитами» без запису (для `accounts`, щоб відмова не
  записала нічого); `checkTerms(terms)` — перевірка умов без запису (кредит: ставка 0–100 з двома знаками і платіж > 0 обов'язкові,
  пільгового періоду немає; картка: ліміт ≥ 0, пільговий період 0–365 днів, без щомісячного платежу; суми — не більше знаків,
  ніж у валюти); `termsMissing(terms)` — «Додайте ставку і платіж» (кредит без ставки чи платежу, FIN-12 AC12);
  `termsAsKind(terms, kind)`; `availableCredit(limit, debt)` — ліміт мінус борг (Decimal); `parseAnnualRate`, `parseTypedAmount`,
  `LIABILITY_KINDS`, `GRACE_PERIOD_MAX_DAYS`; типи `Liability`, `LiabilityKind`, `LiabilityTerms`, `LiabilityTermsInput`,
  `TermsIssue`, `TermsChangeInput`, `TermsPeriod`, `RegisterResult`, `ChangeTermsResult`.

## Передача аудиту (ARC-04 п. 2–4, ADR-0015)

`register` (нове зобов'язання), `changeKind` (змінено тип) і `changeTerms` (змінено умови) пишуть рядок і задачу `liabilities.hand-off` в одній
транзакції модуля (`adapters/queue/job.ts`). Запис аудиту — після коміту: одразу тим самим викликом, а якщо це не вдалося
(подія логу `liabilities.hand_off_deferred`, WARN, лише клас помилки; виклик не падає) — воркером із черги. Ключ задачі —
`create:<зобов'язання>` або `update:<зобов'язання>:<зміна>`, ключ запису аудиту — той самий з префіксом `liabilities.`,
тож обидва проходи пишуть запис один раз. Задача несе значення запису (поля до й після: ідентифікатори, коди, суми й
ставки десятковими рядками — особистих даних немає), бо попередні умови зміни типу після коміту вже не прочитати. До
завершення передачі зобов'язання є без запису аудиту, ніколи навпаки. Задача `dead` після 8 спроб щодня повертається в
чергу (`liabilities.hand-off-recovery`).

## Власні таблиці

Схема `liabilities`; міграції — `adapters/db/migrations/NNNN_slug.sql`.

| Таблиця | Що |
| --- | --- |
| `liabilities` | Зобов'язання рахунку (`account_id` — непрозорий ідентифікатор рахунку `accounts`, без зовнішнього ключа між схемами; унікальний на простір): тип (`loan`, `credit-card`), валюта рахунку, ставка (0–100, два знаки), щомісячний платіж (> 0), кредитний ліміт (≥ 0), пільговий період (0–365). CHECK: кредит має ставку і платіж і не має пільгового періоду; картка не має платежу. `terms_pending` (`0002`, лише для кредиту) — кредит після зміни картки на кредит, у якого ставки чи платежу ще може не бути (FIN-12 AC12): лише для нього правило бази пропускає відсутні ставку й платіж (пільговий період — ні); позначку ставить тільки `changeKind` (`termsMissing`), тож новий кредит, як і раніше, без них не записується ні базою, ні `checkTerms` (FIN-01 п. 5). Під політикою простору |

| `liability_terms` | Історія умов з датами (`0004`, FIN-12@PoC AC10): один рядок на період — тип, валюта, ставка, платіж, ліміт, пільговий період (правила стовпців як у `liabilities`); `valid_from` null — умови від реєстрації до першої зміни (пише перша зміна, тож зобов'язання без змін рядків не має), інакше — з цієї дати; кілька змін одного дня — за `seq`, діє остання. Рядки лише додаються. Поточні умови — у `liabilities`. Ключ до `liabilities` перевіряється при коміті, видалення — каскадом і явно в `eraseHousehold`. Під політикою простору |
| `jobs`, `outbox_events` | Черга модуля (`0003_queue.sql`, таблиці платформи дослівно, ARC-04): задачі `liabilities.hand-off`; подій модуль не публікує. Під політикою простору |

`liability_terms`; платіж 650 EUR; 2 виконані задачі передачі й 1
передана подія для перевірки ізоляції).

- Стирання простору під час виконання завдання передачі (#270 п. 2): обробник `liabilities.hand-off` тримає блокування рядка завдання, поки пише запис аудиту, тож стирання (яке видаляє рядки черги) чекає на нього, а його крок аудиту потім забирає запис; завдання, чий рядок уже стерто, нічого не пише.
