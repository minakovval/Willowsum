# Модуль audit

**Створено:** 2026-11-06 · **Оновлено:** 2026-11-15 (ARC-04: ключ запису, ADR-0015; ключ іншої сутності чи дії — помилка, #252 п. 2; DAT-03: груповий запис; ключ записів `liabilities`, #263)

Картка модуля (ARC-01). Робота з модулем починається з неї; оновлюйте її в тому ж PR, що й інтерфейс.

## Призначення

Журнал аудиту лише на дописування: хто, коли (UTC), яку сутність, які поля, значення до і після, через
який канал змінив у просторі (П-10). Змінити або видалити запис неможливо. Зміни, що не належать жодному
простору (прапорці функцій і аварійні вимикачі, стан акаунтів identity — ACC-01, пізніше дії персоналу), ідуть у журнал
платформи.

## Вимоги

ARC-03@PoC (п. 5: журнал лише на дописування); CICD-06@PoC (журнал платформи для змін прапорців і вимикачів). Журнал
входів `identity` (ACC-04@PoC, NFR-15@PoC п. 29: входи, невдалі входи і завершення сесій з IP-адресою і пристроєм, сутність
`identity.sign-in`) пишеться в журнал простору через `record` і видаляється разом із ним; інтерфейс модуля не змінився. Повні функції журналу (перегляд, фільтри, експорт) додадуть
вимоги ACC, які його використовують.

## Публічний інтерфейс

`index.ts`:

- `auditModule` — опис модуля.
- `createAuditLog(db)` → `AuditLog`, де `db` — `ModuleDatabases.for("audit")`:
  - `record(householdId, entry)` — дописує запис. `entry`: `actor` (`{ kind: "user" | "staff", id }` або
    `{ kind: "system" }`), `channel` (`web`, `api`, `import`, `system`), `entity` (`{ type, id }`, тип на кшталт
    `accounts.account`), `action` (`create`, `update`, `delete`), `changes` (`{ field, before, after,
sensitive }`, необов'язково `record` — UUID запису групового запису: масова дія, DAT-03 п. 11; до 2 200 змін, з них без
    `record` — до 200). Значення полів з `sensitive: true` замінюються на `AUDIT_MASK` до запису; ідентифікатори —
    лише непрозорі UUID, без імен і email. `key` (необов'язковий код `A–Z a–z 0–9 : . _ -`, 1–200 символів; ARC-04 п. 3,
    ADR-0015) — запис дописується один раз на ключ у просторі: повтор із тим самим ключем повертає наявний запис і нічого
    не пише (`dedupe_key`, `migrations/0004_dedupe_key.sql`), якщо це та сама сутність (`entity`) і дія (`action`); ключ
    наявного запису іншої сутності чи дії — помилка `AuditKeyConflict`, нічого не дописано (#252 п. 2). Журнал платформи
    ключів не має.
  - `entriesFor(householdId, entity, limit?)` — записи однієї сутності в хронологічному порядку; з `limit` — лише `limit` найновіших (теж від найстарішого).
  - `recordPlatform(entry)` — дописує запис у журнал платформи (без простору); автор лише `staff` або `system`.
  - `platformEntriesFor(entity)` — записи журналу платформи однієї сутності в хронологічному порядку.
- Типи `AuditEntry`, `PlatformAuditEntry`, `AuditEntryInput`, `PlatformEntryInput`, `AuditChange`; константа `AUDIT_MASK`;
  клас помилки `AuditKeyConflict`.

Запис іде окремою транзакцією модуля `audit`. Модуль, що передає запис аудиту після коміту своєї зміни (задача, яка може
виконатися знову, ADR-0015), передає `key` (`accounts` — кожен свій запис, `transactions`); `liabilities` — запис зобов'язання й зміни типу (#252 п. 3, #263).

- `createAuditErasure(db)` → `AuditErasure.eraseHousehold(householdId)` → `{ entries }` — видалення всього журналу одного
  простору на запит людини (NFR-12@PoC п. 3; ADR-0013, варіант A). `db` — пул ролі видалення `ws_era_audit`
  (`withErasureDatabases`), яку тригери журналу єдину пускають до DELETE, лише в `entries` і лише простору цілком
  (`migrations/0003_erasure.sql`); UPDATE і TRUNCATE заборонені всім. Журнал платформи не видаляється нікому. Викликає лише
  `data-erasure` зі скрипта власника.
