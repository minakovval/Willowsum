# Модуль audit

**Створено:** 2026-11-06 · **Оновлено:** 2026-11-13

Картка модуля (ARC-01). Робота з модулем починається з неї; оновлюйте її в тому ж PR, що й інтерфейс.

## Призначення

Журнал аудиту лише на дописування: хто, коли (UTC), яку сутність, які поля, значення до і після, через
який канал змінив у просторі (П-10). Змінити або видалити запис неможливо. Зміни, що не належать жодному
простору (прапорці функцій і аварійні вимикачі, стан акаунтів identity — ACC-01, пізніше дії персоналу), ідуть у журнал
платформи.

## Вимоги

ARC-03@PoC (п. 5: журнал лише на дописування); CICD-06@PoC (журнал платформи для змін прапорців і вимикачів). Повні функції журналу (перегляд, фільтри, експорт) додадуть
вимоги ACC, які його використовують.

## Публічний інтерфейс

`index.ts`:

- `auditModule` — опис модуля.
- `createAuditLog(db)` → `AuditLog`, де `db` — `ModuleDatabases.for("audit")`:
  - `record(householdId, entry)` — дописує запис. `entry`: `actor` (`{ kind: "user" | "staff", id }` або
    `{ kind: "system" }`), `channel` (`web`, `api`, `import`, `system`), `entity` (`{ type, id }`, тип на кшталт
    `accounts.account`), `action` (`create`, `update`, `delete`), `changes` (`{ field, before, after,
sensitive }`). Значення полів з `sensitive: true` замінюються на `AUDIT_MASK` до запису; ідентифікатори —
    лише непрозорі UUID, без імен і email.
  - `entriesFor(householdId, entity)` — записи однієї сутності в хронологічному порядку.
  - `recordPlatform(entry)` — дописує запис у журнал платформи (без простору); автор лише `staff` або `system`.
  - `platformEntriesFor(entity)` — записи журналу платформи однієї сутності в хронологічному порядку.
- Типи `AuditEntry`, `PlatformAuditEntry`, `AuditEntryInput`, `PlatformEntryInput`, `AuditChange`; константа `AUDIT_MASK`.

Запис іде окремою транзакцією модуля `audit`; атомарність зі зміною даних прийде з подіями (ARC-04).

- `createAuditErasure(db)` → `AuditErasure.eraseHousehold(householdId)` → `{ entries }` — видалення всього журналу одного
  простору на запит людини (NFR-12@PoC п. 3; ADR-0013, варіант A). `db` — пул ролі видалення `ws_era_audit`
  (`withErasureDatabases`), яку тригери журналу єдину пускають до DELETE, лише в `entries` і лише простору цілком
  (`migrations/0003_erasure.sql`); UPDATE і TRUNCATE заборонені всім. Журнал платформи не видаляється нікому. Викликає лише
  `data-erasure` зі скрипта власника.

## Власні таблиці

Схема `audit`; міграції — `adapters/db/migrations/NNNN_slug.sql`.

| Таблиця   | Що                                                                                                                                                                                                   | Права ролі `ws_mod_audit`                                                                                          |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `entries` | Записи журналу: `household_id`, `occurred_at` (timestamptz, UTC), `actor_kind`, `actor_id`, `channel`, `entity_type`, `entity_id`, `action`, `changes` (jsonb: `field`, `before`, `after`, `masked`) | Лише INSERT і SELECT; тригери відхиляють UPDATE, DELETE і TRUNCATE для будь-якої ролі; безпека рядків за простором |
| `platform_entries` | Журнал платформи: ті самі колонки без `household_id`; автор — `staff` або `system` | Лише INSERT і SELECT; ті самі тригери; без даних клієнтів (виняток у `schema-exemptions.json`) |
