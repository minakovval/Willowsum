# Модуль merchants

**Створено:** 2026-11-13 · **Оновлено:** 2026-11-16 (BUD-14 a: мерчант транзакції, нормалізація назви, перейменування, об'єднання, «Роз'єднати»; BUD-07 a1: `MerchantDirectory`)

Картка модуля (ARC-01). Робота з модулем починається з неї; оновлюйте її в тому ж PR, що й інтерфейс.

## Призначення

Довідник мерчантів і нормалізація назв.

Домен каталогу ARC-01: Гроші. Реліз, з якого модуль у каталозі: PoC.

Транзакція належить модулю `transactions`; її мерчант — те, до чого нормалізується її контрагент (опис банку), тож
рядка на транзакцію тут немає: мерчант народжується один раз для кожного ключа зіставлення, який мають описи простору,
а перейменування й об'єднання змінюють лише мерчанта. Оригінальний опис ніколи не змінюється.

## Вимоги

BUD-14@PoC a) (хвиля 2, рядок 22 — серверна частина): п. 1 (детерміноване очищення опису без зовнішніх сервісів:
префікси терміналів, маски карток, номер магазину і все після нього, організаційно-правові форми; посередник — «канал»,
без отримувача — мерчант-посередник з позначкою), 2 (серверна частина: мерчант, ініціали, «Оригінальний опис», «Канал»,
`joinedFrom` для «Роз'єднати»; логотипів немає), 3 (перейменування й об'єднання для простору, «Роз'єднати», нові
транзакції з тими самими описами — до об'єднаного); AC1, AC10, AC11, AC13 (серверна частина — ініціали), AC16;
граничні випадки 3 і 6. FLW-41@PoC AC6. Далі: правила категорій (п. 4–13, рядок 23 — їм потрібен мерчант транзакції
через публічний інтерфейс цього модуля), фільтр «Мерчант: <назва>» списку транзакцій за мерчантом (п. 14; сьогодні —
за контрагентом), «як раніше» в `categorization` (остання ручна категорія мерчанта), UI (рядок 120).

## Публічний інтерфейс

`index.ts`:

- `merchantsModule` — маршрути (прапорець випуску і ключ функції `transactions.merchants`, потребує
  `transactions.manual`; дозвіл читання `household.data.read`, зміни — `household.data.write`; простір — лише сесії;
  транзакція чи мерчант іншого простору — як неіснуючі; учасник з областю: «Транзакції» закриті політикою видимості за
  замовчуванням — читання 404, зміни 403). Мерчант у відповіді: `id`, `name`, `initials` (п. 2, AC13: перші літери
  перших двох слів), `intermediary` («посередник»), `mergedInto` (до кого приєднано або null).
  - `GET /v1/transactions/{transactionId}/merchant` (`getTransactionMerchant`) → `transactionId`,
    `originalDescription` (контрагент як отримано чи введено), `channel` (посередник або null), `merchant` (показаний;
    null — контрагента немає), `joinedFrom` (власний мерчант опису, приєднаний до показаного, — «Роз'єднати»; інакше
    null). Мерчант опису, що трапився вперше, народжується тут. Транзакції немає в просторі — 404.
  - `GET /v1/merchants` (`listMerchants`, `search` — частина назви без урахування регістру) → `items`: мерчанти, що ні
    до кого не приєднані, за назвою, з `transactionCount` (показані транзакції — свої і приєднаних). Спершу народжуються
    мерчанти всіх описів простору.
  - `PATCH /v1/merchants/{merchantId}` (`renameMerchant`) — `{ name }`: один рядок, 1–100 символів після обрізання
    (інакше 400 `name: invalid`); та сама назва — нічого. Приєднаний мерчант — 409 `MERCHANT_MERGED`.
  - `POST /v1/merchants/{merchantId}/merge` (`mergeMerchants`) — `{ merchantId }`: мерчант тіла приєднується до
    мерчанта шляху, чия назва лишається. Тіло: невідомий чи іншого простору — 400 `merchantId: not_found`, той самий —
    `same_merchant`, приєднаний — `merged`; приєднаний мерчант шляху — 409 `MERCHANT_MERGED`. Ті, що були приєднані до
    мерчанта тіла, приєднуються до мерчанта шляху напряму (без ланцюжків).
  - `POST /v1/merchants/{merchantId}/unmerge` (`unmergeMerchant`) — «Роз'єднати»: мерчант знову свій, з назвою і всіма
    транзакціями своїх описів; неприєднаний — нічого.
- `createMerchantsServices({ transactions, audit })` → `MerchantsServices` — порти маршрутів (`src/api.ts` →
  `ctx.services`; `main.ts`): `TransactionTexts` модуля transactions (контрагенти), журнал аудиту.
- `createMerchantDirectory(db)` → `MerchantDirectory.shownMerchants(householdId, counterparties)` — для `recurring`
  (BUD-07 a1: групування транзакцій за мерчантом): показаний мерчант кожного контрагента (той, до кого приєднано, інакше
  власний; `id`, `name`); контрагента без мерчанта немає в результаті. Мерчант опису, що трапився вперше, народжується,
  як і під час будь-якого читання мерчантів.
- `createMerchantsWorkerQueue(db, audit)` — черга воркера (`src/wiring.ts`): задача `merchants.hand-off`
  (`HAND_OFF_JOB`, запис аудиту зміни).
- `createMerchantsRecovery(db, households)` → `{ run() }` — щоденна задача планувальника `merchants.recovery` (до
  очищення черги): задачі `dead` повертаються в чергу; подія логу `merchants.jobs_requeued` (WARN).
- `createMerchantsErasure(db)` → `eraseHousehold(householdId)` → `{ merchants, jobs }` — видалення простору
  (NFR-12@PoC п. 3, крок `merchants.records`); викликає лише `data-erasure`.
- `normalizeDescription` (п. 1: опис → `name`, `key`, `channel`, `intermediary` або null), `merchantKey`,
  `merchantInitials`; типи `Merchant`, `NormalizedMerchant`.

Порядок однієї зміни (ARC-04, ADR-0015): у транзакції модуля з рядками під блокуванням (за порядком ідентифікаторів):
рядок (версія + 1) і задача `merchants.hand-off` (ключ `set:<мерчант>:<версія>`) → коміт → запис аудиту одразу (невдача
— 200 і WARN `merchants.hand_off_deferred`, запис допише воркер). Запис аудиту — сутність `merchants.merchant`, дія
`update`: перейменування — замаскована зміна `name` (назва походить з опису банку і може називати людину; у задачі назв
немає), об'єднання і «Роз'єднати» — `mergedInto` до й після; об'єднання пише запис на кожного мерчанта, що приєднався.
