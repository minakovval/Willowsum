[лише PoC v2] **Мета.** Як користувач із великою історією, я хочу, щоб списки транзакцій відкривалися і імпорт файлів виконувався швидко навіть на великому просторі, щоб продуктом було зручно користуватися щодня.
[MVP] **Мета.** Як користувач із великою історією, я хочу, щоб Головна і списки відкривалися швидко навіть на великому просторі, щоб продуктом було зручно користуватися щодня.

**Функціональні вимоги**
#. [MVP] Головна (net worth, розподіл, список дій) відкривається «холодно» за ≤ 2 с (p95) на просторі з 10 000 активів і 100 000 транзакцій.
#. [PoC v2] Запити API на читання виконуються за ≤ 300 мс (p95), на запис — за ≤ 500 мс (p95).
#. [лише PoC v2] Усі списки використовують серверну пагінацію. Сторінка списку транзакцій із 50 записів і фільтрами повертається за ≤ 500 мс (p95).
#. [MVP] Усі списки використовують серверну пагінацію. Сторінка списку активів чи транзакцій із 50 записів і фільтрами повертається за ≤ 500 мс (p95). Пошук повертає результат за ≤ 1 с (p95).
#. [PoC v2] Імпорт файлів вкладається в цілі часу (p95, середовище конфігурації production): розбір текстового файлу або таблиці до 5 000 рядків ≤ 5 с, до 20 000 рядків ≤ 20 с; застосування 5 000 транзакцій ≤ 10 с.
#. [MVP] Вебзастосунок відповідає Core Web Vitals на 75-му перцентилі: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1.
#. [MVP] Конкурентне редагування захищене оптимістичним блокуванням: кожен запис має версію; конфлікт на тому самому записі повертає зрозумілу помилку з поточним станом і зміненими полями; дані не втрачаються.
#. [MVP] Перерахунок net worth після оновлення оцінок чи курсів завершується не пізніше ніж за 5 хв.
#. [MVP] Повільні віджети (наприклад, мапа портфеля) завантажуються окремо після основних і не блокують сторінку; збій одного віджета не ламає інші.
#. [v1-mobile] Мобільний застосунок: холодний старт ≤ 2,5 с на середньому Android-пристрої; 60 кадрів за секунду під час прокручування.

**Бізнес-правила**
- [PoC v2] Грошові суми — Decimal із точністю валюти, без чисел з плаваючою комою; округлення лише під час показу. Оптимізація продуктивності не може змінювати точність розрахунків.
- [лише PoC v2] Приймання виконується на тимчасовому середовищі тієї ж конфігурації, що й production; після тесту середовище знищується.
- [MVP] Приймання виконується на тимчасовому середовищі тієї ж конфігурації, що й production, або на staging, тимчасово масштабованому до конфігурації production; після тесту середовище знищується.
- [PoC v2] Мета вимірювання — знайти алгоритмічні проблеми (запити без індексів, N+1, обчислення в пам'яті), а не підібрати потужніше обладнання.

**Критерії приймання**

| Критерій | Поріг | Спосіб перевірки |
| --- | --- | --- |
| [лише PoC v2] API | Читання ≤ 300 мс (p95); запис ≤ 500 мс (p95) | Тест на тимчасовому середовищі форми production |
| [лише PoC v2] Списки | Сторінка 50 транзакцій із фільтрами ≤ 500 мс (p95); пагінація серверна | Навантажувальний тест |
| [MVP] Головна | ≤ 2 с (p95), простір 10 000 активів і 100 000 транзакцій | Навантажувальний тест на еталонному наборі, 100 холодних запусків |
| [MVP] API | Читання ≤ 300 мс (p95); запис ≤ 500 мс (p95) | APM-моніторинг у production; тест у staging |
| [MVP] Списки | Сторінка 50 записів із фільтрами ≤ 500 мс (p95); пагінація серверна | Навантажувальний тест |
| Імпорт | Розбір файлу до 5 000 рядків ≤ 5 с, до 20 000 рядків ≤ 20 с; застосування 5 000 транзакцій ≤ 10 с (p95) | Навантажувальний тест |
| [MVP] Пошук | ≤ 1 с (p95) | Навантажувальний тест |
| [MVP] Core Web Vitals | LCP ≤ 2,5 с; INP ≤ 200 мс; CLS ≤ 0,1 (p75) | RUM-моніторинг; Lighthouse у CI |
| [MVP] Конкурентний доступ | Обидві зміни різних записів збережено; конфлікт на одному записі повертає помилку версії; 0 втрачених змін | Автотест паралельного редагування з двох сесій |
| [MVP] Фонові задачі | Перерахунок net worth ≤ 5 хв | Метрика черги задач; тривога при перевищенні |
| [v1-mobile] Мобільний застосунок | Холодний старт ≤ 2,5 с; 60 fps | Профілювання на еталонних пристроях |

#. [лише PoC v2] **Given** синтетичний простір зі 100 000 транзакцій і 3 валютами (EUR, UAH і ще одна), створений генератором синтетичних даних, і тестове середовище з відомою конфігурацією (у протоколі вказано CPU, RAM, версію бази даних) **When** користувач гортає список транзакцій сторінками по 50 записів із фільтрами **Then** p95 відповіді API ≤ 500 мс, а пагінація виконується на сервері.
#. [MVP] **Given** синтетичний простір із 10 000 активів, 100 000 транзакцій, 5 власниками і 3 валютами (EUR, UAH і ще одна), створений генератором синтетичних даних, і тестове середовище з відомою конфігурацією (у протоколі вказано CPU, RAM, версію бази даних) **When** 100 разів вимірюється час холодного відкриття Головної до показу net worth, розподілу і списку дій **Then** p95 ≤ 2 с; порушення блокує вихід на запуск.
#. [MVP] **Given** той самий простір **When** користувач гортає списки активів і транзакцій сторінками по 50 записів із фільтрами **Then** p95 відповіді API ≤ 500 мс, а пагінація виконується на сервері.
#. [MVP] **Given** два учасники одного простору редагують різні активи одночасно **When** обидва зберігають **Then** обидві зміни збережено; якщо вони редагують той самий запис, другий отримує зрозумілу помилку конфлікту з поточною версією, і жодна зміна не втрачається мовчки.
#. [PoC v2] **Given** вимірювання завершено **When** готується звіт **Then** він містить таблицю p50, p95 і p99 для кожного сценарію, кількість SQL-запитів на запит, найповільніші запити і план оптимізації, а результати порівнюються з попереднім прогоном.

**Граничні випадки**
- [лише PoC v2] Вимір на тимчасовому середовищі не гарантує продуктивності production: у звіті вказано відмінності конфігурацій.
- [MVP] Вимір на staging не гарантує продуктивності production: у звіті вказано відмінності конфігурацій.
- [MVP] Холодне відкриття означає відсутність кешу застосунку; кеш браузера для статичних файлів допускається.

Припущення: третьою валютою еталонного набору може бути будь-яка валюта, відмінна від EUR і UAH.
