**Мета.** Як команда розробки, ми хочемо будувати мобільний застосунок на спільному з вебом коді, щоб одна команда підтримувала обидві платформи без розбіжностей у поведінці.

**Функціональні вимоги**
1. Мобільний застосунок розробляється на React Native (Expo, New Architecture) і TypeScript в одному монорепозиторії з вебзастосунком на React.
2. Бізнес-логіка, API-клієнт, валідація, розрахунки і дизайн-токени спільні для вебу і мобільного застосунку щонайменше на 70 %.
3. Нативні модулі використовуються лише для біометрії, камери й OCR, push-сповіщень і покупок у магазинах застосунків.
4. Виправлення JavaScript-частини доставляються OTA-оновленням не пізніше ніж за 24 год без перевипуску в магазинах, у межах правил Apple і Google.
5. Веб і мобільний застосунок обслуговує одна команда клієнтських розробників.

**Критерії приймання**

| Критерій | Поріг | Спосіб перевірки |
| --- | --- | --- |
| Технологія | React Native (Expo, New Architecture) + TypeScript у спільному монорепозиторії | Архітектурний огляд |
| Спільний код | ≥ 70 % бізнес-логіки, API-клієнта, валідації, розрахунків і дизайн-токенів | Метрика спільного коду в монорепозиторії |
| Нативні модулі | Лише біометрія, камера і OCR, push, покупки в магазинах | Перелік нативних залежностей у релізному чек-листі |
| OTA-оновлення | Доставка ≤ 24 год без перевипуску | Тестове OTA-оновлення в staging |
| Вартість підтримки | Одна команда клієнтських розробників | Огляд структури команди на кожному квартальному плануванні |

1. **Given** знайдено помилку в JavaScript-частині мобільного застосунку **When** виправлення випущено OTA-оновленням **Then** користувачі отримують його не пізніше ніж за 24 год без оновлення в магазині.

**Граничні випадки**
- Потрібен новий нативний модуль поза переліком: його додавання вимагає окремого архітектурного рішення до реалізації.

Припущення: вимога про окреме архітектурне рішення для нового нативного модуля додана як розумне значення.
