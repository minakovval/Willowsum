**Мета.** Як команда розробки, ми хочемо мати один задокументований API, надійний журнал фінансових подій і замінних зовнішніх провайдерів, щоб веб, мобільний застосунок та інтеграції поводилися однаково, а зміна провайдера не ламала клієнтів.

**Функціональні вимоги**
#. [PoC] Усі клієнти (веб, мобільний застосунок, віджети, API-токени користувача) повинні використовувати той самий задокументований API (OpenAPI). Прихованих ендпоінтів для окремих клієнтів немає.
#. [PoC] Права доступу й обмеження видимості перевіряються лише на сервері на рівні запиту до бази даних; усі клієнти отримують ті самі правила доступу.
#. [PoC] Фінансові події зберігаються в реляційній базі даних з ACID-транзакціями в єдиному журналі подвійного запису. Купівля, продаж, дохід, витрата і переоцінка — одна подія, що одночасно змінює актив і грошовий рахунок. Баланс проводок кожної операції дорівнює нулю.
#. [PoC] Журнал проводок і журнал аудиту лише доповнюються: записи не змінюються і не видаляються, виправлення робиться сторнувальною проводкою.
#. [PoC] Зовнішні провайдери (банківський агрегатор, курси валют, автооцінки, карти) підключаються через абстракцію: вибір провайдера за країною чи типом і заміна без змін у клієнтах. Для ключових провайдерів існують щонайменше дві реалізації інтерфейсу.
#. [PoC] Фонові задачі ідемпотентні, мають повтори з затримкою і чергу непрацездатних повідомлень (dead-letter).
#. [PoC] Кожен імпортований чи синхронізований запис має зовнішній ідентифікатор, джерело, дату імпорту, дату останньої синхронізації і перелік полів, змінених вручну. Повторна обробка пакета не створює дублів. Автоматичні дані не перезаписують ручні виправлення.
#. [PoC] Повторне надсилання тієї самої фінансової події (з тим самим ідентифікатором події від клієнта) не створює повторних проводок.

**Бізнес-правила**
- [PoC] Єдиний журнал подій подвійного запису: кожна операція — одна подія з проводками, сума яких дорівнює нулю; журнал у реляційній базі з ACID-транзакціями.
- [PoC] Перевірка прав і обмежень доступу — лише на сервері, на рівні запиту до бази; клієнти не мають власних правил доступу.
- [PoC] Збій зовнішнього провайдера не блокує перегляд даних.

**Критерії приймання**

| Критерій | Поріг | Спосіб перевірки |
| --- | --- | --- |
| API-first | 100 % функцій вебу і мобільного застосунку використовують задокументований API | Контрактні тести за специфікацією OpenAPI; перевірка, що клієнти не викликають незадокументованих ендпоінтів |
| Фінансовий журнал | Баланс проводок = 0 для кожної операції; ACID | Інваріант-тести і властиво-орієнтовані тести на довільних послідовностях подій; щоденна автоматична звірка |
| Незмінність журналів | 0 успішних UPDATE чи DELETE рядків журналу проводок і аудиту | Тест на рівні бази (тригер відхиляє зміну) |
| Абстракція провайдерів | Заміна провайдера без змін у клієнтах | Архітектурний огляд; дві реалізації інтерфейсу для ключових провайдерів |
| Фонові задачі | Ідемпотентність; повтори; dead-letter | Тести повторної обробки того самого повідомлення |
| Повтор подій | 0 дублів проводок при повторі з тим самим ідентифікатором події | Автотест повторного запиту |

#. [PoC] **Given** довільна послідовність подій (купівля, продаж, платіж, переоцінка, зміна частки власності) **When** виконуються властиво-орієнтовані тести **Then** баланс проводок кожної операції і всього журналу дорівнює нулю на рівні Decimal.
#. [PoC] **Given** пакет синхронізації вже оброблено **When** той самий пакет обробляється вдруге **Then** нових записів не з'являється, а поля, змінені вручну, лишаються без змін.

**Граничні випадки**
- [PoC] Провайдер повертає дані в несподіваному форматі: задача потрапляє в чергу dead-letter, користувач бачить останні збережені значення.
