# PRC-02@PoC · Процес змін: вплив змін вимог і дизайну на інші артефакти

**Реліз:** PoC · **Пріоритет:** M

**Зв'язки**
- Розширює: —
- Залежить від: CICD-01@PoC, CICD-02@PoC, PRC-01@PoC
- Дизайн: —
- Спільні правила: ARC-01, NFR-19
- Сценарії: —
- Модуль: —
- Перевіряється: tools/req-check/test/impact.test.mjs

**Мета.** Як власник продукту, я хочу, щоб кожна зміна вимоги, дизайну чи спільного правила доходила до всіх залежних артефактів в одному PR або явно фіксувалася як подальша робота, щоб вимоги, дизайн, тести й код не розходилися.

**Функціональні вимоги**
1. Процес змін запускається одним із тригерів: рішення власника (коментар на канвасі, відповідь у чаті); зміна вимоги або її зрізу; зміна дизайну на канвасі (борд додано, змінено або видалено); зміна спільного правила — загального правила П-n, вимоги дизайн-системи, архітектури чи нефункціональної вимоги.
2. Для кожної зміни виконується аналіз впливу за блоками «Зв'язки» і матрицею трасування. Для зміненого зрізу, вимоги, екрана, борда, правила П-n, сценарію чи модуля знаходяться всі залежні артефакти: зрізи, що його «Розширює» або «Залежить від» нього, транзитивно; зрізи, у «Дизайн» яких є цей екран чи борд; зрізи, у «Спільні правила» яких є це правило; сценарії використання і карти досвіду; карта екранів; спільні правила, на які спираються зачеплені зрізи; тести з поля «Перевіряється»; модулі коду; рядки таблиць README модулів і загального README; таблиця функцій релізів у Google Sheets.
3. Перевірка вимог видає перелік впливу командою `node tools/req-check/index.mjs --impact <ціль>`, де ціль — ідентифікатор вимоги, зрізу, екрана, правила П-n, сценарію, назва борда канваса або модуля. Перелік містить зачеплені зрізи з причиною і зрізом, через який зв'язок пройшов, файли вимог і README модулів, екрани й борди, сценарії, згадки цілі та зачеплених вимог у карті екранів, сценаріях і картах досвіду, спільні правила, тести, модулі коду, а також згенеровані й зовнішні артефакти, які треба оновити. Невідома ціль завершує команду помилкою.
4. Дизайн спершу. Перед злиттям борд канваса і вимога мають збігатися: зміна борда оновлює зрізи, у «Дизайн» яких він вказаний, і навпаки — зміна зрізу, що змінює інтерфейс, оновлює борд. Правило, ухвалене на канвасі, потрапляє у вимоги в тому самому кроці дизайну з таблицею покриття.
5. Перенесення обсягу між релізами. Коли функція чи її частина виходить з релізу, вона переходить у наступний реліз за правилом власника (наприклад, з PoC у PoC v2): раніший зріз скорочується, пізніший отримує цей обсяг, а рядок «Реліз» картки і README модуля оновлюються в тому самому PR.
6. Зміна спільного правила. PR, що змінює загальне правило П-n або вимогу дизайн-системи, архітектури чи нефункціональну вимогу, містить у тілі перелік усіх зачеплених зрізів з аналізу впливу.
7. Залежні артефакти лишаються узгодженими. Кожен зачеплений зріз оновлюється в тому самому PR або явно позначається в тілі PR як подальша робота з посиланням на створену задачу.
8. Згенеровані файли. Файли трасування і звіт перевірки вимог генеруються заново в тому самому PR.
9. Запис рішення. Тіло PR фіксує рішення власника, яке зміна реалізує: дату, джерело (коментар на канвасі, відповідь у чаті) і зміст.

**Ролі і погодження**
- Власник продукту погоджує зміни вимог і дизайну.
- AI-агент виконує зміну і аналіз впливу; рев'ю виконує окрема сесія.
- PR зливається, коли всі перевірки конвеєра пройдені на останньому коміті і рев'ю дало «Ready»; окремого підтвердження злиття від власника не потрібно.
- Розгортання, зміни інфраструктури і дії в production, як і раніше, потребують погодження власника.

**Бізнес-правила**
- Аналіз впливу знаходить лише те, що видно в блоках «Зв'язки»; для ще не мігрованих вимог перелік показує їх окремо з позначкою «не мігровано», і їх перевіряють вручну.
- Таблиця функцій релізів у Google Sheets лежить поза репозиторієм; перелік впливу лише нагадує оновити її рядки.

**Критерії приймання**
1. **Given** зріз A релізу PoC, зріз B релізу PoC, що залежить від A, і зріз C, що залежить від B **When** виконується аналіз впливу для A **Then** перелік містить B з причиною «Залежить від» і C з позначкою, що зв'язок пройшов через B.
2. **Given** вимога зі зрізами PoC і PoC v2, де зріз PoC v2 розширює зріз PoC **When** виконується аналіз впливу для зрізу PoC **Then** перелік містить зріз PoC v2 з причиною «Розширює».
3. **Given** два зрізи, у «Дизайн» яких вказано той самий екран **When** виконується аналіз впливу для цього екрана **Then** перелік містить обидва зрізи, а також залежні від них зрізи.
4. **Given** зріз, у «Спільні правила» якого вказано загальне правило П-n **When** виконується аналіз впливу для цього правила **Then** перелік містить цей зріз і нагадування оновити файли трасування та таблицю функцій релізів.
5. **Given** ціль, якої немає серед вимог, зрізів, екранів, правил, сценаріїв, бордів і модулів **When** виконується аналіз впливу **Then** команда завершується помилкою з назвою цілі.
6. **Given** ідентифікатор зміненої вимоги згадано в карті екранів або в сценарії використання **When** виконується аналіз впливу для цієї вимоги **Then** перелік містить файл і рядок кожної згадки.
7. **Given** PR змінює зріз, а залежний зріз не змінено **When** його переглядають **Then** тіло PR містить залежний зріз у переліку подальшої роботи з посиланням на задачу; інакше рев'ю не дає «Ready».
8. **Given** рішення власника перенести частину функції з PoC у PoC v2 **When** зміна злита **Then** зріз PoC більше не містить цієї частини, зріз PoC v2 її містить, а рядок «Реліз» картки і рядок README модуля називають обидва релізи.

**Граничні випадки**
- Видалено борд канваса — аналіз впливу за назвою борда показує всі зрізи, що на нього посилаються; їхнє поле «Дизайн» оновлюється в тому самому PR.
- Зміна торкається лише не мігрованих вимог — перелік показує їх як «не мігровано», а аналіз доповнюється пошуком згадок у карті екранів, сценаріях і картах досвіду.
- Зміна лише тексту без зміни поведінки (виправлення формулювання) — аналіз впливу все одно виконується, але залежні зрізи не змінюються, якщо їхній текст від неї не залежить.
