Секрети (ключі, паролі, токени) створюють і розносять машини, а не люди. Людина вводить лише кілька кореневих доступів один раз і ніколи — у чат, код, задачу чи документ.

**Де що зберігається**

| Що | Де | Хто створює |
| --- | --- | --- |
| Особисті паролі власника, коди відновлення, доступ до реєстратора домену і хмари | Менеджер паролів власника з другим фактором (passkey або TOTP) | Власник |
| Секрети застосунку (паролі БД, ключі сесій, ключі підпису) для кожного середовища | Сховище секретів із регіоном даних у ЄС — окремий проєкт сховища на кожне середовище | Конвеєр інфраструктури генерує значення і записує їх у сховище напряму |
| Головний ключ шифрування | Керований KMS хмари хостингу (OCI Vault в Oracle Cloud Infrastructure) з PoC; у сховищі секретів не зберігається. У PoC хостинг і резервні копії працюють за профілем «Старт», а головний ключ живе в керованому KMS хмари хостингу (OCI Vault в Oracle Cloud Infrastructure): значення ключа не залишає KMS, копій поза KMS немає. | KMS |
| Ключі зовнішніх сервісів (платежі, пошта, CAPTCHA, курси валют) | Те саме сховище, проєкт середовища | Власник один раз створює ключ у кабінеті сервісу і вставляє його у вебформу сховища |
| Доступ конвеєра GitHub Actions до хмари | Без збережених ключів: короткоживучі токени через OIDC-довіру між GitHub і хмарою | Опис інфраструктури |
| Доступ до сховища секретів production | Без збережених токенів у GitHub. Робочі процеси інфраструктури і розгортання з гілки main отримують короткоживучий доступ (запис для генерації, ротації і резервної копії) через OIDC-довіру сховища або хмари з умовою «цей репозиторій, гілка main, конкретний файл робочого процесу»; запуск із робочої гілки чи PR доступу не має. Хост production має машинний токен лише для читання свого проєкту сховища | Власник один раз |
| Доступ конвеєра до секретів CI | Машинний токен у GitHub Actions secrets з правом лише читати свій проєкт сховища; секретів production у GitHub немає | Власник один раз |
| Секрети для сесій агентів (тестові ключі пісочниць провайдерів) | Налаштування середовища Claude (секрети середовища), лише значення для локального середовища і CI | Власник один раз |

**Функціональні вимоги**

1. Жоден секрет не зберігається в репозиторії, образах, логах, задачах, коментарях PR, документах і чатах з агентами. Агент ніколи не просить вставити секрет у чат; якщо секрету бракує, він називає змінну і місце, куди власник має її додати.
2. Внутрішні секрети застосунку генеруються автоматично описом інфраструктури і записуються в сховище без показу людині: симетричні секрети і паролі — ≥ 32 байти криптографічно випадкових даних; асиметричні ключі підпису генеруються стандартною бібліотекою. Значення бачить лише власник, і лише під час розслідування інциденту.
3. Застосунок під час старту отримує секрети зі сховища або з середовища запуску, яке наповнює конвеєр; конфігурація перевіряється схемою, і за відсутності секрету процес не стартує, називаючи змінну без значення.
4. Головний ключ шифрування застосунок отримує лише через адаптер KMS; ключ створюється і живе в керованому KMS хмари, і застосунок ніколи не бачить його значення. У PoC хостинг і резервні копії працюють за профілем «Старт», а головний ключ живе в керованому KMS хмари хостингу (OCI Vault в Oracle Cloud Infrastructure): значення ключа не залишає KMS, копій поза KMS немає. Головний ключ не записується в сховище секретів, GitHub, логи конвеєра чи журнали.
5. Кожне середовище має окремі секрети. Секрети production недоступні агентам, CI для PR і будь-якому іншому середовищу.
6. Агенти отримують лише тестові ключі пісочниць через секрети середовища Claude; для production вони діють тільки через дозволені дії конвеєра після схвалення власника.
7. Ротація: внутрішні секрети — автоматично щонайменше раз на рік і негайно після підозри на витік, без простою (головний ключ — переобгортанням ключів просторів у фоні); ключі зовнішніх сервісів — за нагадуванням власнику раз на рік. Кожна ротація записується в журнал.
8. Кожне читання секретів production машинним доступом записується в журнал сховища; доступ людей до значень production — лише власника, з другим фактором.
9. Якщо сканер секретів знаходить секрет у коді або історії, PR блокується, а знайдений секрет вважається скомпрометованим і ротується.
10. Перехід на профіль «Комерційний» замінює сховище на керований сервіс секретів хмари лише зміною адаптера і конфігурації; імена секретів не змінюються; головний ключ уже живе в керованому KMS і не переноситься.

**Що робить власник один раз**

- Створює акаунт сховища секретів і проєкти на середовища, видає машинні токени.
- Додає токен сховища для CI у GitHub Actions secrets; токен production (лише читання) — на хост production; тестові ключі — у секрети середовища Claude.
- Налаштовує OIDC-довіру сховища і хмари до гілки main і робочих процесів інфраструктури та розгортання і підтверджує кожну зміну цих умов схваленням у PR: коментарем з рядком «Схвалюю» / «Approved» або рішенням з чату, записаним в описі PR рядком «Рішення власника (РРРР-ММ-ДД): схвалено …».
- Створює ключі зовнішніх сервісів у їхніх кабінетах і вставляє у вебформу сховища.

Усе інше (паролі БД, ключі шифрування, ключі підпису) створюється і оновлюється автоматично.

| Критерій | Поріг | Перевірка |
| --- | --- | --- |
| Секрети в репозиторії, історії git, образах, логах | 0 | Сканер секретів на кожному PR і щотижня по всій історії |
| Секрет, згенерований людиною вручну для внутрішніх потреб застосунку | 0 | Рев'ю опису інфраструктури |
| Доступ агентів, CI для PR або інших середовищ до секретів production | Відсутній | Щоквартальний перегляд прав сховища |
| Старт процесу без обов'язкового секрету | Відмова з назвою змінної, без значення | Тест |
| Вік внутрішнього секрету production | ≤ 12 місяців | Щомісячна перевірка конвеєром |
| Робочий процес не з гілки main, що отримав доступ до секретів або хмари production | 0 | Тест: запуск із робочої гілки отримує відмову OIDC |
| Застосування інфраструктури, розгортання в production або зміна робочих процесів, які це роблять, чи налаштувань довіри до них (OIDC, сховище секретів production) чи DNS production, злиті без схвалення власника в PR (коментар з рядком «Схвалюю» / «Approved» або рядок «Рішення власника (РРРР-ММ-ДД): схвалено …» в описі PR) | 0 | Щоденна перевірка злитих PR |
| Резервна копія секретів | Пакет, зашифрований відкритим ключем власника, в окремому сховищі; головний ключ не залишає KMS і в пакет не входить; приватний ключ — лише в менеджері паролів власника і на паперовій копії | Конвеєр щодня і після кожної зміни |

Припущення: сховище секретів обирається з тих, що мають регіон даних у ЄС, окремі простори на середовище, журнал читань і автентифікацію GitHub Actions через OIDC з умовами на гілку і файл робочого процесу (кандидати — Infisical, Bitwarden Secrets Manager); перед підключенням перевіряється, що потрібні можливості є в доступному тарифі.
