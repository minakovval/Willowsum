# CICD-12 · Зберігання секретів і доступів

**Реліз:** PoC (секрети поза репозиторієм і чатами, перевірка конфігурації під час старту, головний ключ лише через порт KMS, тестові ключі агентів, сканер секретів); MVP (сховище секретів, OIDC-доступ конвеєра, секрети production, ротація, журнал читань, пакет секретів, головний ключ у керованому KMS хмари) · **Пріоритет:** M

**Зв'язки**
- Зрізи: CICD-12@PoC, CICD-12@MVP
- Модуль: —

Секрети (ключі, паролі, токени) створюють і розносять машини, а не люди. Людина вводить лише кілька кореневих доступів один раз і ніколи — у чат, код, задачу чи документ.

**Де що зберігається**

| --- | --- | --- |

| [лише PoC] Головний ключ шифрування | Лише через порт KMS; PoC і PoC v2 розгортаються лише локально (рішення власника 2026-11-16), тож ключ дає локальний адаптер KMS; керований KMS хмари хостингу — з MVP | Локальний адаптер KMS |
| [MVP] Головний ключ шифрування | Керований KMS хмари хостингу (OCI Vault в Oracle Cloud Infrastructure); у сховищі секретів не зберігається. | [MVP] Ключі зовнішніх сервісів (платежі, пошта, CAPTCHA, курси валют) | Те саме сховище, проєкт середовища | Власник один раз створює ключ у кабінеті сервісу і вставляє його у вебформу сховища |
| [MVP] Доступ конвеєра GitHub Actions до хмари | Без збережених ключів: короткоживучі токени через OIDC-довіру між GitHub і хмарою | Опис інфраструктури |
| [MVP] Доступ до сховища секретів production | Без збережених токенів у GitHub. Робочі процеси інфраструктури і розгортання з гілки main отримують короткоживучий доступ (запис для генерації, ротації і резервної копії) через OIDC-довіру сховища або хмари з умовою «цей репозиторій, гілка main, конкретний файл робочого процесу»; запуск із робочої гілки чи PR доступу не має. | [MVP] Доступ конвеєра до секретів CI | Машинний токен у GitHub Actions secrets з правом лише читати свій проєкт сховища; секретів production у GitHub немає | Власник один раз |
| Секрети для сесій агентів (тестові ключі пісочниць провайдерів) | Налаштування середовища Claude (секрети середовища), лише значення для локального середовища і CI | Власник один раз |

**Функціональні вимоги**

#. [PoC] Жоден секрет не зберігається в репозиторії, образах, логах, задачах, коментарях PR, документах і чатах з агентами. Агент ніколи не просить вставити секрет у чат; якщо секрету бракує, він називає змінну і місце, куди власник має її додати.
#. [PoC] Внутрішні секрети застосунку генеруються автоматично описом інфраструктури і записуються в сховище без показу людині: симетричні секрети і паролі — ≥ 32 байти криптографічно випадкових даних; асиметричні ключі підпису генеруються стандартною бібліотекою. Значення бачить лише власник, і лише під час розслідування інциденту.
#. [PoC] Застосунок під час старту отримує секрети зі сховища або з середовища запуску, яке наповнює конвеєр; конфігурація перевіряється схемою, і за відсутності секрету процес не стартує, називаючи змінну без значення.
#. [лише PoC] Головний ключ шифрування застосунок отримує лише через порт KMS (адаптер) і ніколи не бачить його значення поза адаптером. PoC і PoC v2 розгортаються лише локально (рішення власника 2026-11-16): ключ дає локальний адаптер KMS, а керований KMS хмари хостингу (OCI Vault) — з MVP. Головний ключ не записується в GitHub, логи конвеєра чи журнали.
#. [MVP] Головний ключ шифрування застосунок отримує лише через адаптер KMS; ключ створюється і живе в керованому KMS хмари, і застосунок ніколи не бачить його значення. Хостинг і резервні копії працюють за профілем «Старт», а головний ключ живе в керованому KMS хмари хостингу (OCI Vault в Oracle Cloud Infrastructure): значення ключа не залишає KMS, копій поза KMS немає. Головний ключ не записується в сховище секретів, GitHub, логи конвеєра чи журнали.
#. [PoC] Кожне середовище має окремі секрети. Секрети production недоступні агентам, CI для PR і будь-якому іншому середовищу.
#. [PoC] Агенти отримують лише тестові ключі пісочниць через секрети середовища Claude; для production вони діють тільки через дозволені дії конвеєра після схвалення власника.
#. [MVP] Ротація: внутрішні секрети — автоматично щонайменше раз на рік і негайно після підозри на витік, без простою (головний ключ — переобгортанням ключів просторів у фоні); ключі зовнішніх сервісів — за нагадуванням власнику раз на рік. Кожна ротація записується в журнал.
#. [MVP] Кожне читання секретів production машинним доступом записується в журнал сховища; доступ людей до значень production — лише власника, з другим фактором.
#. [PoC] Якщо сканер секретів знаходить секрет у коді або історії, PR блокується, а знайдений секрет вважається скомпрометованим і ротується.
#. [MVP] Сховище секретів доступне лише через адаптер, тож його можна замінити на керований сервіс секретів хмари без зміни імен секретів; головний ключ уже живе в керованому KMS. Інших профілів розгортання в цьому релізі немає.

[MVP] **Що робить власник один раз**

- [MVP] Створює акаунт сховища секретів і проєкти на середовища, видає машинні токени.
- [MVP] Додає токен сховища для CI у GitHub Actions secrets; токен production (лише читання) — на хост production; тестові ключі — у секрети середовища Claude.
- [MVP] Налаштовує OIDC-довіру сховища і хмари до гілки main і робочих процесів інфраструктури та розгортання і підтверджує кожну зміну цих умов схваленням у PR: коментарем з рядком «Схвалюю» / «Approved» або рішенням з чату, записаним в описі PR рядком «Рішення власника (РРРР-ММ-ДД): схвалено …».
- [MVP] Створює ключі зовнішніх сервісів у їхніх кабінетах і вставляє у вебформу сховища.

[MVP] Усе інше (паролі БД, ключі шифрування, ключі підпису) створюється і оновлюється автоматично.

| Критерій | Поріг | Перевірка |
| --- | --- | --- |
| Секрети в репозиторії, історії git, образах, логах | 0 | Сканер секретів на кожному PR і щотижня по всій історії |
| [MVP] Секрет, згенерований людиною вручну для внутрішніх потреб застосунку | 0 | Рев'ю опису інфраструктури |
| [MVP] Доступ агентів, CI для PR або інших середовищ до секретів production | Відсутній | Щоквартальний перегляд прав сховища |
| [MVP] Доступ тимчасового середовища перевірки відновлення | Короткоживучий доступ через OIDC лише для робочого процесу відновлення з main: читання копій і розшифрування їхнього ключа; секретів застосунку production немає | Тест: середовище не бачить секретів застосунку production, запуск не з main отримує відмову OIDC |
| Старт процесу без обов'язкового секрету | Відмова з назвою змінної, без значення | Тест |
| [MVP] Вік внутрішнього секрету production | ≤ 12 місяців | Щомісячна перевірка конвеєром |
| [MVP] Робочий процес не з гілки main, що отримав доступ до секретів або хмари production | 0 | Тест: запуск із робочої гілки отримує відмову OIDC |
| Застосування інфраструктури, розгортання в production або зміна робочих процесів, які це роблять, чи налаштувань довіри до них (OIDC, сховище секретів production) чи DNS production, злиті без схвалення власника в PR (коментар з рядком «Схвалюю» / «Approved» або рядок «Рішення власника (РРРР-ММ-ДД): схвалено …» в описі PR) | 0 | Щоденна перевірка злитих PR |
| [MVP] Резервна копія секретів | Пакет, зашифрований відкритим ключем власника, в окремому сховищі; головний ключ не залишає KMS і в пакет не входить; приватний ключ — лише в менеджері паролів власника і на паперовій копії | Конвеєр щодня і після кожної зміни |

[MVP] Припущення: сховище секретів обирається з тих, що мають регіон даних у ЄС, окремі простори на середовище, журнал читань і автентифікацію GitHub Actions через OIDC з умовами на гілку і файл робочого процесу (кандидати — Infisical, Bitwarden Secrets Manager); перед підключенням перевіряється, що потрібні можливості є в доступному тарифі.
