## Частина A. Перевірка вимірювання

### A1. Чи cache read — правильна міра витрат

**Як сукупна міра — так, як міра для порівняння дій — ні.**

- На рівні сесій cache read, output і ≈ USD майже пропорційні: кореляція Пірсона USD з cache read 0,99, з output 0,99, cache read з output 0,997 (20 сесій, де є всі три числа, без «ведучого 2», чий USD не включає агентів). Долар на мільйон cache read: 0,36–0,56, медіана 0,44, коефіцієнт варіації 0,13. Тобто сума cache read передбачає суму доларів з похибкою ≈ ±15 %.
- Але cache read — лише близько половини рахунку. Метод: моделі з репозиторію (`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-fable-5-2`), ціни з довідки API (Opus 5.5: 4 / 20 $ за млн input / output, читання кешу 0,20 $; Sonnet 5.5: 2 / 10 $, читання 0,10 $; Fable 5.2: 8 / 40 $). Для тих самих 20 сесій: cache read × 0,20 ≈ 48 % USD, output × 20 ≈ 17 %, **решта ≈ 36 % — записи в кеш і некешований input, яких #180 не записує**. Це оцінка: я не знаю таблиці цін, за якою платформа рахує `cost_usd`, усе пораховано за ціною Opus, частка Fable зсуває результат. Регресія USD на cache read і output разом нестійка (змінні колінеарні): 0,042 $ за млн cache read і 105 $ за млн output, R² 0,987 — коефіцієнт output «вбирає» невидимі записи в кеш.
- Співвідношення цін інше, ніж у завданні: читання кешу в Opus 5.5 у 20 разів дешевше за input (не в 10), output у 5 разів дорожчий за input, тобто токен output у 100 разів дорожчий за токен cache read. В агентів 8 687 млн cache read проти 37,2 млн output (233 : 1), тож у доларах cache read ≈ у 2,3 раза більший за output.
- **Запис у кеш — найімовірніша невидима стаття (припущення).** Кеш живе 5 хвилин (або 1 годину — залежить від режиму платформи, я цього не перевірив). Агент, що чекає CI довше за строк життя кешу, на наступному виклику записує весь контекст наново: 250 тис. токенів за ціною запису (≈ 5 $ за млн) — ≈ 1,25 $ за одне «пробудження» проти 0,05 $ за читання. Те саме стосується ведучого між повідомленнями агентів. Перевірка: сума `cache_creation_input_tokens` із журналів.
- **Моделі не зважено.** Sonnet удвічі дешевший за токен, Fable (за вашим правилом у `token-economy.md`) витрачає ліміт удвічі швидше. 9 дій з 24 — категорія «модель»: вони змінюють ціну токена, а не кількість. Перехід автора з Opus на Sonnet може навіть збільшити cache read (більше кроків) і при цьому здешевити роботу. Розподіл за моделями є у 316 з 375 рядків (Opus 5 189 млн, Sonnet 1 612, Fable 439; разом 7 240 з 8 687 млн), тож зважити можна вже зараз.

**Виправлення.**
1. `tools/token-report batch`: додати в рядок PR і в «Сесії» колонки `cache write` та `input` (у `usage` журналів вони є) і колонку «умовні $» = сума за моделями (cache read, cache write, input, output × ціна моделі). Ціни — один JSON-файл у `tools/token-report`.
2. До того часу на сторінці — «токени у вазі Opus»: Opus × 1 + Sonnet × 0,5 + Fable × 2 (рядки без розподілу — як Opus).

### A2. Ведучого в ціні пункту немає

- Власні витрати ведучого за його журналом (примітки «Сесій»): ведучі 3–12 — 37,6–74,8 млн за сесію, 13–31 %; ведучий 34 — 138,8 млн (18 %, 630 викликів моделі); огляд 35 для ведучих 28–34 — 626 млн з 3 357 (19 %).
- У перерахунку на PR (власні токени ÷ злиті PR сегмента): 62,0/8 = 7,8; 74,8/9 = 8,3; 50,8/8 = 6,4; 39,4/6 = 6,6; 37,6/5 = 7,5; 48,2/7 = 6,9; 42,7/6 = 7,1; 37,7/6 = 6,3; 42,9/8 = 5,4; 138,8/23 = 6,0; 626/109 = 5,7. Тобто **5,4–8,3 млн cache read на кожен злитий PR**, майже незалежно від розміру. Для PR типу «процес» і «вимоги» (8–10 млн агентів) ведучий коштує стільки ж, скільки всі агенти PR.
- 7 дій з 24 спрямовані на ведучого (#279, #380, #517, #751, частково #320, #360, #753). Метрика «cache read агентів ÷ пункти» не може показати їхнього ефекту за побудовою.
- Рядок «Сесії» має три визначення: «лише ведучий» (2, 15–19), «з агентами» (3–14, 26–34) і невідомо. Віднімання «сесія мінус рядки PR» дає частку ведучого від −68 % до +54 % (ведучі 6, 18, 30 — агенти більші за сесію). Огляди 24, 27 і 35 тричі записали «одне визначення „Сесій“» у чергу й не зробили.
- 12 сесій без USD (15–25 і частково 13), у 6 з них немає й cache read.

**Виправлення.** У «Сесії» три колонки: разом, агенти, сам ведучий (`token-report session` уже це рахує; `batch` має викликати його сам). На сторінці — рядок «ведучий, млн на PR» і ціна пункту «з ведучим»: власні токени ведучого сегмента діляться порівну на PR сегмента. Прогноз токенів до кінця PoC зараз занижено на ≈ 20–25 % з цієї причини.

1. **Епохи замість 24 рядків.** Дії, злиті протягом 24 годин, — один «пакет» (вийде ≈ 9). Порівнювати цілі періоди між пакетами; PR відносити до періоду за часом відкриття (перший коміт), не злиття.

   - контекст ведучого — млн cache read ведучого на PR;
   - синхронізації — частка PR із синхронізацією.
4. **Два знаменники.** Пункти — лише для вікон від 40 PR або тижня. Для коротших порівнянь — змінені рядки коду й тестів (ваш Спірмен 0,78 проти 0,37 для пунктів) або «витрати проти очікуваних»: очікування з простої моделі (тип, рядки, `sensitive`), ефект дії — зсув залишків.
5. **Корекції вимог окремо.** Парасолькові PR корекцій (#695, #705, #722, #733) — тип «корекція вимог», поза ціною пункту «код».
6. **Розкладати ціну.** Ціна пункту = (токени на PR) × (PR на пункт). Поруч — суміш: частки типів, `sensitive`, другого кола, моделей.

### A4. Дрібніші помилки

- **Колонка «Раунди» з 27.11 рахується інакше.** `batch` пише «кількість рядків `r`» (README `token-report`), а підтвердження — роль `c`. Сесій із ціною 19 із 34, пунктів у них 661 з 1 280.
- **`subagent_tokens`** у нових рядках 0; у #745, #746, #736 нулі й у часі. Колонку прибрати.
- **Тип парасольки** — «тип найбільшої частини»: #705 став «код», хоча це корекції вимог.
- **Два рядки без cache read** (#211, #406: «лише ведучий») у ціну не входять — ще один наслідок відсутності ведучого.
- **«Спірмен 0,84 на рівні зрізу»** показує, що більший зріз коштує більше; він не доводить придатності пункту для порівняння періодів.

3. **Ведучий — фіксований податок на PR**, тому дрібні PR (процес, вимоги, виправлення: 148 PR, 39 % кількості) коштують удвічі більше, ніж показує їхній рядок.

## Пропозиції, за очікуваною економією

Відсотки — від усіх витрат (агенти + ведучий, у вазі цін). Пропозиції перекриваються; сума без подвійного рахунку — **20–30 %**. Спершу треба виправити вимірювання (A1–A3), інакше ефекту не буде видно.

### 1. Автор: менший контекст, без очікування CI, передача на 150 тис. — 5–10 %

- **Що.**
  - Автор закінчує після локальних перевірок і push. CI чекає скрипт ведучого `merge-ready.mjs --wait`. Червоний CI — новий агент із журналом збою (`investigate-ci-failure`).
  - Автор, чий контекст перейшов ≈ 150 тис., робить WIP-коміт, пише 10 рядків стану й передає роботу новому агенту. Зараз поріг 100 тис. є лише для відновлення (`token-economy.md` п. 5); у старих рядках автори закінчували на 200–380 тис. (`subagent_tokens`: 309 579, 324 474, 378 108).
  - Тихі звіти тестів (лише збої), читання великих файлів частинами, одна самоперевірка замість двох (`implement-requirement` §4, останній пункт, і §5 «Self-check» — те саме двічі).
- **Метод оцінки.** Cache read ≈ кроки × середній контекст. Агент, що дійшов до 300 тис., має середній контекст ≈ 150 тис.; два агенти по 150 тис. — ≈ 75 тис. плюс повторне читання ≈ 30–40 тис. Це −25–35 % для таких авторів. Автор коду ≈ 0,58 × 0,55 ≈ 32 % токенів агентів; якщо половина авторів доходить до порога: 0,3 × 0,5 × 32 % ≈ 5 % агентів, з UI — до 6 %. Частка очікування CI невідома, доки немає колонки cache write; тому діапазон 5–10 %.
- **Ризик якості.** Середній: новий агент не знає рішень попереднього. Пом'якшення: стан у тілі PR, тести вже написані першими.
- **Ризик швидкості.** Малий: +3–5 хв на передачу.
- **Що змінює.** `implement-requirement/SKILL.md` (шапка «CI green», §4, §5, форма звіту), `screen-from-canvas`, `token-economy.md` п. 5, `pr-pipeline/SKILL.md` крок 3.
- **Як виміряти.** Токени ролі `a` на PR і на 1 тис. рядків; cache write ролі `a`; хвилини автора.

### 2. Менше других кіл — 5–8 %

- **Що.**
  - «Changes requested» лише за трьох підстав: критерій без тесту або з хибним тестом; порушене жорстке правило; гроші, дані, безпека. Решта — «Ready» із записом у «Follow-ups» або правкою рецензента.
  - Ліміт правки рецензента — з 60 до ≈ 150 рядків для PR без `sensitive` (проба A: 14 з 15 правок обійшлися без раунду автора; одноколових UI стало 10/12 замість 7/18).
  - Підтвердження без агента, коли виправлення дослівно дорівнює латкам рецензента: скрипт порівнює `git diff` голови з латками; збіг і зелений CI — підтверджує ведучий, як уже робить для синхронізації.
  - У примітці #180 — причина другого кола (`r2: тест`, `r2: правило`, `r2: безпека`, `r2: інше`). Огляд 27 це пропонував, не зроблено.
- **Метод оцінки.** Надлишок багатоколових — 29 % токенів агентів; причинна частина, за моєю оцінкою, половина (≈ 15 %). Зниження частки з ≈ 50 % до 30 % прибирає ≈ 40 % цього: 6 % агентів ≈ 5 % усього, плюс ведучий і CI (CI двоколового кодового PR — 63 хв проти 36).
- **Ризик якості.** Середній: вада з категорії «інше» піде у follow-up і може загубитися; правка на 150 рядків — код без незалежної рецензії. Пом'якшення: `sensitive` і файли фундаменту виключено, CI на новій голові обов'язковий.
- **Ризик швидкості.** Прискорює: мінус 25–60 хв на PR.
- **Що змінює.** `review-pr/SKILL.md` §7 і правила вердикту, `merge-rules.md` («Merge on Ready»), `pr-pipeline/SKILL.md` крок 5, рішення `2026-11-17-owner-process-rules.md`, `2026-11-19-owner-reviewer-patch-paths.md`, п. 3 частини 2 `2026-11-27-owner-rules-rewrite.md`.
- **Як виміряти.** Частка PR з `f` або `c`; токени `f` + `c` на PR; розподіл причин `r2`.

### 3. Ведучий: стиснення на ≈ 120 тис., один скрипт стану — 5–7 %

- **Що.**
  - Поріг автостиснення 200 → ≈ 120 тис. (#179 оновлювати з ≈ 100 тис.).
  - Скрипт `pipeline-status`: один виклик повертає таблицю «PR → голова, CI, вердикти на голові, behind_by, мітки, агент» замість кількох `gh api` на PR.
  - Перестати писати коментар-ретроспективу на #180 після кожної сесії (лишити один в огляді процесу); вартість у щоденному звіті рахує скрипт.
- **Метод оцінки.** Ведучий ≈ 20 % усього. Середній контекст між стисненнями: з ≈ 115 тис. (30 → 200) до ≈ 75 тис. (30 → 120), −35 %; викликів −15–20 %; разом ≈ −45 % ведучого мінус вартість самих стиснень — 5–7 % усього. Оцінка груба: ефекту порога 400 → 200 тис. ще ніхто не виміряв.
- **Ризик якості.** Середній: частіше стиснення — частіше втрата деталей (у сесії 34 губилися брифи). Пом'якшення: хук після стиснення, стан у #179.
- **Ризик швидкості.** Малий.
- **Що змінює.** `CLAUDE_CODE_AUTO_COMPACT_WINDOW` (дія власника), `restarts.md`, `merge-checklist.md`, `token-economy.md` («Session retrospective»), рішення `2026-11-15-owner-auto-compact.md`, `2026-11-17-owner-compaction-trial.md`, п. 1 частини 2 `2026-11-27-owner-rules-rewrite.md`.
- **Як виміряти.** Млн cache read ведучого на PR; викликів на PR; середній контекст виклику (`token-report session`).

### 4. Sonnet-автор для серверного коду поза фундаментом — 3–4 % грошей, 0 % токенів

- **Що.** Зараз серверні PR пише Opus (86 % токенів «код»). Автор на Sonnet для рівня «Функціональність» без `sensitive` і для частин «лише тести»; Opus — фундамент, гроші, схема, права.
- **Метод оцінки.** Автор коду ≈ 32 % токенів агентів; третина на Sonnet за пів ціни — ≈ 5 % витрат агентів ≈ 4 % усього. Частку серверних PR без `sensitive` я не рахував (роль `s` мають 68 з 72 кодових рядків із ролями), тож реально може бути 1–2 %.
- **Ризик якості.** Середній: більше знахідок і других кіл. UI на Sonnet цього не показав (друге коло в #500–#650 — 45 %, як раніше), але серверний код складніший.
- **Що змінює.** Таблиця ролей у `token-economy.md` п. 1, рішення `2026-11-17-owner-limit-and-models.md`, `2026-11-20-owner-sonnet-reviews.md`.

### 5. Дрібні PR пакетами — 3–4 %

- **Що змінює.** `pr-pipeline/SKILL.md` крок 3, `merge-rules.md` «Review tiers», `security-review/SKILL.md`, `token-economy.md` п. 1.
