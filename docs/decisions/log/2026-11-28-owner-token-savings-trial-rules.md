# Рішення власника 2026-11-28: правила пробного запуску з економії токенів (пропозиції 1 і 2)

**Створено:** 2026-11-28

Рішення власника, передане з прямої сесії «Дашборд ефективності токенів» і підтверджене у чаті ведучого. Джерело порад:
`docs/validation/token-review-2026-11-28.md` (PR #772), частина B, пропозиції 1 і 2. Цей запис — PR 2 плану; інструменти
(PR 1) описує `2026-11-28-owner-token-savings.md`. Журнал лише дописується.

## Слова власника (дослівно)

- Сесія дашборда: «так, виправляй розрахунки для дошборда і всі поради з з економії з середнім та малим ризиком передавай оркестратору на імплементацію».
- Раніше в тому ж чаті: «мої правила і рішення можна переглядати».
- Питання ведучого 1: «Підтверджуєте цей план?» (а — так, починай з PR 1 і PR 2; б — змінити). Відповідь: «1 а, 2 поки не буду змінювати, не зрозумів скнсу».
- Не впроваджуємо: пропозицію 6 і список «не робити» огляду. Поріг стискання ведучого (`CLAUDE_CODE_AUTO_COMPACT_WINDOW`) не змінюється, доки власник не вирішить.

## Пробний запуск

Правила нижче — **проба на наступному розділі плану, ≈ 20 PR коду**. Результат перевіряється на огляді процесу:
токени ролей `a`, `f`, `c` на PR; частка PR з другим колом; причини других кіл; скільки латок рецензента й скільки
виправлень без підтвердження агента; скільки PR потрапило на передачу автора. Погіршення якості (вади, що пройшли в
`main` через «Ready» + follow-up або латку) — підстава повернути старі правила. Без перевірки на огляді проба не
стає постійною.

## Що змінюється

Кожне правило записане в одному місці; в інших — вказівник.

**Пропозиція 1. Автор** (текст: `.claude/skills/implement-requirement/SKILL.md`, «Stop and hand over», §4, §5)
1. Автор закінчує після локальних перевірок і push; CI не чекає. Червоний CI — новий агент із `investigate-ci-failure`.
2. На ≈ 150 тис. контексту автор робить WIP-коміт, пише 10 рядків стану (у тіло PR або в scratchpad) і зупиняється з цією
   передачею в звіті; ведучий запускає нового агента.
3. Тихі репортери тестів, великі файли читати частинами.
4. Одна самоперевірка замість двох: останній пункт §4 злито з §5 «Self-check before review».
   Вказівники: `screen-from-canvas/SKILL.md`, `pr-pipeline/references/token-economy.md` п. 5, `pr-pipeline/SKILL.md` крок 3.

**Пропозиція 2. Менше других кіл**
1. «Changes requested» лише за: критерій без тесту або з хибним тестом; порушене жорстке правило; гроші, дані, безпека.
   Решта — «Ready» плюс follow-up або латка рецензента (`review-pr/SKILL.md` §3; вказівник у `merge-rules.md`).
2. Ліміт латок рецензента: ≈ 150 рядків для PR без `sensitive` (було 60); для `sensitive` — 60. Файли фундаменту
   виключено (`review-pr/SKILL.md` §7).
3. Без агента підтвердження, коли виправлення дослівно дорівнює латкам рецензента: `tools/pr-rules/patch-equal.mjs
   <old-head> <new-head> <patch-file…>` друкує `equal` або `differs` з іменами файлів; при `equal` і зеленому CI
   підтверджує ведучий (`pr-pipeline/SKILL.md` крок 5).

**Рішення ведучого (2026-11-28; власник не схвалював; PR #774):** без агента-підтвердження лише для PR без мітки sensitive; sensitive завжди отримує підтвердження агентом (`pr-pipeline/SKILL.md` крок 5).
