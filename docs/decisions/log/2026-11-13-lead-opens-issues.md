# Рішення 2026-11-13: GitHub issues створює лише ведучий; новий сеанс ведучого; свіжі рецензенти

**Створено:** 2026-11-13 · **Оновлено:** 2026-11-13

- 2026-11-13, власник (чат ведучому, за повідомленням ведучого): GitHub issues створює лише ведучий, не виконавці й
  рецензенти. Причина: автоматичний класифікатор дозволів у сесіях агентів блокує записи у зовнішні системи, спроба
  агента зазнає невдачі, і ведучий мусить вирішувати, чи повтор є обходом відмови. Агенти не створюють issues:
  наступні кроки вони перелічують у розділі «Follow-ups» тіла PR або у звіті, ведучий відкриває issues і додає
  посилання. Оновлено AGENTS.md; skills `pr-pipeline`, `implement-requirement`, `review-pr`, `security-review`,
  `change-requirement`, `fix-review-findings`, `investigate-ci-failure`; довідники `flaky-tests`,
  `requirements-format`, `hard-rules-checklist`, `review-checklist`.
- 2026-11-13, власник (чат ведучому, за повідомленням ведучого): окремого суворішого правила щодо відмов
  класифікатора дозволів не потрібно, а про суто технічні відмови власника не питати; чинні жорсткі правила не
  змінюються.
- 2026-11-13, власник (чат ведучому, за повідомленням ведучого): (a) новий сеанс ведучого — коли контекст ведучого
  уже стиснуто або після 8–10 злитих PR він не починає нових завдань, дочекається завершення агентів, записує
  стан в issue «Lead state» (відкриті PR із head і вердиктами, робота, питання власнику, follow-ups, наступні
  рядки плану) і просить власника почати новий сеанс, який спершу читає цей issue (`pr-pipeline`,
  `references/restarts.md`); (b) кожна рецензія, перша чи повторна, — свіжому агентові з вузьким завданням, без
  відновлення рецензента з довгим контекстом (`references/token-economy.md`).
