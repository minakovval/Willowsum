# Заміна ключів даних: перевірка до першого запису і скасування (NFR-01@PoC п. 3)

**Створено:** 2026-11-27

Привід: рев'ю PR #736 (review-pr, пункт (a); безпековий огляд, follow-up 1): значення, яке не відкриває жоден ключ,
залишало простір під `SPACE_KEY_ROTATING` назавжди.

Рішення ведучого (2026-11-27; власник не схвалював; PR #736, раунд рев'ю 1): дрібні деталі, вирішені в PR.

- **Перевірка.** Перед першим записом (і в `--dry-run`) кожне значення простору відкривається старим ключем (і новим,
  якщо заміна вже почалась). Хоч одне не відкривається — простір не починається: він лишається зі старим ключем і
  працює як раніше, рахується в `failed`, а звіт називає лише модуль і кількість (`unopenable`), без id і значень.
  Інші простори замінюються як звичайно. Перевірка обходить ту саму вибірку, що й заміна (`ResealPart.unopenable`),
  але через власний замкнений обхід частини, тож точки зупинки тестів (обгортки `reseal`) її не зачіпають.
- **Скасування.** `kms:rotate-data-keys --abort` (`pnpm local:dev --rotate-data-keys --abort`) запечатує всі значення
  незавершеного простору назад старим ключем, також після завершених частин і файлів; значення, яке не відкриває
  жоден ключ, лишається як є і рахується. Потім запис `household.space-key`/`delete` нового ключа в журналі простору і
  видалення рядка заміни під замком. Старий ключ лишається `exposed`: наступний запуск замінить його знову.
