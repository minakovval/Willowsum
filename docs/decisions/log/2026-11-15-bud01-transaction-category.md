# Рішення 2026-11-15: BUD-01@PoC b) — категорія транзакції (серверна частина)

**Створено:** 2026-11-15

Дрібні рішення виконавця PR «BUD-01: category of a transaction — categorization module, «Без категорії», change by
hand, «Змінити категорію» (server part b)» (хвиля 2, рядок 20; #272 п. 1). Рішення ведучого (2026-11-15; власник не
схвалював), кожне:

- Категорію транзакції і її джерело зберігає модуль `categorization` (таблиця `transaction_categories` за
  ідентифікатором транзакції), як записано в картках `categories` і `categorization` і в рішенні про видалення
  категорії (#260). `transactions` дає лише читання — `createTransactionLookup` (`facts`, `select`), бо
  `categorization` залежить від `transactions`, а не навпаки.
- Ключ функції і прапорець випуску маршрутів — `categories.tree`, як у дерева категорій (BUD-01 ключа не називає);
  ліміту плану немає (BUD-01 «Ліміти плану»).
- API: `GET` і `PUT /v1/transactions/{transactionId}/category`; `categoryId: null` — «Без категорії» з джерелом
  «немає». Колонка й фільтр «Категорія» списку транзакцій — не в цьому PR (follow-up).
- Тип категорії зі знаком суми не звіряється: повернення (надходження) отримує категорію витрат початкової покупки
  (BUD-01 п. 1). Прихована категорія доступна; об'єднана, службова («Переказ», «Коригування»), невідома чи іншого
  простору — 400 `categoryId: not_found` (п. 9; так само, як у частин розділення).
- Власну категорію не змінюють: сторона переказу (409 `TRANSACTION_IN_TRANSFER`; «Переказ» дає п. 7), розділена
  транзакція (новий код 409 `TRANSACTION_SPLIT`: категорії мають частини, п. 6, FIN-03 п. 23), злитий дубль (409
  `TRANSACTION_MERGED`, FIN-03 п. 11).
- Запис аудиту — сутність `categorization.transaction-category` з ідентифікатором транзакції, дія `update`, поля
  `categoryId` і `source`; передача після коміту задачею черги модуля (ADR-0015), щоденне повернення задач `dead` —
  `categorization.recovery` (#249).
- Об'єднання категорій (п. 8) переносить транзакції задачею події `categories.merged`; джерело категорії лишається.
- «Змінити категорію» (DAT-03 п. 2): ціль `transactions` дає `categorization` з полями `category` і `source` (щоб
  «Відмінити» повертало і джерело); транзакція з тією самою категорією — «без змін» незалежно від джерела; категорія
  поза деревом — «невалідний» для всіх записів. Дії «Додати теги» (рядок 21) і «Підтвердити категорії» (рядок 24)
  мають ту саму сутність `transactions`: їхні PR складають одну ціль з полів кількох модулів (follow-up).
- Рушій списку DAT-01 отримав `ids(q, { filter, sort }, { excluded, limit })` для «Вибрати всі M за фільтром»: ті самі
  фільтр, сортування й права, що й у сторінки.
- «Порожня» категорія (п. 12): рядок видаленої транзакції не є вжитком (`categorization` питає `transactions`, чи є
  транзакція); сам рядок лишається до видалення простору (follow-up: подія видалення транзакції).
