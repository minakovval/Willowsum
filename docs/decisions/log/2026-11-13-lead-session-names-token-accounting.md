# Рішення 2026-11-13: назви сесій ведучого, облік токенів, підтвердження для PR лише з документацією, ліміт відновлень агента, підтвердження передачі сесій, рішення власника в документах, чат лише про важливе

**Створено:** 2026-11-13 · **Оновлено:** 2026-11-13

- 2026-11-13, власник (чат ведучому, за повідомленням ведучого; #180): облік токенів обов'язковий відтепер, ще до
  виходу процесного PR, що його записує. На старті і в кінці сесії ведучий читає `get_session` → `usage`
  (`cache_read_tokens`, `output_tokens`, `cost_usd`) і записує в issue «Облік токенів» (#180) знімок на старті та
  різницю. У тому самому ході, що й злиття, ведучий додає рядок PR: тип (код / UI / вимоги / процес /
  виправлення), раунди, сума `subagent_tokens` автора, усіх рецензентів і підтверджень. Раз на тиждень — аналіз:
  найдорожчі типи PR і частка самого ведучого.
- 2026-11-13, власник (чат ведучому, за повідомленням ведучого; #178): назви сесій ведучого —
  `Willowsum · ведучий N · <з чого починає>`. Нова сесія на старті перейменовує себе (`set_session_title`); перед
  завершенням дописує до назви «(завершено)» і вказує в «Lead state» назву для наступної.
- 2026-11-13, власник («так» на пропозицію ведучого; #178): PR лише з документацією чи `.claude`, якщо після
  оновлення з `main` його файли не перетинаються зі змінами `main`, не потребує агента підтвердження; ведучий сам
  перевіряє однією командою, що власний diff PR не змінився.
- 2026-11-13, власник («так» на пропозицію ведучого; #178): CI кількох PR очікувати однією командою, а не окремими
  ходами.
- 2026-11-13, власник (за ретроспективою токенів сесії «ведучий 1», #180; #178): агента-автора відновлюють не
  більше 2 разів; третій раунд правок — свіжий агент із коротким завданням (diff, знахідки, патч). Великі
  перенесення scope і міграції ділять на частини: один агент — одна частина.
- 2026-11-13, власник (чат ведучому, за повідомленням ведучого): кожну передачу між сесіями ведучого
  підтверджують власнику в чаті повністю, пункт за пунктом: що зроблено з кожним пунктом і де це записано
  (файл навички чи інструкції, PR або issue, з посиланням). Пункт без дій позначають як не виконаний, з
  причиною. Скорочений підсумок не зараховується.
- 2026-11-13, власник (чат ведучому, за повідомленням ведучого): кожне рішення власника записують у конкретний
  документ (журнал рішень, навичка, AGENTS.md, вимога) і переносять у відповідні правила; ведучий ніколи не
  тримає рішення лише в пам'яті сесії.
- 2026-11-13, власник (#178): у чаті з власником — лише важливе з продуктової точки зору. На службові
  сповіщення (CI, підписка на PR, проміжний стан агента, «чекаю на коміт») ведучий не пише власнику нічого,
  навіть одного рядка; пише лише коли PR злито, потрібне рішення власника або є проблема.
- Рішення ведучого (2026-11-13; власник не схвалював; PR «PRC-02: назви сесій ведучого, облік токенів»): виняток
  щодо підтвердження не діє для PR з міткою `sensitive`; без змін лишаються CI на новій голові і `behind_by` = 0;
  перевірка побайтово порівнює повний diff PR (з повними хешами blob) до і після оновлення; ведучий публікує
  її вивід і обидва SHA як рецензію PR, що називає нову голову і закінчується `Verdict: Ready` (щоб щоденна
  перевірка `main`, ADR-0008, бачила вердикт на злитій голові). Причина: виняток не має послаблювати правила безпеки.
