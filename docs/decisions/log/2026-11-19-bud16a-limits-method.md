# Рішення 2026-11-19: BUD-16@PoC a — метод «Ліміти» і «План місяця» (серверна частина)

**Створено:** 2026-11-19

Рішення ведучого (2026-11-19; власник не схвалював; BUD-16; рядок 32 хвилі 2, `docs/plans/poc-wave-2.md`):

1. Метод не зберігається: у PoC він один — «Ліміти» (п. 1). Ні поля `method`, ні маршруту зміни методу, ні історії
   методів у моделі й API немає; поле з'явиться разом із PoC v2 (BUD-16@PoC v2 п. 2), без міграції зараз.
2. «План місяця» (п. 4) віддає новий маршрут `GET /v1/budget/trend?from=YYYY-MM&to=YYYY-MM[&categoryId=]` (`getBudgetTrend`):
   для кожного місяця `plan` (сума лімітів; завершений місяць — зі знімка, як BUD-02 п. 11), `spent` і `income`.
   Порівняння «факт / план» (BUD-06, рядок 36) і «Тренд» (рядок 133) беруть план звідси або з того самого правила
   `monthPlan` (`domain/trend.ts`).
3. Прапорець випуску і ключ функції — окремий `budget.trend` (вимкнений під час постачання), щоб «Тренд» вмикався
   незалежно від бюджету періоду (`budget.period`).
4. Проміжок — не більше 120 місяців (10 років) за запит: «Усе» перемикача графіка; більше — 400 `from: too_many_months`.
5. Місяць до першого періоду бюджету: витрати й дохід є, `plan` = null (лінії плану немає). Бюджету немає — 404, як
   `GET /v1/budget/periods/{period}`.
6. `spent` — усі витрати місяця: категорії з лімітом, «Поза планом» і «Без категорії» (як BUD-02 п. 12). З фільтром
   категорії (BUD-06 п. 7) — витрати й ліміт цієї категорії; без ліміту в тому місяці — `plan` null; `income` — завжди
   дохід місяця. Фільтр — активна або прихована категорія витрат простору; інша — 400 `categoryId: not_found` /
   `not_expense`.
7. Суми поза межами грошового типу — те саме правило, що в бюджеті (#586, `adapters/money-range.ts`): кожен місяць
   читається тим самим `budgetReads`, пропущені суми додаються в `approximate.unavailableCount` за всі місяці.
8. Факти, не поради (п. 5): відповідь має лише місяці, режими, валюту, суми й лічильники — жодного тексту.
