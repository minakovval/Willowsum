# Рішення 2026-11-28: файл історії у виписці — розпізнавання і передача (BUD-21 j, рядок 243)

**Створено:** 2026-11-28 · **Оновлено:** 2026-11-28

Серверна частина BUD-21@PoC п. 2, AC2 та IMP-08@PoC п. 17. Це новий рядок 243 плану `docs/plans/poc-wave-2.md`, від
якого залежить рядок 240 (веб). Автор рядка 240 повідомив про блокер: майстер не може спитати «це файл історії?», бо
серверу бракує трьох речей. Перша — у розборі виписки немає ознаки файлу історії. Друга — немає кроку, який переносить
файл із партії виписок у власну партію файлу історії. Третя — немає прапорця «імпортувати як виписку». Нижче — рішення
ведучого. Власник їх не схвалював.

## Рішення ведучого

- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 2): веб не завантажує байти файлу вдруге. Для «вивести
  правила» сервер сам читає збережений оригінал виписки і зберігає його як «файл історії». Збереження проходить ті самі
  перевірки, що й завантаження (п. 3). Потім файл виходить із партії виписок, а його оригінал виду «виписка» видаляється.
  Чому: файл уже прийнято й перевірено. Друге завантаження подвоїло б трафік і час, а користувач міг би підкласти інший
  файл під тим самим питанням.
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 2): майстер питає про файл, коли розпізнавання з рядка
  233 знаходить у ньому колонку категорії, підкатегорії чи позначки переказу (`historyFile.looksLikeHistory`). Колонка
  тегів сама по собі не підстава питати. Колонка «рахунок» до розбору користувача не належить: банк теж може друкувати
  в колонці номер картки. Чому: п. 2 називає колонку категорії або позначки переказу; підкатегорія — частина категорії.
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 2): «імпортувати як виписку» — це поле `asStatement`
  файлу в «Розібрати» (`POST …/parse`). З ним колонки категорії, підкатегорії, позначки переказу й тегів отримують роль
  «ігнорувати». Тому жодна їхня клітинка не стає описом, контрагентом, посиланням чи категорією транзакції. Відповідь
  зберігається з розбором файлу (`file_parses.as_statement`, міграція 0012). Наступне «Розібрати» без цього поля її
  лишає, а `false` повертає читання колонок. Чому: розбір файлу вже має свої параметри (рецепт, рахунок), і відповідь
  на питання майстра — ще один такий параметр. Окремого кроку для неї не потрібно.
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 2, IMP-08 FR 17): файл може вийти з партії у станах
  «завантажено», «розібрано», «потребує перегляду» і «не вдалося розібрати». У стані «в обробці» він не виходить (409),
  а з застосованої партії — теж ні. Сервер не вимагає, щоб файл був розпізнаний як історія. Якщо в файлі бракує колонок,
  крок «Перевірка розпізнавання» сам скаже, яких саме (AC3).
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 2): після виходу файлу стан партії рахується з тих
  файлів, що лишились, так само, як після розбору. Партія, яка чекала перегляду лише через цей файл, стає «розібрано».
  Партія без жодного прийнятого файлу стає «скасовано»: вона закривається, нічого не записавши. Партія «завантажено»
  лишається відкритою, щоб у неї можна було додати інші файли. Рішення щодо всієї партії видаляються, бо їх приймали
  для іншого набору файлів.
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 2, FR 3): якщо той самий файл (SHA-256) уже збережено
  як файл історії, відкривається наявна партія (`existing: true`), як при завантаженні. Файл однаково виходить із партії
  виписок.
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 2): ознака файлу історії й поле `asStatement` працюють
  за прапорцем `data.import`, як і решта розбору. Це додаткові поля, і маршрут не має способу перевірити інший прапорець
  усередині. Перенесення файлу працює за прапорцем і ключем функції `categorization.history-rules`. Коли прапорець
  вимкнено, маршрут відповідає 404.
