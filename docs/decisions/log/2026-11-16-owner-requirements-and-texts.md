## Тлумачення ведучого

Тлумачення ведучого (2026-11-16; власник його не затверджував):

1. **Вимоги лише для свого релізу.**
   - Рішення ведучого (2026-11-16; власник не схвалював; PR процесу «легший процес»): детально (FR, AC, EC, стани,
     тексти) описують лише поточний реліз; майбутні релізи — 1–2 речення (що і навіщо), без FR/AC/станів/текстів;
     деталізують, коли реліз стає поточним, одним пакетним PR перед `plan-wave`; наявні деталі майбутніх релізів не
     видаляють і не переписують, лише не підтримують (за суперечності позначають «переглянути при деталізації»);
     агенти читають лише view свого релізу, інші релізи — лише за прямим посиланням; причина: слова власника «мають
     читати лише ту версію, до якої відносяться». Правило: `docs/requirements/README.md`, «Detail only the current
     release».
2. **Тексти інтерфейсу: канва — єдине джерело.**
   - Рішення ведучого (2026-11-16; власник не схвалював; PR процесу «легший процес»): (1) будь-який текст інтерфейсу
     спершу з'являється на канві; нема тексту на канві — нема тексту в коді; (2) біля кожної дошки екрана — блок
     «Тексти»: ID і назва екрана, таблиця «Де» / «Обраний текст» / «Інші варіанти», тексти станів, яких нема на макеті
     (помилки сервера й валідації, сповіщення, підтвердження, порожні стани), обраний варіант позначено, інші — лише
     для обговорення; (3) `uk.ts` дослівно дорівнює обраному тексту, `en.ts` перекладає `uk.ts`, англійських варіантів
     на канві нема; (4) у вимогах немає текстів інтерфейсу — поведінка і посилання на екран чи елемент («кнопка
     підтвердження на S-050 (текст — канва)»); для юридичних і продуктових текстів вимога каже, що такий текст має
     бути і що він передає, а формулювання — на канві; (5) без масового перенесення: коли PR уперше торкається екрана,
     текст переходить у блок на канві й зникає з вимоги; за розбіжності перемагає канва, розбіжність — у тілі PR;
     (6) зміна тексту: правка блоку «Тексти» в живій канві (спершу Artifact `read`), потім один PR оновлює знімок
     `design/canvas/` і `uk.ts`/`en.ts`; рівень рецензії — за `merge-rules.md`, «Review tiers» (рядок нижче); причина:
     слова власника «треба узгодженний сорс оф трус» і «текст завжди варто додавати на канву … окремим блоком можливих
     варіантів біля потрібного екрану». Правило і формат блоку: `docs/design/ARTIFACTS.md`, «Тексти інтерфейсу».
   - Рішення ведучого (2026-11-16; власник не схвалював; PR процесу «легший процес»): формат блоку — окрема дошка
     `<Дошка екрана>Texts.dc.html` праворуч від дошки екрана на тій самій сторінці канви, назва в `canvas.json`
     «<S-id> <назва> · Тексти»; правило формату записано в `docs/design/ARTIFACTS.md`, бо `design/canvas/` — дзеркало
     файлів `project/` живої канви і README там опублікувався б на канву; причина: блок має бути поруч із екраном і
     читатися як файл знімка.
   - Рішення ведучого (2026-11-16; власник не схвалював; PR процесу «легший процес»): `screen-from-canvas` бере рядки
     лише з блоку «Тексти»; якщо тексту нема — автор додає його на канву в тому самому PR з позначкою «варіант від
     агента, потребує погодження» і пише про це в тілі PR; `review-pr` для PR інтерфейсу перевіряє, що кожен новий чи
     змінений рядок `uk.ts` дорівнює обраному тексту з канви і що у вимогах не з'явилося нових текстів інтерфейсу;
     `change-requirement` веде правки текстів через канву.
   - Рішення ведучого (2026-11-16; власник не схвалював; #369): зміна текстів, що зачіпає `uk.ts`/`en.ts`, — рівень
     «Функціональність» (`review-pr` перевіряє, що рядки дорівнюють блоку «Тексти» на канві); рівень «Документи» —
     лише зміна знімка канви (`design/canvas/`, без коду); причина: `uk.ts`/`en.ts` — код, вони не проходять
     `isDocsOnly`, і рядки не мають обходити `review-pr` (рецензія #369). Правило: `.claude/references/merge-rules.md`,
     «Review tiers».
