# Рішення 2026-11-28: сторінка «Пропозиції правил» і прийняття (BUD-21 i, рядок 241)

**Створено:** 2026-11-28 · **Оновлено:** 2026-11-28

Вебчастина рядка 241 плану `docs/plans/poc-wave-2.md`: BUD-21 FR 21–23, AC20, AC21, AC24–AC26 і BUD-14 FR 16. Сервер не змінено.
Нижче — дрібні деталі, які вирішив виконавець; власник їх не схвалював. Рішення власника про «Переказ» при «Застосувати до
наявних» (2026-11-28, `2026-11-28-bud21e-acceptance.md`) виконано: діалог і сповіщення показують кількість пропущених.

## Рішення ведучого

- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 21): група «Переказ» за замовчуванням не вибрана, як на дошці
  `PocMoneySuggestions`, хоча сервер віддає такі пропозиції з `selected: true` (вони «впевнені»). Чому: правило «Переказ» — окремий
  вибір користувача, а дошка його не вибирає; вимога каже про вибір лише впевнених і суперечливих.
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 21): сторінка показує виведення найновішого файлу історії;
  перемикача між кількома файлами немає (кількість на S-197 — сума неприйнятих пропозицій усіх файлів, як віддає сервер). Чому:
  вимога описує одну сторінку; перемикач — окреме питання дизайну.
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 21): «посилання на рядки файлу» — номери рядків (`evidence.rows`,
  «та інші», коли їх більше), бо сервер не віддає вмісту рядків; винятки — дата, сума, категорія й номер рядка. Чому: вміст рядків
  файлу з API не виходить (рядки живуть лише як докази на сервері).
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 18, AC20): «перші N рядків» — це `derivation.count` мінус
  `check.rows` (останні 20 %, на яких перевірено), покриття — `covered / rows`, збіг — `agreeing / covered` (цілі відсотки,
  округлення до цілого). Число 50 у тексті «Історії замало…» — `check.minimum` із відповіді (змінна {minimum}).
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 22): які теги будуть створені, діалог прийняття визначає
  порівнянням тегів вибраних пропозицій (з урахуванням олівця) зі списком тегів простору (`GET /v1/transaction-tags`); якщо
  список не прочитано, тег показується як новий.
- Рішення ведучого (2026-11-28; власник не схвалював; BUD-21 FR 21, EC «категорію видалено»): пропозиція з видаленою
  категорією не вибирається, доки олівець не дасть їй іншу; для об'єднаної сервер віддає цільову категорію, її й показано.
  Назви видаленої категорії API не дає, тому текст помилки прийняття без назви.
- Рішення ведучого (2026-11-28; власник не схвалював): дати форматує спільна `formatDate` («1 черв. 2025 р.»), не «01.06.2025»
  з дошки; тож у тексті «Скасувати можна до {date}» прибрано кінцеву крапку. Умови читає той самий `conditionText`, що й таблиця
  правил («Сума > 40,00 €», а не «Сума більша за 40,00 €»). Чому: одна форма запису в усьому інтерфейсі (DS-04).
- Рішення ведучого (2026-11-28; власник не схвалював): після виведення на S-299 до посилання «До правил категорій» додано
  посилання «Пропозиції правил» (вхід на S-301, `screen-map.md`). Ліміт правил (422) показує наявний текст `rules.error.limit`.
