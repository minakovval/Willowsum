# Рішення власника 2026-11-28: сторінка ходу показує ціну пункту вимоги в токенах

**Створено:** 2026-11-28 · **Оновлено:** 2026-11-28

- Запит власника (2026-11-28, чат), дослівно: «хочу дашборд ефективності використання ьокенів, треба якась одиниця виміру, на яку витрачаються оокени і яку можна порахувати ретроспективно по проекту».
- Мета, дослівно: «… продовж розробки змінювалися процеси і робились якісь дії для оптимізації витрат. для цього і потрібен дашборд, щоб аналізувати цих дій з оптимізації».
- Одиниця — **пункт вимоги**: нумерований FR, AC чи EC з `docs/requirements`, який тест назвав уперше. Пілот зі сторі-поінтами (30 зрізів PoC, 6 оцінювачів) кращого зв'язку з токенами не дав: на рівні зрізу пункти 0,84, сторі-поінти 0,50 (Спірмен). Тому лишаємо пункт без ваг.
- «так, додай прогноз» — прогноз до кінця PoC.
- «об'єднай цей дашборд з вже існуючим дашбордом по темпу» — розділ додано на сторінку ходу https://minakovval.github.io/Willowsum/. Окремий дашборд-артефакт був робочим прототипом.
- Рішення власника (2026-11-28, чат, після незалежного огляду методу — `docs/validation/token-review-2026-11-28.md`), дослівно: «так, виправляй розрахунки для дошборда і всі поради з з економії з середнім та малим ризиком передавай оркестратору на імплементацію». Раніше: «мої правила і рішення можна переглядати».
- Обмеження з рішення 2026-11-27 (`2026-11-27-owner-dashboard-features.md`) не змінено: «я не хочу щоб на його оновлення витрачались токени».

## Що змінено

- `tools/req-check`: `--coverage-json` додає поле `distinct` (`covered` — пункти, названі тестами в будь-якому релізі, кожен один раз; `mentions`). Решту полів не змінено.
- `tools/progress-dashboard/history.mjs`: CI після кожного злиття в main додає одну точку в `history.json`:
  - коміт, час, PR;
  - пункти, названі тестами (distinct);
  - пункти PoC: покрито і всього.

  Початок історії — `history-seed.json`: 370 комітів main від #166 до #770. Ці числа порахував `req-check --coverage` на кожному коміті. У тому ж файлі `umbrella` — PR, злиті в гілку іншого PR, а не в main. Їхні токени додаються до того PR.
- `tools/progress-dashboard/events.json` — 24 дії з оптимізації. Для кожної: дата злиття, PR, категорія, що очікували і файл рішення.
- Сторінка, новий розділ «Ціна пункту вимоги» між «Темпом» і фактами. У ньому:
  - підсумки: нові пункти; млн cache read агентів на пункт за весь час і за 7 днів; ≈ USD на пункт; частка токенів на PR без нових пунктів;
  - прогноз до кінця PoC: залишок пунктів, токени, долари, дні — завжди діапазон;
  - ковзна ціна пункту (20 PR типу «код» і UI) з позначками дій;
  - таблиця «До і після дій» (20 PR типу; 30 PR усіх типів).

  Розрахунок — блок `<script id="eff-lib">`, його тестує `tools/progress-dashboard/test/efficiency.test.mjs`.
- Workflow `progress-dashboard.yml`:
  - `build` (лише читання) читає опубліковану гілку `gh-pages` як дані і запускає `history.mjs`;
  - `publish` копіює третій файл `history.json`;
  - права й розподіл на два job не змінено.

  Тести безпеки workflow оновлено.

## Виправлення методу за оглядом (частина A)

- Токени зважено за ціною моделі: «умовні млн» = cache read у ціні Opus, Sonnet × 0,5, Fable × 2; частина рядка без розподілу за моделями — як Opus.
- Дії, злиті протягом доби, — один пакет; вікна — 20 PR типу до першої дії і після останньої; біля зміни — 90 % інтервал повторної вибірки (1 000 разів, сталий генератор); інтервал із нулем — «у межах шуму».
- Плацебо: розкид зміни «до і після» в кожній точці історії без дії (10–90 %) — під таблицею.
- Ведучий: власний cache read ведучого з приміток «Сесій» на злитий PR — окрема плитка і доданок прогнозу токенів.
- «Сесії»: діапазон «#181–#186» — усі PR у ньому; PR у двох сесіях рахується в першій; USD сесії, чий `usage` не включає агентів, не береться.
- PR корекцій вимог власника (#705, #722, поле `corrections` у `history-seed.json`) — окремий тип, поза ціною «код».
- Частку «на PR без пунктів» розкладено: з неї PR «код» і UI.
- Не зроблено на сторінці (немає даних у #180): записи в кеш та input, причини другого кола, час відкриття PR. Збирання цих даних передано ведучому разом із пропозиціями частини B.

## Оновлення без токенів Claude

Звідки сторінка бере дані:

- `history.json` пише CI, без кроку агента.
- Облік токенів сторінка читає з тіла #180 і його архіву (#499) через GitHub API, як і решту даних. Це 2–3 запити: при відкритті й за кнопкою «Оновити», не за 10-хвилинним таймером.
- Список дій бере з `events.json` у main.

Нова дія з оптимізації — рядок у `events.json` у тому самому PR.

## Ризики, мінуси

- Пункт — не обсяг роботи. Медіана FR — 27 слів, p90 — 80. Ціну окремого PR видно погано. Порівнювати варто суми за 20 і більше PR.
- 30 % токенів іде на PR без нових пунктів: вимоги, процес, виправлення. Їх видно окремою часткою.
- Два злиття за ~1 хв:
  - кожен `build` читає ту саму опубліковану історію, тож точка першого може загубитися;
  - пункти тоді перейдуть до наступного PR;
  - сума не зміниться.
- PR, злитий не в main і не внесений в `umbrella`, у ціну за PR не входить. Сторінка показує, скільки таких рядків.
- Долари — лише 19 сесій ведучого, де записано ≈ USD.
- Ефект дії — підказка, не доказ: поруч відбуваються інші зміни. Приклад: після #650/#652 зросла ціна пункту для «код», бо тоді були великі PR корекції вимог.
