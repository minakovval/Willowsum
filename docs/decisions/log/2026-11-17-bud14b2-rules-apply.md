# Рішення 2026-11-17: BUD-14@PoC b2) — «Застосувати до N наявних», «Відмінити», «Видалити», дія «теги»

**Створено:** 2026-11-17

Дрібні рішення виконавця PR «BUD-14: rules — apply to existing, undo, delete, tags (server part b2)» (хвиля 2, рядок
23). Кожне — «Рішення ведучого (2026-11-17; власник не схвалював; BUD-14): …».

- Рішення ведучого (2026-11-17; власник не схвалював; BUD-14): «Застосувати до N наявних транзакцій» — окремий запит
  `POST /v1/category-rules/{ruleId}/apply` після «Зберегти правило» (клієнт надсилає його, якщо прапорець відмічено);
  запуск бере правило таким, яким воно є на початку (категорія й теги), і ті самі N, що «Показати» (найновіші 20 000
  показаних транзакцій простору). Запуск одночасно — один на простір (409 `RULE_RUN_RUNNING`).
- Рішення ведучого (2026-11-17; власник не схвалював; BUD-14): «одразу» — запит обробляє перші 500 записів частинами по
  100 до відповіді; решту — фонова задача `categorization.rule-run-part` по 100 з прогресом `processed` з `count`
  («Оброблено X з N», `GET /v1/category-rule-runs/{runId}`). «Відмінити» понад 500 записів так само.
- Рішення ведучого (2026-11-17; власник не схвалював; BUD-14): явне застосування замінює будь-яку автоматичну категорію
  (іншого правила, «як раніше», банку, словника, «Без категорії»), але не ручну — вона лишається і рахується в
  «Пропущено: ручні зміни» (п. 9); теги правила при цьому додаються. `changed` — записи, у яких змінено категорію чи
  теги.
- Рішення ведучого (2026-11-17; власник не схвалював; BUD-14): «Відмінити» доступне 7 днів від кінця запуску, один раз
  (`RULE_RUN_UNDO_EXPIRED` «Час для відміни минув», `RULE_RUN_UNDONE` «Запуск уже відмінено»); категорія повертається,
  лише якщо версія рядка та, що лишив запуск, теги — лише якщо вони ті самі (за назвою й порядком); інакше запис «не
  відновлено» (`undo.notRestored`, граничний випадок 5). Запуск правила, що відтоді видалене, теж можна відмінити.
- Рішення ведучого (2026-11-17; власник не схвалював; BUD-14): «Видалити» — `DELETE /v1/category-rules/{ruleId}` → 200
  `{ deleted: true }` (як інші видалення API); транзакції лишаються з категорією й джерелом «за правилом», без
  посилання на правило (`rule` і `appliedRules` зникають), версія рядка не змінюється. Запуск, що виконується, після
  видалення правила зупиняється: решта записів — «unavailable».
- Рішення ведучого (2026-11-17; власник не схвалював; BUD-14): теги правила зберігаються за назвою (як «Додати теги»
  масових дій); тег, якого в просторі вже немає, створюється при застосуванні. Теги додаються після власних тегів
  транзакції, той самий (без урахування регістру) — раз; понад 20 — теги не змінюються. Тегів немає, коли вимкнено
  `transactions.attributes`.
- Рішення ведучого (2026-11-17; власник не схвалював; BUD-14): «Застосовано правила: №…» — `appliedRules` відповіді
  `GET /v1/transactions/{id}/category`: правило категорії й правило тегів у поточному порядку; для кожного атрибута
  діє перше правило, що його задає (п. 8, AC3).
- Рішення ведучого (2026-11-17; власник не схвалював; BUD-14): записи аудиту — категорія кожної транзакції запуску
  (`categorization.transaction-category`, автор — користувач), теги — запис транзакції модуля transactions (автор —
  користувач; на новій транзакції — система), запуск — `categorization.rule-run` (`create` наприкінці, `update` при
  «Відмінити»; лише ідентифікатори й лічильники), видалення правила — `categorization.rule` `delete` (умови й теги
  замасковано).
