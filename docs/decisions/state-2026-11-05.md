регіон — домен `platform_types.data_region` (лише `eu`), таблиця `household.households` (ACC-08) мусить мати `data_region` і `encryption_key_ref`; міграції звуження (DROP, RENAME, зміна типу, SET NOT NULL, NOT NULL без DEFAULT, нове обмеження, TRUNCATE, DROP TRIGGER) — лише з позначкою `-- ws:contract <NNNN_expand.sql> <причина>` після випущеної міграції-розширення, а в CI тести модулів базової версії йдуть на схемі PR; журнал аудиту — модуль `audit`, роль має лише INSERT і SELECT, тригери відхиляють UPDATE, DELETE і TRUNCATE, чутливі поля маскуються до запису; синтетичні дані — `tools/synthetic` з генераторами модулів у `synthetic.ts`; великі об'єкти `lo_*` закрито для PUBLIC одноразовим `db:bootstrap` від суперкористувача; далі міграції запускає власник бази з CREATEROLE без суперкористувача і без BYPASSRLS; SQL міграцій модуля виконується від ролі-власника модуля `ws_own_<схема>` (NOLOGIN, без BYPASSRLS, CREATE лише на своїй схемі, володіє об'єктами схеми) усередині SECURITY DEFINER-обгортки, з якої SET ROLE і RESET ROLE неможливі, тож правила, тригери й функції модуля діють із її правами, а поза своєю схемою міграція нічого не створить; оскільки власник таблиці може вимкнути FORCE чи змінити політику, `db:bootstrap` ставить страж — тригер подій суперкористувача `ws_module_guard`, що після кожної DDL ролі-власника одразу ізолює нові таблиці клієнтів і відхиляє інструкцію, якщо безпека рядків не ввімкнена й не примушена, політика не єдина стандартна (обмежувальні теж заборонено), є матеріалізоване представлення, правило перезапису чи представлення без `security_invoker`; без справного стража міграції зупиняються; страж також відхиляє в схемах модулів будь-які функції, крім тригерних без SECURITY DEFINER, оператори й приведення типів, традиційне успадкування (лише декларативні розділи таблиць клієнтів), у CHECK, індексах і збережених згенерованих колонках — будь-що, крім незмінних функцій `pg_catalog`, а другий тригер подій (`table_rewrite`) — зміну типу колонки (лише через нову колонку); `check_module` працює лише з тригера подій; нетранзакційні канали однієї відхиленої інструкції (`setval`, налаштування сеансу, текст помилки в журналі міграцій) прийнято як низький ризик; після міграцій кожен запуск перевіряє всі правила `check:schema`, а не лише межу; перенесення даних між просторами — окремим механізмом із рецензією пізніше; кожен запуск міграцій і `check:schema` перевіряють межу поза схемами модулів: ролі модулів нічим не володіють, їхні права — лише на свою схему і дозволений список (`platform_context.current_household()`, USAGE на `platform_context` і `platform_types`), SECURITY DEFINER-функцій немає ніде, крім двох функцій платформи, які мусять збігатися з визначенням платформи, у `platform_context` і `platform_types` немає інших об'єктів, правил перезапису (крім `_RETURN` представлень), тригерів подій і розширень (крім plpgsql) немає, кожен об'єкт схеми модуля належить його ролі-власнику, враховано права на колонки й послідовності та глобальні типові права, у схемі public немає таблиць, `household_id` поза схемами модулів заборонено; унікальні ключі й зовнішні ключі таблиць клієнтів містять `household_id` (виняток — унікальний ключ з однієї колонки uuid); аудит: `id` і `occurred_at` ставить лише база; простір у `inHousehold` поки передає код модуля, прив'язка до сеансу користувача — з ARC-07 (access-scope); канал через `application_name` у `pg_stat_activity` прийнято як низький ризик (потрібні два змовлені модулі).
