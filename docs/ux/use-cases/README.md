# Сценарії використання Willowsum

## Призначення

Сценарії використання (use cases) описують, як конкретна людина досягає мети в продукті: хто діє, з якого екрана починає, що робить система на кожному кроці і чим усе закінчується. Це робочий артефакт UX для прототипування, тестових сценаріїв і перевірки повноти вимог.

Сценарії не є вимогами. Джерело істини — файли в `docs/requirements/`. Якщо сценарій розходиться з вимогою, діє вимога, а розбіжність записують у розділ «Відкриті питання» каталогу.

## Склад

- `UC-<МОДУЛЬ>.md` — каталог сценаріїв одного функціонального модуля.
- [coverage.md](coverage.md) — матриця покриття: кожна вимога з `docs/requirements/` і сценарії, що її покривають.
- [open-questions.md](open-questions.md) — зведені відкриті питання всіх каталогів, згруповані за темами.

## Формат каталогу

Каталог починається із заголовка `# Сценарії використання · <МОДУЛЬ> · <назва>` і рядка джерела. Далі розділи:

1. **«Перелік»** — таблиця: ID, сценарій, актор, реліз, вимоги.
2. **«UC-<МОДУЛЬ>-NN · <назва>»** — по одному розділу на сценарій.
3. **«Покриття»** — таблиця вимог модуля з пунктами ФВ, сценаріями і непокритим.
4. **«Відкриті питання»** — нумерований список розбіжностей і прогалин; кожне питання посилається на файл і пункт вимоги.

## Формат сценарію

Кожен сценарій має однаковий набір полів у такому порядку:

| Поле | Що містить |
| --- | --- |
| **Актор** | Роль у просторі (Owner, Admin, Editor, Viewer, обмежений учасник), роль персоналу або «система» |
| **Реліз** | MVP, v1, v1-mobile або v2 — за файлом вимоги |
| **Мета** | Що хоче отримати актор, одним реченням |
| **Передумови** | Що має бути правдою до початку (план, 2FA, наявні дані) |
| **Тригер і точка входу** | Звідки актор починає, з кодами екранів S-NNN з карти екранів |
| **Основний сценарій** | Нумеровані кроки «актор робить — система відповідає» з конкретними даними прикладу |
| **Альтернативні сценарії й винятки** | Відгалуження з номером кроку, від якого відходять (2а, 3б) |
| **Результат** | Стан системи після успішного завершення |
| **Вимоги** | ID вимог і пункти, які сценарій покриває (`AST-04 п. 1–3; крит. 2`) |
| **Потоки й шляхи** | FLW і JRN, кроки яких реалізує сценарій, або «—» |
| **Екрани** | Коди екранів S-NNN з `docs/ux/screen-map.md` |

Поля «Вимоги», «Потоки й шляхи» і «Екрани» читає скрипт матриці покриття, тож ID у них пишуть точно так, як у назві файлу вимоги.

## Як підтримувати актуальність

- **Нова вимога** в функціональному модулі: додайте сценарій (або розширте наявний) у каталог модуля, вкажіть ID у полі «Вимоги», оновіть «Перелік» і «Покриття» каталогу.
- **Змінена вимога**: знайдіть сценарії, що цитують її ID (`grep -l 'ID' docs/ux/use-cases/UC-*.md`), і виправте кроки, актора, реліз чи екрани. Якщо зміна закриває відкрите питання — приберіть його з каталогу і з open-questions.md.
- **Нова або змінена FLW чи JRN**: додайте ID у поле «Потоки й шляхи» відповідних сценаріїв.
- **Новий екран** у карті екранів: додайте код S-NNN у поле «Екрани» сценаріїв, що його використовують.
- **Розбіжність** між вимогами, знайдена під час роботи над сценарієм: запишіть її у «Відкриті питання» каталогу з посиланням на файл і пункт, потім — в open-questions.md.
- Після будь-якої зміни перегенеруйте [coverage.md](coverage.md) і перевірте: кожна функціональна вимога, FLW і JRN має щонайменше один сценарій, а всі ID у полях «Вимоги» і «Потоки й шляхи» існують у `docs/requirements/`.
