# ADR-0004: прапорці функцій, поступовий випуск і аварійні вимикачі модулів

**Створено:** 2026-11-06 · **Оновлено:** 2026-11-06 (рецензії PR #82: перевірки до читання тіла, і для невідомого шляху; межа застарілого стану; тайм-аут запитів прапорців; обидва прапорці маршруту і `requires`; ключ у записах аудиту; окрема роль запису)

**Статус:** Прийнято (рішення ведучого, PR CICD-06). **Вимоги:** CICD-06@PoC, ARC-01@PoC (п. 7), DAT-05@PoC
(п. 6, 7, 9 — серверна частина). Доповнює [ADR-0003](0003-api-contract.md): додає до порядку перевірок
запиту аварійний вимикач модуля і прапорець функції; решти рішень ADR-0001…0003 не змінює.

## Контекст

CICD-06 вимагає, щоб кожна нова функція виходила вимкненою прапорцем і вмикалася поступово (тестові
простори → частка просторів → усі), щоб кожен прапорець мав власника і дату перегляду, а тимчасовий
видалявся з коду не пізніше ніж через 30 днів після повного вмикання, і щоб кожен модуль мав аварійний
вимикач, що вимикає його в production за ≤ 1 хв без релізу. ARC-01 п. 7: кожна нова функція має ключ у
каталозі функцій і прапорець. DAT-05: вимкнена функція прихована (без «Coming soon»), запис іншого простору
поводиться як неіснуючий, звіт про помилку без персональних і фінансових даних. Інтерфейсу власника для
прапорців ще немає (ADM).

## Рішення

| Що | Вибір | Чому |
| --- | --- | --- |
| Де живуть прапорці | Модуль `feature-flags` (каталог ARC-01). Каталог прапорців — у коді (`domain/catalogue.ts`): ключ = ключ функції з `plan-catalog`, вид (`release` — тимчасовий, `operational` — постійний вимикач), власник (роль або команда, не ім'я людини), дата перегляду, для `release` після повного вмикання — `fullyEnabledOn`. Модуль під час завантаження і `check:flags` перевіряють, що ключі прапорців і ключі функцій збігаються | Одне джерело для коду і CI; функції без прапорця не буває |
| Стан випуску | Схема `feature_flags`: таблиця `flags` (етап `off` / `test` / `share` + відсоток 1–99 / `all`, коли досягнуто `all`), `kill_switches` (модуль, вимкнено), `test_households` (позначки тестових просторів з історією). Прапорець без рядка — вимкнений. `flags` і `kill_switches` — налаштування платформи без даних клієнтів (винятки в `schema-exemptions.json`); `test_households` — таблиця клієнтів під політикою простору | «Нова функція виходить вимкненою»; позначка простору не лежить поза політикою рядків |
| Частка просторів | Кошик простору 0–99 — FNV-1a (32 біт) від «<ключ>:<простір>»; простір у частці, якщо кошик < відсотка. Тестові простори ввімкнені і на етапі `share` | Детерміновано на всіх серверах; більша частка лише додає простори; різні прапорці беруть різні простори; без залежностей |
| Як маршрут оголошує прапорець | Прапорець функції — `access.feature`. Підфункція додає власний `access.flag`: тоді мають бути ввімкнені обидва (`routeFlags`), тож вимкнена функція ховає й підфункцію. API не стартує, якщо маршрут називає невідомий прапорець. Контракт пише їх у `x-willowsum-access.flags` | ARC-01 п. 7: ключ функції і є ключем прапорця; власний прапорець маршруту не може обійти прапорець його функції (рецензія безпеки #82) |
| Порядок перевірок | У хуку маршруту `onRequest`, до читання тіла: аварійний вимикач модуля маршруту (503 `MODULE_UNAVAILABLE`, `Retry-After: 60`) → сеанс (401) → прапорці для простору сеансу (404 `NOT_FOUND`, той самий статус, заголовки й тіло, що для невідомого шляху). Далі, в обробнику: тіло (415, 413, 400) → роль і scope (403) → план (402) → далі як в ADR-0003. Публічні маршрути платформи (без модуля) не мають ні вимикача, ні прапорця | Вимкнений модуль не виконує нічого свого, навіть автентифікації маршруту; вимкнена функція не існує для простору, тож ні розбір тіла, ні роль, ні план про неї не говорять |
| Затримка ≤ 1 хв | Кожен процес API тримає знімок стану (прапорці + вимикачі). Вік знімка рахується від початку його завантаження, тож повільне завантаження не подовжує 15 с. Перший запит після 15 с (`REFRESH_MS`; більше 60 с заборонено) починає перечитування (одне за раз) і чекає його не довше 2 с (`LOAD_WAIT_MS`); якщо воно не вдалося чи ще триває, діє останній стан, поки йому менше 60 с (`KILL_SWITCH_MAX_DELAY_MS`). Без такого стану (ще не завантажений або останнє вдале завантаження почалося 60 с тому чи раніше) усі модулі «тимчасово недоступні», а «готовий» (`/health/ready`) ролі `api` відповідає `flags-not-loaded` або `flags-stale` (рішення — чиста функція `flagsReadiness` / `checkFlagsReady`). Пул модуля в процесі API має `statement_timeout` і тайм-аут з'єднання 5 с (`FLAGS_DB_TIMEOUTS`), тож завислий запит перечитування закінчується за 5 с, і наступний запит пробує знову | Зміна діє в усіх процесах за ≤ 15 с без релізу і без черги (ARC-04 ще немає); жоден процес не служить станом, старшим за 1 хв, тож вимикач не пропуститься довше за межу CICD-06 (рецензія безпеки #82); один запит до бази на процес раз на 15 с |
| Зміна прапорців | Лише внутрішній інтерфейс `FlagAdmin` (`createFlagAdminFor`): `setRollout`, `setKillSwitch`, `setTestHousehold`, `state`, `overdue`. Автор — персонал (UUID) або система. Кожна зміна пише запис аудиту: прапорці й вимикачі — у новий журнал платформи `audit.platform_entries` (лише дописування, як `entries`, без `household_id`; запис містить ключ прапорця чи назву модуля, а не лише id рядка), позначка тестового простору — у журнал цього простору. Зміна без різниці нічого не пише | П-10; екран власника (ADM) викличе той самий інтерфейс |
| Правило 30 днів і дата перегляду | `pnpm check:flags` (CI-задача `api`): падає, якщо дата перегляду минула, `release`-прапорець повністю ввімкнений понад 30 днів (`fullyEnabledOn`) або функція не має прапорця. Правило 30 днів у CI тримається лише на `fullyEnabledOn`: його записує людина в PR, що фіксує повне вмикання; без нього CI про повне вмикання не знає. Тому `scripts/flags.ts rollout <release-прапорець> all` друкує нагадування з датою, яку треба записати, а те саме правило на збереженому стані дає `FlagAdmin.overdue(now)` (`flags.ts state`; нагадування планувальника — коли буде ARC-04) | Збережений стан production у CI недоступний; код — так |
| «Немає доступу» до записів | `requireFound(record)` (`platform/http/problem.ts`): запис, якого немає або який належить іншому простору (політика рядків його ховає), — 404 `NOT_FOUND` з тим самим тілом, що для невідомого шляху | DAT-05 п. 6, AGENTS.md «Data access» |
| Звіт про помилку | `ApiOptions.reportError(ErrorReport)`: метод, шаблон маршруту (не конкретна адреса), код і статус проблеми, назва класу помилки. Без повідомлення, стека, тіла, запиту і заголовків. 503 вимкненого модуля і помилки 4xx не звітуються. Збій звітування не змінює відповіді | DAT-05 п. 9, AGENTS.md «Privacy»; експортер дасть ARC-09 |
| Список увімкнених функцій | `GET /v1/me/features` (модуль `feature-flags`): лише ключі, увімкнені для простору сеансу; вимкнених клієнт не бачить узагалі. Прапорець підфункції в каталозі має `requires` (прапорець її функції) і вважається ввімкненим лише разом із ним — те саме правило, що `routeFlags` для маршруту; `check:flags` відхиляє невідомий `requires` і цикли | Клієнт ховає вимкнене, а не показує «Скоро» (DAT-05 п. 7); підфункція не з'являється, поки її функція прихована |
| Невідомий шлях | Хук рівня застосунку `onRequest` (`installProblemHandlers`): запит без маршруту (`request.is404`) одразу отримує 404 `NOT_FOUND`, до читання тіла | Інакше невідомий шлях із неправильним, порожнім чи завеликим тілом відповідав би 400 / 413, а прихована функція — 404, і їх можна було б розрізнити (рецензія безпеки #82, другий раунд). На наявні маршрути, зокрема `/health/*`, хук не діє |

## Наслідки

- `household.core` — постійний (`operational`) прапорець, власник `product-owner`, перегляд до 2027-02-04. Як і будь-який
  прапорець, у новій базі він вимкнений: після розгортання власник вмикає його через `FlagAdmin` (етап `all`), інакше
  маршрути простору відповідають 404.
- Зміна стану і запис аудиту — окремі транзакції (як усюди до ARC-04): якщо запис аудиту не вдався після зміни, зміна
  лишається, а виклик повертає помилку.
- Що лишається до прапорця: помилки, які Fastify дає до хуків `onRequest`, — неправильна адреса (400 `FST_ERR_BAD_URL`)
  і недозволений метод — не залежать від прапорця й нічого про функцію не кажуть. Невідомий шлях відповідає 404 до
  читання тіла (хук рівня застосунку), тож із будь-яким тілом він збігається з прихованою функцією. 415, 413 і 400 тіла йдуть лише після вимикача, сеансу й прапорців, тобто лише для
  функції, яку простір і так бачить; там вони передують ролі (403) і плану (402), і це прийнятно: розбір тіла не
  відкриває записів, а сама функція для простору не прихована.
- Лише код робить `FlagAdmin` єдиним, хто пише таблиці прапорців: роль модуля `ws_mod_feature_flags` може писати їх і з
  будь-якого іншого коду модуля. Коли з'явиться екран власника (ADM), запис стану переходить до окремої ролі входу
  (наприклад, `ws_flags_admin` з INSERT/UPDATE лише на `flags`, `kill_switches`, `test_households`), якою користуються
  лише `FlagAdmin` і `scripts/flags.ts`, а роль модуля в процесі API лишається лише з SELECT. Це окремий PR із рецензією
  безпеки разом з ADM.
- Доопрацювання після #82: власний `access.flag` маршруту мусить мати в каталозі `requires` = ключ функції маршруту
  (`assertRoutes`, інакше API не стартує), тож маршрут і `GET /v1/me/features` завжди однаково кажуть, чи функція
  ввімкнена; обхід `requires` у `check:flags` обмежено глибиною 8, як у `flagOn`; пули `feature-flags` і `ws_context`
  мають `statement_timeout` і тайм-аут з'єднання 5 с та клієнтський `query_timeout` 6 с; запит «чи тестовий простір»
  чекає не довше 2 с (`LOAD_WAIT_MS`); якщо не встигла або впала з помилкою, простір для цього запиту не тестовий
  (функція прихована: 404, а не 500) і відповідь не кешується; налаштування пулів і перевірка готовності — у `src/wiring.ts`, який використовує `main.ts`.
- Аварійний вимикач діє на маршрути модуля. Події й задачі воркера (ARC-04) мають перевіряти той самий
  `isModuleAvailable`, коли з'являться.
- Перевірка `check:flags` іде лише на PR (тригер `pull_request`); щоденна перевірка `main` — з CICD-01.
- Інтерфейс власника для прапорців (ADM) і клієнтський стан «Тимчасово недоступно» (DAT-05, UI) — окремими PR.
