# ADR-0012: ключі просторів — конвертне шифрування через адаптер KMS

**Створено:** 2026-11-13 · **Оновлено:** 2026-11-13

**Статус:** Прийнято (рішення ведучого, PR ARC-06@PoC, хвиля 1). **Вимоги:** ARC-06@PoC (п. 1 — ключ простору і адаптер
KMS; п. 2 — механізм окремого шифрування полів; п. 3 — переобгортання ключів просторів у фоні; п. 5 — знищення ключа),
NFR-12@PoC (п. 3 — «знищує ключ простору»: лише сам механізм знищення). Доповнює [ADR-0002](0002-data-isolation.md)
(`encryption_key_ref`), [ADR-0005](0005-provider-adapters.md) (адаптери) і [ADR-0010](0010-first-space-and-daily-cleanup.md)
(перший простір); їхніх рішень не змінює. Видалення даних із таблиць лише на дописування — окремо, [ADR-0013](0013-erasure-in-append-only-tables.md).

## Контекст

До цього PR `household.households.encryption_key_ref` = `pending:<id>`: ключів просторів не було (модель загроз, прогалина 5).
Головний ключ уже описано кодом без apply (`infra/start/kms.tf`, OCI Vault, HSM). Полів з особливо чутливими даними (IBAN,
номери полісів) у коді ще немає: модулі `accounts` і `insurance` з'являться пізніше.

## Рішення

| Що | Вибір | Чому |
| --- | --- | --- |
| Порт KMS | `src/platform/adapters/kms/`: порт `key-management` з операціями `wrap` (обгорнути ключ даних), `unwrap` і `currentVersion`. Ключ даних і його обгортка — байти; кожна обгортка прив'язана до простору через `associatedData` (`space`), тож обгортку одного простору не можна підставити іншому | ARC-06 п. 1, ARC-05 п. 1: головний ключ — лише через адаптер; назви провайдера поза адаптером немає. OCI KMS приймає `associatedData` в encrypt і decrypt |
| Тестова реалізація | `localKeyManagement()` (`WS_PROVIDER_MODE=test`, локально і в CI): AES-256-GCM з `node:crypto`; ключ версії `local-N` виводиться HKDF-SHA256 із фіксованої несекретної мітки, тож локальні дані читаються після перезапуску. `rotate()` додає версію, `retire(version)` вимикає стару — для тесту ротації. Це не секрет і не захист: розгорнутий процес (staging, production) її не отримує за жодної ролі й режиму — `keyManagement(mode, …, { deployed })` тоді повертає реалізацію, що відмовляє закрито (рецензія безпеки PR #141: конфігурація вимагає `live` лише для ролей api і scheduler) | ARC-05 п. 2 (тестова реалізація без мережі). Ключ, що зникає з процесом, зробив би локальні простори нечитаними після кожного перезапуску |
| Робоча реалізація | У цьому PR її ще немає: `live` відмовляє закрито — кожен виклик дає `ProviderError` `unavailable`, тож простір без ключа не створюється. Робочий адаптер OCI Vault (крипто-ендпоінт, підпис запитів принципалом інстансу) — окремий PR до деплою, умова деплою | Деплою ще немає (сервер не створено). Неперевірений код підпису запитів або важкий SDK без тестів гірші за явну відмову |
| Ключ простору | Під час створення простору (`ensureFirstSpace`) — 32 випадкові байти (`randomBytes`), обгорнуті поточною версією головного ключа ще до транзакції; у транзакції простору — рядок `household.space_keys` (`household_id`, `key_id`, `master_key_version`, `wrapped_key`) і `encryption_key_ref` = `dek:<key_id>`. Збій KMS — простір не створюється (вхід відповідає 500, як і за будь-якого збою створення простору, ADR-0010). Відкритий ключ ніде не зберігається | ARC-06 п. 1; П-24: модель даних повна з PoC |
| Окреме шифрування полів | `createSpaceKeys(db, audit, kms)` → `SpaceKeys.seal(householdId, field, text)` → `ws1.<base64url(iv ‖ tag ‖ шифротекст)>`, `open(…)` — зворотне. AES-256-GCM, новий 12-байтовий IV на кожне значення, додаткові дані — `household:<id>|field:<назва>`, тож шифротекст іншого простору чи іншого поля не відкривається. Ключ розгортається через KMS на кожен виклик (кешу немає) | ARC-06 п. 2. Модулі з IBAN і номерами полісів зберігають лише результат `seal`. Кеш розгорнутих ключів — коли з'являться споживачі і буде видно навантаження |
| Ротація головного ключа | Щоденна задача планувальника `household.space-keys`: для кожного простору з ключем, обгорнутим не поточною версією, — `unwrap` старою і `wrap` поточною; нову обгортку розгортають і порівнюють із ключем, перш ніж зберегти; оновлення рядка умовою «версія не змінилася»; запис `household.space-key` / `update` (`masterKeyVersion` до і після) у журналі простору. Ключ даних не змінюється, тож дані читаються до, під час і після переобгортання (без простою). Тією ж задачею простір із `pending:` (створений до цього PR) отримує ключ. Збій одного простору не зупиняє інших; якщо збоїв був хоч один — подія `household.space_keys_failed` рівня «помилка» з їхньою кількістю (`ws.household.spaces`), без ідентифікаторів; успішний прогін сліду в логах не лишає (слід — записи аудиту) | ARC-06 п. 3 і критерій «Ротація головного ключа». Стару версію в KMS вимикають лише після повного переобгортання: перед вимкненням перевіряють, що в `household.space_keys` не лишилося жодного рядка з цією версією (задача бачить лише простори з учасником) (процедура — CICD-12, перша ротація в production — після репетиції з хмарним KMS у PoC v2) |
| Знищення ключа | `SpaceKeys.destroy(householdId)`: спершу запис у журналі платформи `household.space-key` / `delete` від імені системи (журнал простору зникне разом із простором; якщо запис не вдався, ключ лишається і повтор спробує знову), потім видаляє рядок `space_keys` і ставить `encryption_key_ref` = `destroyed:<key_id>`. Простір, що ще `pending:`, отримує `destroyed:<id простору>` (і той самий запис). Задача ротації такий простір не чіпає й нового ключа не створює. Після цього `open` відповідає `SPACE_KEY_DESTROYED`. У копіях обгорнутий ключ живе до їхньої ротації (≤ 35 днів), далі зашифровані поля нечитані й там | ARC-06 п. 5, NFR-12 п. 3. Хто і коли викликає знищення, і що відбувається з рештою даних простору, — ADR-0013 |

## Наслідки

- `createHouseholdSpaces(db, audit, kms)` і `createSpaceKeys(db, audit, kms)`: `main.ts` вибирає реалізацію KMS за `WS_PROVIDER_MODE` і `config.deployed`, тести — `localKeyManagement()`.
- `schedulerDailyTasks` отримує `spaceKeys` і додає задачу `household.space-keys`.
- Файли користувачів, зашифровані ключем простору (ARC-06 п. 4), — з модулем `file-storage`; поля IBAN і номерів полісів — з їхніми модулями.
- Робочий адаптер OCI Vault — до деплою; до нього розгорнутий процес не створює просторів.
