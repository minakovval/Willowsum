# ADR-0006: спостережуваність — OpenTelemetry, фільтр персональних даних, код помилки, SLO і алерти в коді

**Створено:** 2026-11-07 · **Оновлено:** 2026-11-07 (рецензії PR #85: помилки Fastify до маршрутизації, 503 під час зупинки, вимикач модуля поза бюджетом помилок, вільний текст поза атрибутами, явна телеметрія в staging і production, мінімум запитів для алертів затримки)

**Статус:** Прийнято (рішення ведучого, PR ARC-09). **Вимоги:** ARC-09@PoC (п. 1–4, критерії), NFR-10@PoC
(п. 1–6, критерії приймання 1–2). Сервіс телеметрії — Grafana Cloud з регіоном ЄС (рішення власника 2026-11-06,
`docs/decisions/state-2026-11-05.md`; Grafana Labs — обробник у NFR-17). Доповнює [ADR-0003](0003-api-contract.md)
(поле `supportId` проблем) і [ADR-0005](0005-provider-adapters.md) (виклики провайдерів); рішень ADR-0001…0005 не змінює.

## Контекст

ARC-09 вимагає: логи, метрики й траси через OpenTelemetry у сервіс із даними в ЄС, заміна сервісу — лише конфігурація
(п. 1); фільтр на рівні експортера маскує email, суми, IBAN, токени й тіла запитів (п. 2); ідентифікатор траси кожного
запиту передається у фонові задачі й показується як код помилки (п. 3); SLO 99,9 %, p95 читання ≤ 300 мс, запису
≤ 500 мс, 5xx ≤ 1 %, алерт на порушення бюджету помилок (п. 4); зовнішній монітор із двох точок ЄС (п. 5). NFR-10 додає:
без сум, назв рахунків, IBAN, адрес, координат і тіл запитів (п. 1); помилки БД — лише код стану, обмеження, таблиця,
стовпець (п. 2); виклики провайдерів — без URL, параметрів і ключів (п. 3); ідентифікатор запиту генерує сервер
випадково, ідентифікатор клієнта не приймається (п. 4); трейсинг 100 % запитів і SLO-дашборди (п. 5); тривоги на збої
синхронізації банків > 5 % за годину, 5xx > 1 %, порушення SLO, черговий ≤ 5 хв (п. 6). NFR-17: телеметрія без IP-адрес.

## Рішення

| Що | Вибір | Чому |
| --- | --- | --- |
| Бібліотеки | OpenTelemetry JS, точні версії: `@opentelemetry/api` 1.10.0, `sdk-trace` 3.0.0, `sdk-metrics` 3.0.0, `sdk-logs` 3.0.0, `resources` 3.0.0, `core` 3.0.0, `context-async-hooks` 3.0.0, `exporter-trace-otlp-http`, `exporter-metrics-otlp-http`, `exporter-logs-otlp-http` 0.300.0 (Apache-2.0). Без `sdk-node` і без автоінструментування | П. 1. `sdk-node` тягне gRPC, protobuf, Zipkin, Prometheus і детектори ресурсів; автоінструментування (fastify, pg, http) патчить модулі й записує URL, SQL і заголовки, які потім довелося б вирізати. Ручне інструментування трьох місць (HTTP, БД, провайдери) дає 100 % запитів і повний контроль над атрибутами. Версії 3.0.0 / 0.300.0 вийшли 2026-10-20 (старші за два тижні) |
| Не SDK провайдера | Пакети OpenTelemetry не внесені в `apps/api/provider-sdks.json`: вони не залежать від постачальника, говорять стандартним OTLP і працюють із будь-яким сервісом. Специфічне для Grafana Cloud — лише адреса OTLP і заголовок `Authorization` у змінних середовища | ARC-05 п. 1 стосується SDK конкретних провайдерів; заміна сервісу — лише конфігурація (ARC-09 п. 1) |
| Де код | `apps/api/src/platform/telemetry/` — код платформи без бізнес-правил: `telemetry.ts` (запуск), `redaction.ts` (фільтр), `exporters.ts` (обгортки експортерів, пам'ять), `http.ts` (траси запитів), `jobs.ts` (траси задач), `signals.ts` (метрики, події логів), `errors.ts` (звіт про помилки API), `testing.ts`. Платформний код бере трасер, лічильники й логер через глобальний `@opentelemetry/api` | Один набір для трьох ролей; модулі не імпортують SDK |
| Режими | `WS_TELEMETRY`: `test` (типово — локально і в CI: усе проходить фільтр і лишається в обмеженій пам'яті процесу, по 1000 останніх записів кожного сигналу; нічого не виходить з машини), `otlp` (розгорнуті середовища: OTLP/HTTP на `WS_OTLP_ENDPOINT` + `/v1/traces`, `/v1/metrics`, `/v1/logs` із заголовком `Authorization` = `WS_OTLP_AUTHORIZATION`), `off` (нічого не зберігається, ідентифікатори трас усе одно генеруються). `WS_TELEMETRY_ENVIRONMENT` — `deployment.environment.name` (типово `local`). Для `otlp` обидві змінні обов'язкові. Якщо `WS_TELEMETRY_ENVIRONMENT` — `staging` або `production`, `WS_TELEMETRY` має бути задано явно і не `test` (інакше процес не стартує й називає змінну); деінде типово `test`; адреса — https (http лише для localhost), без облікових даних, запиту й фрагмента, також без голого `?` чи `#`; помилка конфігурації називає лише змінну | П. 1; CICD-12 (секрет лише в змінній середовища, без значення в помилках); тести без мережі (ARC-05) |
| Ролі | `main.ts` запускає телеметрію першою в кожній ролі (`api`, `worker`, `scheduler`; атрибут ресурсу `ws.role`) і зупиняє останньою (скидає буфери) | П. 1 «у всіх ролях» |
| Ресурс | Лише `service.name` = `willowsum-api`, `service.namespace` = `willowsum`, `deployment.environment.name`, `ws.role`. Детектори ресурсів (host, process, env) не використовуються | Без імені хоста, аргументів процесу, змінних середовища |
| Фільтр: allow-list | Обгортка кожного експортера (OTLP і пам'яті — тест бачить рівно те, що пішло б у сервіс) копіює кожен запис лише з дозволеними атрибутами. Атрибут проходить, якщо (1) ключ у переліку `ATTRIBUTE_RULES`, (2) значення відповідає граматиці ключа (шаблон маршруту, метод, код статусу 100–599, SQLSTATE, ідентифікатор SQL, назва класу, технічна назва) і (3) не спрацював жоден детектор: email, IBAN, номер картки чи рахунку (12–19 цифр, також із пробілами), 6+ цифр поспіль, десяткове число (сума, координата), валюта, JWT, `Bearer`/`Basic`, ключ за назвою (`token=`, `api_key:` …), довгий непрозорий рядок із літер і цифр, `?`, `&`, `#`, `=`. Решта відкидається, `ws.telemetry.redacted` рахує відкинуте. Назва спана — `МЕТОД` або `МЕТОД /шаблон`, або технічна назва (`db.transaction <модуль>`); тіло логу — лише назва події; інакше `redacted`. Повідомлення статусу спана, `exception.message`, `exception.stacktrace`, атрибути області інструментування, опис метрики не експортуються; текст рівня логу — лише назва рівня (`ERROR`, `WARN2` …), версія області й `service.version` — лише версія без збігів детекторів після `x.y.z`, одиниця метрики — лише одиниця (рецензія безпеки PR #85) | П. 2, NFR-10 п. 1. Deny-list мав би розпізнати кожну назву рахунку, адресу й формат суми (кирилиця, пробіли, коми); allow-list розпізнає лише наші технічні значення: назва рахунку чи адреса не відповідає жодній граматиці, а детектори — другий рубіж для цифр і токенів |
| HTTP | `instrumentHttp` (у `buildServer`, до маршрутів): кожен запит, крім `/health/*`, — новий кореневий спан SERVER (`traceRequest`); атрибути — метод, шаблон маршруту (`request.routeOptions.url`, ніколи не URL), статус і для відповіді-проблеми її код `ws.problem.code` (закритий перелік кодів API); для невідомого шляху — лише метод. Помилковий — лише 5xx (конвенція OpenTelemetry для сервера); перерваний клієнтом запит закінчує спан з `error.type=RequestAborted`. Гістограма `http.server.request.duration` (с) з межами 5 мс … 10 с, серед них 0,3 і 0,5. Контекст запиту встановлюється в `onRequest` і зберігається до кінця обробки, зокрема після читання тіла частинами через сокет (тест), тож спани БД і провайдерів — дочірні; повторного входу в контекст у пізніших хуках немає (рецензія PR #85: тест не відрізняв його, тож прибрано як мертвий код) | NFR-10 п. 5 (100 %); межі на порогах SLO дають точні p95 біля порогу; проби — не запити API й лише шум |
| Помилки Fastify до маршрутизації | `frameworkErrors` у `buildServer`: URL, який Fastify не може декодувати (`FST_ERR_BAD_URL`, напр. `/v1/%c0`), і задовгий параметр шляху (`FST_ERR_MAX_PARAM_LENGTH`) — теж спан, зразок тривалості й проблема `NOT_FOUND` із `supportId`, а не тіло Fastify, яке повторює шлях. `NOT_FOUND`, як для невідомого шляху: такий URL не відрізняє наявний маршрут від неіснуючого | NFR-10 п. 4–5, DAT-05 п. 7 (рецензія PR #85) |
| Зупинка | `return503OnClosing: false`: запит, що дійшов під час коректної зупинки (на зайнятому keep-alive з'єднанні), отримує проблему `SERVICE_UNAVAILABLE` (503, `Retry-After: 5`, `Connection: close`) з `supportId` і спаном, а не сирий 503 Fastify. Телеметрія зупиняється останньою й скидає буфери (тест процесу з OTLP-збирачем) | ARC-02 п. 5, NFR-10 п. 4 |
| Ідентифікатор запиту | Ідентифікатор траси (128 біт) і спана (64 біти) — з `crypto.randomBytes`, не `Math.random` (типовий генератор SDK); семплер `AlwaysOn`. Вхідні `traceparent`, `tracestate`, `x-request-id` та інші ідентифікатори клієнта не читаються ніколи: публічний API завжди починає нову трасу. Ідентифікатор траси — `supportId` кожної проблеми RFC 9457 (`src/api.ts` типово бере `requestTraceId`); контракт описує поле як код помилки | NFR-10 п. 4: клієнт не може вибрати чи підробити ідентифікатор і приєднатися до чужої траси; ARC-09 п. 3 |
| Фонові задачі | `jobTraceCarrier()` дає `{ traceparent }` поточної траси — він зберігається з задачею в нашій черзі (ARC-04); `runJob(назва, carrier, робота)` виконує задачу як спан CONSUMER у тій самій трасі; `runScheduled(назва, робота)` — окрема траса планувальника. Некоректний носій → нова траса. Помилка задачі — подія `job.failed` з класом, без повідомлення | ARC-09 п. 3. Черги ще немає (ARC-04): помічник готовий для воркера, тест показує ту саму трасу від запиту до задачі |
| Помилки API | `reportError(report, request)` (`ErrorReport` DAT-05 AC7 + поля БД і провайдера) → подія логу `api.server_error` (ERROR) у трасі запиту і ті самі атрибути на спані: метод, шаблон маршруту, статус, код проблеми, клас помилки | NFR-10 п. 1–2; повторно використовує звіт без значень із CICD-06 |
| Помилки БД | `databaseErrorFields(error)` (`platform/db/errors.ts`) бере з помилки node-postgres лише SQLSTATE (`code`) і назви `constraint`, `table`, `column`, `schema` (лише якщо це ідентифікатор SQL); ніколи `message`, `detail` (у ньому значення: «Key (name)=(…) already exists»), `where`, `hint`, SQL чи параметри. Кожна транзакція модуля — спан CLIENT `db.transaction <модуль>` із тими самими полями при збої | NFR-10 п. 2, критерій 1 (інтеграційний тест на PostgreSQL) |
| Провайдери | `createProviderClient.call` — спан CLIENT `provider <операція>`, лічильник `ws.provider.calls` і при збої подія `provider.failure`: адаптер, операція, кількість спроб, результат (`ok` або вид збою), клас помилки або HTTP-статус. Ніколи URL, параметри, заголовки, ключі, тіла | NFR-10 п. 3 |
| Синхронізація банків | Лічильник `ws.bank_sync.runs` з `ws.outcome` = `success` / `failure` (`recordBankSyncRun`) визначено зараз; заповнить модуль `bank-sync` (FIN) | NFR-10 п. 6: правило алерту вже діє |
| SLO і алерти в коді | Джерело — `tools/observability/definitions.mjs`; з нього генеруються `infra/observability/rules.yaml` (групи правил Prometheus / Mimir: записи частки помилок за 5m…3d, p95 читання і запису, частка збоїв синхронізації за 1h; алерти), `alertmanager.yaml` (маршрутизація) і `dashboard-slo.json` (Grafana). `pnpm check:alerts` (CI-задача `infra`) перевіряє: файли збігаються з генерацією, вирази збалансовані й читають лише відомі серії, кожна вимога NFR-10 п. 6 / ARC-09 п. 4 має алерт `page`, пороги — числа вимог. Тест у `apps/api` тримає назви метрик, інтервал експорту і межі гістограми рівними коду | П. 4, NFR-10 п. 5–6; правила рецензуються як код |
| Алерти | Бюджет помилок (99,9 % за 30 днів) — багатовіконні швидкості вигорання: 14,4× (1h і 5m) і 6× (6h і 30m) — `page`, 1× (3d і 6h) — `ticket`; 5xx > 1 % за 5m (і є трафік); p95 читання > 0,3 с і запису > 0,5 с — лише якщо за 5m було ≥ 20 запитів цього виду (поріг `minRequests5m`: за трафіку PoC один повільний запит інакше сам був би p95 і будив би чергового); збої синхронізації > 5 % за 1h. `for` — 2m (синхронізація 1m, повільне вигорання 15m) | Стандартний підхід Google SRE: швидке виявлення великих збоїв без хибних сигналів від коротких сплесків |
| Навмисні 503 | Рішення ведучого (рецензія PR #85): 503 `MODULE_UNAVAILABLE` від аварійного вимикача модуля (CICD-06) і `SERVICE_UNAVAILABLE` під час зупинки не рахуються в чисельнику частки 5xx (селектор `http_response_status_code=~"5..", ws_problem_code!~"MODULE_UNAVAILABLE\|SERVICE_UNAVAILABLE"`), тож заплановане вимкнення не будить чергового й не спалює бюджет. Щоб вимкнений модуль не забули — `ticket` ApiModuleSwitchedOff: запити відхиляються вимикачем понад 30 хв (видно лише за трафіку до модуля) | Планова дія — не збій |
| ≤ 5 хв | Для кожного `page`: інтервал експорту метрик 30 с + ще один інтервал, щоб `rate()` побачив новий зразок, + оцінка правил 1 хв + `for` + `group_wait` 30 с ≤ 300 с (5xx: 270 с). Перевірка відмовляє правилу, що виходить за межу. `ticket` — не збій, а поступове вигорання бюджету: його не надсилають черговому | NFR-10 п. 6, критерій 2; ARC-09 «час від збою до алерту ≤ 5 хв» |
| Назви в Prometheus | Grafana Cloud (OTLP → Mimir) називає метрики так: крапки → підкреслення, одиниця `s` → `_seconds`, лічильник → `_total`; атрибути → мітки так само. Один стек Grafana Cloud на середовище, тож правила не фільтрують за середовищем | Якщо стек налаштує інший переклад, змінюються лише `METRICS` у `definitions.mjs` |

## Наслідки

- Модуль не імпортує OpenTelemetry: HTTP, транзакції БД і виклики провайдерів трасуються платформою. Новий атрибут —
  лише через `ATTRIBUTE_RULES` із граматикою значення й тестом; інакше фільтр його відкидає.
- Новий сигнал для алерту: метрика в `signals.ts` (`METRICS`), її назва в Prometheus у `definitions.mjs`, правило там же,
  `node tools/observability/index.mjs --write`.
- Тести: `testTelemetryForFile()` вмикає режим `test` на файл тестів; `exportedText()` — усе, що отримали експортери.
- Обмеження: SDK мовчки відкидає помилки експорту (сервіс недоступний) — запити не страждають, але процес, що впав чи
  перестав надсилати метрики, алерти на частках не помітять: це покриє зовнішній монітор доступності (ARC-09 п. 5, пізніше). `promtool` у CI не запускається: перевірку
  синтаксису PromQL робить власна перевірка (дужки, відомі серії); остаточну — ruler Grafana Cloud під час завантаження.
- Пізніше: обліковий запис і стек Grafana Cloud EU, адреса і токен у сховищі секретів, завантаження правил і дашборду
  (mimirtool / Terraform-провайдер — рішення про застосування з approval власника), контактна точка чергового,
  зовнішній монітор із двох точок ЄС (ARC-09 п. 5), щотижневе автоматичне сканування вибірки логів, продуктова
  аналітика зі згодою (NFR-10 п. 7) і звіти адмін-панелі (п. 8), показ коду в компоненті ErrorState (CMP-24).
