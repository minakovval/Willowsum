# ADR-0001: стек бекенду і межі модулів

**Створено:** 2026-11-06 · **Оновлено:** 2026-11-06

**Статус:** Прийнято (рішення ведучого, PR ARC-01). **Вимоги:** ARC-01@PoC, ARC-03@PoC, ARC-07@PoC.

## Контекст

ARC-01 вимагає модульний моноліт на TypeScript: окрема схема БД на модуль, один файл правил
залежностей, аналізатор у CI, генератор каркаса і версіонований каталог подій. Вимоги не називають
бібліотек, а кожна нова залежність потребує обґрунтування (AGENTS.md, «Crypto and dependencies»).

## Рішення

| Що | Вибір | Чому |
| --- | --- | --- |
| Мова і запуск | TypeScript, Node.js 22 із вбудованим зняттям типів (`node file.ts`), без збірки для скриптів і тестів | Те саме, що вже діє в `packages/ui`; менше інструментів |
| Десяткові суми | `decimal.js` 10 (MIT) у `packages/domain-kernel`; точність 60 значущих цифр, сума обмежена NUMERIC(38,18) | Зрілий, без залежностей, працює в браузері й на сервері; float заборонено |
| База даних | PostgreSQL 17, драйвер `pg` (MIT) | Стандартний драйвер; конструктор запитів додаємо лише з першими таблицями, окремим рішенням |
| Міграції | Власний невеликий виконавець (`apps/api/src/platform/db/migrate.ts`): SQL-файли `NNNN_slug.sql` у папці модуля, контрольна сума, незмінність застосованих файлів, кожна міграція в транзакції | Потрібні саме схема і роль на модуль; це 150 рядків без криптографії, простіше перевірити, ніж налаштовувати сторонній інструмент |
| Схеми й права | Схема на модуль; роль `ws_mod_<module>` має DML лише в своїй схемі; роль застосунку `ws_app` — NOINHERIT і без власних прав; код модуля працює через `ModuleDatabase`, що робить `SET LOCAL ROLE` і `search_path`; DDL — лише в міграціях | Межу модулів тримає сама база (критерій ARC-01 «запити до таблиць чужої схеми — 0»), а не лише рев'ю |
| Схеми даних і подій | `zod` 4 (MIT); JSON Schema для подій — `z.toJSONSchema` | Ті самі схеми згодом дають OpenAPI 3.1 (ARC-07) |
| Аналізатор залежностей | `dependency-cruiser` 18 (MIT), правила будуються з `apps/api/module-rules.json` | Широко вживаний; розуміє TypeScript, типові імпорти і цикли |
| Тести | Vitest (як у фронтенді); інтеграційні `*.it.test.ts` — на реальному PostgreSQL 17 у CI-задачі `api` | Один інструмент на весь репозиторій |
| HTTP-фреймворк | Обирається в PR ARC-02 / ARC-07 | Не потрібен для ARC-01 |

## Правила, які перевіряє CI (`pnpm check:modules`)

- Модулі й залежності — лише з `module-rules.json`; назви — лише з каталогу модулів ARC-01; цикли
  заборонено; напрям: платформа ← предметні модулі ← процесні модулі.
- Інший модуль — лише через його `index.ts`; заборонено імпорт, що не розв'язується.
- Домен імпортує лише свої файли, `@willowsum/domain-kernel`, `zod`, `decimal.js`; застосунок не
  імпортує адаптери; модулі не імпортують драйвер БД; `src/platform` не знає про модулі.
- Події: опублікована версія змінюється лише сумісно (нові необов'язкові поля), інакше — нова версія;
  кожна подія, яку споживає модуль, існує в потрібній версії.

## Наслідки

- Новий модуль створюється лише генератором: `pnpm new-module <name> [--depends a,b]`.
- Пул з'єднань працює від імені `ws_app`; пароль і LOGIN для нього задає інфраструктура (CICD-07), а
  міграції запускає окрема роль-власник схем.
- Код модуля не може змінити роль або `search_path`: `ModuleDatabase` відхиляє такі запити.
