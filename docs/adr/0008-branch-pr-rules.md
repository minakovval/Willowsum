# ADR-0008: правила гілок і PR — мітка «чутливий» за шляхами, перевірка опису PR, щоденна перевірка `main`

**Створено:** 2026-11-12 · **Оновлено:** 2026-11-12

**Статус:** Прийнято (рішення ведучого, PR CICD-01). **Вимоги:** CICD-01@PoC (п. 1 — звіт про вік гілок; п. 2; п. 3,
пункти 1 і 3; п. 4; п. 5 — через перевірку рецензії; критерії 1–4). Пункт 3.2 і критерій 5 (у production — лише
образ із зеленого коміту) належать розгортанню CICD-07. Рішень ADR-0001…0007 не змінює.

## Контекст

Безкоштовний план GitHub не дозволяє заборонити прямий запис у `main` чи вимагати перевірки перед злиттям. Тому
захист — процес (AGENTS.md, крок 7), а CI його перевіряє: PR-час — назва й опис, позначка чутливості; щодня —
що все злите в `main` пройшло правила. Як це влаштовано насправді: агенти пишуть рецензії як COMMENT з облікового
запису власника (того самого, що зливає), закінчуючи рядком «Verdict: Ready» / «Verdict: Not ready» (review-pr) або
«Security verdict: Ready» / «Security verdict: Changes requested» (рецензія безпеки); зливає агент (squash);
схвалення власника для хмари й production — коментар у PR з облікового запису власника. Отже, хто написав рецензію,
за обліковим записом не відрізнити: розпізнається лише текст.

## Рішення

| Що | Вибір | Чому |
| --- | --- | --- |
| Де код | `tools/pr-rules/` без залежностей: `lib/paths.mjs` (мапа шляхів), `lib/description.mjs` (опис PR), `lib/daily.mjs` (чиста логіка щоденної перевірки), `lib/fetch.mjs` і `lib/github.mjs` (лише читання REST API і issue алерту), `index.mjs` (команди `label`, `description`, `daily`). Тести — `node --test tools/pr-rules`, у задачах `traceability` і `main-check` | Як `tools/infra-check`: логіка тестується на записаних відповідях API без мережі |
| Чутливі шляхи (п. 4) | Мапа категорія → glob у `SENSITIVE_PATHS`: `auth` (модуль `identity`, `**/auth/**`, cookie, Origin, ліміти частоти), `permissions` (`access-scope`, `household`, `plan-catalog`, `staff-admin`, спільний доступ сховища, `platform/http`, `api.ts`, правила модулів), `encryption` (`vault-items`, `file-storage`, `*encrypt*`, `*cipher*`, `*kms*`), `money` (`domain-kernel` і модулі з грошовими розрахунками), `schema` (`**/migrations/**`, `platform/db`, скрипти схеми й міграцій), `pipeline` (`.github/**`, `Dockerfile`, `.dockerignore`, налаштування gitleaks, `tools/pr-rules`), `infrastructure` (`infra/**`, `tools/infra-check`, `tools/observability`). Markdown не чутливий ніде: документація не змінює поведінку. Перейменування класифікується за обома назвами | Одна мапа для мітки й щоденної перевірки — вони не розходяться. Модулі, яких ще немає, уже в мапі |
| Мітка (п. 4) | `pr-sensitive-label.yml`, задача `sensitive-label` на `pull_request` (opened, reopened, synchronize, ready_for_review): мітки `sensitive` і `sensitive:<категорія>`; токен — `contents: read`, `pull-requests: write` лише для цієї задачі. Мітки лише додаються, ніколи не знімаються. PR з форка отримує токен лише для читання — задача тоді тільки пише в журнал. Задача інформаційна, не обов'язкова. Рішення «зливати чи ні» не залежить від мітки: агент, що зливає, і щоденна перевірка визначають чутливість за файлами (мітка або файли) | `pull_request_target` не використовується: задача виконує код PR, тож токен не може бути ширшим, ніж права автора PR. Для того самого репозиторію автор і так має запис |
| Блокування за п. 4 у CI | Немає: перевірка в CI, яка падає до вердикту безпеки, повторно запускалася б на кожну рецензію і не відрізнила б рецензію агента від тексту автора. Правило злиття виконує агент (AGENTS.md, крок 7), щоденна перевірка ловить порушення. Опис PR з чутливими файлами мусить мати відмічене «Sensitive areas touched» — це блокує | Перевірка CI лише інформує й позначає |
| Опис PR (п. 2, критерій 4) | Задача `traceability` переїхала з `pr-checks.yml` у `pr-description.yml` (та сама назва, тож перелік обов'язкових задач у AGENTS.md не змінюється) і запускається також на `edited` — виправлення опису перезапускає лише її. Перевіряє: назва починається з ID (`ABC-12`, `ABC-12a`), за яким `:`, `,`, пробіл чи `(`, і для ID є файл у `docs/requirements/<модуль>/`; у тексті є розділи шаблону `Requirement`, `Acceptance criteria covered`, `How it was tested`, `Sensitive areas touched` (HTML-коментарі шаблону не рахуються); «Requirement» не порожній; «Acceptance criteria covered» не порожній, а таблиця в ньому має хоч один рядок; «How it was tested» не порожній і не лише невідмічені пункти шаблону; за чутливих файлів відмічено «Sensitive areas touched». Назву й опис скрипт читає з файлу події, не з виразів `${{ }}` | Окремих «процесних» префіксів не потрібно: усі назви злитих PR починаються з ID, для якого є файл (PRC-02, DS-01 теж вимоги). PR лише з документацією пише в «Acceptance criteria covered» пояснення замість таблиці (як #76, #79). Перевірено на злитих PR: з #68 усі проходять; #61–#67 (опис без шаблону) не пройшли б |
| Щоденна перевірка (п. 3, критерії 1–3) | `daily-main-check.yml`: щодня о 05:41 UTC і вручну (`workflow_dispatch` з необов'язковими `since`/`until`). Вікно — 25 год (година перекриття на затримку розкладу). Токен — `contents`, `pull-requests`, `checks` на читання і `issues: write`. Спершу запускає власні тести | Алерт — GitHub issue з міткою `main-check`: нове, або коментар у відкритому (сповіщення власнику). Задача завершується з помилкою, коли є що перевірити, — це друге сповіщення. Зовнішніх сервісів і секретів немає |
| Коміти без PR, force-push | Два джерела: журнал змін репозиторію (`GET /repos/{repo}/activity?ref=refs/heads/main`) — будь-яка подія, крім `pr_merge`, є порушенням (`force_push`, `push`, видалення гілки); і коміти `main` — датовані у вікні плюс ті, що принесла кожна подія журналу (`compare before...after`). Коміт у порядку, лише якщо він — `merge_commit_sha` злитого в `main` PR (`GET /commits/{sha}/pulls`). Журнал, який не вдалося прочитати, — теж порушення | Дату коміту автор задає довільно, тож лише датою не обійтися; журнал змін фіксує force-push, який у самій історії не видно. Межі: журнал GitHub зберігається обмежений час (не менше вікна перевірки); власник із правами адміністратора міг би обійти будь-яку перевірку, тож це виявлення, а не заборона |
| Злиті PR: CI | Обов'язкові задачі — задачі `pr-checks.yml` і `pr-description.yml` у версії `main` перед злиттям (батько коміту злиття), щоб PR не міг сам себе звільнити. Для кожної — остання за id перевірка `github-actions` на останньому коміті PR: `completed`, `success` і завершена до злиття | Перезапуск рахується: вирішує останній запуск задачі |
| Злиті PR: рецензії (п. 3, п. 5) | Вердикт — рядок, що починається з `Verdict:` або `Security verdict:` (можна як заголовок `##`, жирним, значення в «»); у рецензії діє останній такий рядок. Рахуються рецензії до моменту злиття; вирішує **остання** за часом рецензія свого виду. Порушення: немає «Ready» або останній вердикт не «Ready». «Перевірити»: «Ready» дано на коміті, старішому за злитий (коміти після рецензії ніхто не рецензував). Для чутливого PR (мітка `sensitive` або чутливі файли) — те саме для «Security verdict» | Автора рецензії не відрізнити (усі пишуть з облікового запису власника), тож рахується текст. Рецензія на старішому коміті — не порушення букви п. 3, але й не перевірка останнього коміту; рішення — за власником (див. відкриті питання) |
| Злиті PR: хмара і production | Потребує схвалення, якщо PR змінює робочий процес, що застосовує інфраструктуру, розгортає чи публікує (`tofu`/`terraform apply`, `id-token: write`, `environment: production`, `docker push`, `cosign sign`, або назва файлу з `deploy`, `release`, `apply`, `promote`, `production`), або в `infra/` (крім `infra/local/`, крім Markdown і рядків-коментарів) — довіру OIDC, сховище секретів production (`oci_vault_secret`) чи записи DNS. Робочий процес оцінюється за повним текстом на коміті злиття. Схвалення — коментар до злиття з облікового запису власника репозиторію з окремим рядком **«Схвалюю»** або **«Approved»** (без цитування `>`); схвалення, написане до останнього коміту, — «перевірити». Код інфраструктури без застосування (як `infra/start`, KMS як код) схвалення не потребує | Облікові записи агента й власника збігаються, тож розпізнається точна фраза; агенти такого рядка не пишуть (див. відкриті питання) |
| «stop» власника | Коментар власника з окремим рядком «stop» / «стоп» у злитому PR — «перевірити»: чи відповів власник до злиття | Відповідь власника від відповіді агента за обліковим записом не відрізнити |
| Вік гілок (п. 1) | Гілка, у якої найстаріший коміт, якого немає в `main`, старший за 3 дні, — «довідково», з номером і станом її PR. Сама по собі issue не відкриває | Після squash-злиття гілка лишається; її видалення — рішення власника |
| Записані відповіді API | `daily --save-input <файл>` зберігає вхід перевірки, `daily --input <файл>` відтворює її без мережі. Тест `daily.test.mjs` використовує запис для PR #82–#86 (логіни замінено, тіла рецензій скорочено до заголовка й рядка вердикту) | Логіка й реальна історія перевіряються однаково |

## Що показує щоденна перевірка на реальній історії

Запуск 2026-11-12 для вікна 2026-11-06T23:00Z…2026-11-07T12:00Z (PR #82–#86): 5 комітів у `main`, усі — коміти
злиття PR; force-push немає; CI зелений на останньому коміті кожного PR і завершився до злиття. Знайдено:

- **Порушення:** #86 — злито, коли останній вердикт безпеки був «Changes requested» (рецензія 5811865652 на
  `591cfef`); виправлення `e0ca73a` повторної рецензії безпеки не мало.
- **Перевірити:** «Verdict: Ready» на старішому коміті — #83 (`6ce7f5a` → злито `edf2b77`), #84 (`5a95cf0` → `4a9f400`),
  #86 (`591cfef` → `e0ca73a`); «Security verdict: Ready» на старішому коміті — #83 (`6ce7f5a` → `edf2b77`),
  #85 (`7d56a8a` → `ad0f51f`).

Історія не змінюється; ці знахідки — питання до власника про правило, нижче.

## Відкриті питання власнику

1. **Фраза схвалення.** Пропозиція: схвалення дії на хмару чи production — коментар з окремим рядком «Схвалюю»
   (або «Approved»), і агенти ніколи не пишуть такого рядка. Це змінює правила агентів (AGENTS.md, крок 7, і skills),
   тож потребує рішення власника; до нього перевірка вже шукає саме цю фразу.
2. **Рецензія на останньому коміті.** Чи має «Ready» (і «Security verdict: Ready») бути дано на тому коміті, який
   зливається? Зараз агенти зливають після дрібних виправлень без повторної рецензії (#83–#86); перевірка позначає це
   «перевірити». Якщо так — правило додається до AGENTS.md і skill; якщо ні — знахідку можна прибрати.
3. **Формат вердикту безпеки.** Skill `review-pr` описує лише «Verdict»; рядок «Security verdict: Ready» — звичай
   рецензій безпеки з #68. Закріпити його в skill (зміна skills — рішення власника).
4. **Старі гілки.** 30 робочих гілок старші за 3 дні, PR усіх злиті. Видалити їх (і вмикати автоматичне видалення
   гілки після злиття в налаштуваннях репозиторію)?

## Наслідки

- Агент, що відкриває PR, заповнює шаблон: без розділів, рядка критерію чи відмітки чутливих змін задача
  `traceability` червона. Редагування опису перезапускає лише її.
- Обов'язкові задачі CI ті самі, що в AGENTS.md; нова задача в `pr-checks.yml` чи `pr-description.yml` стає
  обов'язковою для щоденної перевірки автоматично (тест порівнює їх з AGENTS.md).
- Пізніше: п. 3.2 і критерій 5 — розгортання лише образу, зібраного з коміту злитого PR із зеленим CI, з перевіркою
  підпису (CICD-07, перший PR розгортання); тоді ж робочий процес розгортання потрапить під правило схвалення власника.
