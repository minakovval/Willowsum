# ADR-0008: правила гілок і PR — мітка «чутливий» за шляхами, перевірка опису PR, щоденна перевірка `main`

**Створено:** 2026-11-12 · **Оновлено:** 2026-11-12

**Статус:** Прийнято (рішення ведучого, PR CICD-01). **Вимоги:** CICD-01@PoC (п. 1 — звіт про вік гілок; п. 2; п. 3,
пункти 1 і 3; п. 4; п. 5 — через перевірку рецензії; критерії 1–4). Оновлено 2026-11-12 за рецензіями PR #87 і рішенням
власника 2026-11-12 (схвалення, вердикти на коміті злиття, формат вердикту безпеки). Пункт 3.2 і критерій 5 (у production — лише
образ із зеленого коміту) належать розгортанню CICD-07. Рішень ADR-0001…0007 не змінює.

## Контекст

Безкоштовний план GitHub не дозволяє заборонити прямий запис у `main` чи вимагати перевірки перед злиттям. Тому
захист — процес (AGENTS.md, крок 7), а CI його перевіряє: PR-час — назва й опис, позначка чутливості; щодня —
що все злите в `main` пройшло правила. Як це влаштовано насправді: агенти пишуть рецензії як COMMENT з облікового
запису власника (того самого, що зливає), закінчуючи рядком «Verdict: Ready» / «Verdict: Not ready» (review-pr) або
«Security verdict: Ready» / «Security verdict: Changes requested» (рецензія безпеки) і називаючи SHA перевіреного
коміту (формат закріплено в AGENTS.md і skill `review-pr`, рішення власника 2026-11-12); зливає агент, лише squash
(технічне обмеження перевірки — злиття комітом злиття чи rebase не підтримуються: коміти гілки не є `merge_commit_sha`, і перевірка позначила б
їх порушенням); схвалення власника для хмари й production — коментар з облікового запису власника з рядком
«Схвалюю» / «Approved» або рішення власника з чату, записане в описі PR. Отже, хто написав рецензію, за обліковим
записом не відрізнити: розпізнається лише текст.

Назву й опис скрипт читає з файлу події, не з виразів `${{ }}` | Окремих «процесних» префіксів не потрібно: усі назви злитих PR починаються з ID, для якого є файл (PRC-02, DS-01 теж вимоги). | Щоденна перевірка (п. 3, критерії 1–3) | `daily-main-check.yml`: щодня о 05:41 UTC і вручну (`workflow_dispatch` з необов'язковими `since`/`until`). Вікно починається за годину до старту останнього запуску за розкладом, у якому крок «Check main and merged PRs» завершився успішно (Actions API, лише читання), але не раніше ніж 7 днів тому; якщо такого запуску немає або журнал запусків не прочитано — 25 год (причина пишеться у звіт). Якщо вікно не почалося з останнього перевіреного запуску (межа 7 днів, журнал не прочитано, запуски були, але жоден не перевірив свого вікна), звіт має пункт «перевірити»: успіх цього запуску зсуває наступне вікно, тож пропущений час інакше лишився б непоміченим. Тож пропущений чи невдалий день покриває наступний запуск. Крок перевірки успішний, коли вікно перевірено, навіть зі знахідками; задачу валить наступний крок `alerted`. Токен — `contents`, `pull-requests`, `checks`, `actions` на читання і `issues: write`. Спершу запускає власні тести | Алерт — GitHub issue з міткою `main-check`: нове, або коментар у відкритому, яке відкрив сам `github-actions[bot]` (сповіщення власнику). Задача завершується з помилкою, коли є що перевірити, — це друге сповіщення. Якщо дані не вдалося прочитати, issue теж відкривається (з класом помилки, напр. `HTTP 502`), а задача падає. Обрізаний перелік (більше сторінок, ніж межа) — помилка, а не коротший перелік. Без `--issue` перевірка лише друкує звіт (сухий запуск). Зовнішніх сервісів і секретів немає |
| Коміти без PR, force-push | Два джерела: журнал змін репозиторію (`GET /repos/{repo}/activity?ref=refs/heads/main`) — будь-яка подія, крім `pr_merge`, є порушенням (`force_push`, `push`, видалення гілки); і коміти `main` — датовані у вікні плюс ті, що принесла кожна подія журналу (`compare before...after`). Коміт у порядку, лише якщо він — `merge_commit_sha` злитого в `main` PR (`GET /commits/{sha}/pulls`). Журнал, який не вдалося прочитати, — теж порушення | Дату коміту автор задає довільно, тож лише датою не обійтися; журнал змін фіксує force-push, який у самій історії не видно. Межі: журнал GitHub зберігається обмежений час (не менше вікна перевірки); власник із правами адміністратора міг би обійти будь-яку перевірку, тож це виявлення, а не заборона |
| Злиті PR: CI | Обов'язкові задачі — задачі `pr-checks.yml` і `pr-description.yml` у версії `main` перед злиттям (батько коміту злиття), щоб PR не міг сам себе звільнити. Для кожної — остання за id перевірка застосунку `github-actions` на останньому коміті PR серед завершених до злиття (усі запуски, `filter=all`): `success`. Запуски після злиття (напр. `traceability` після редагування опису злитого PR) ігноруються | Перезапуск рахується: вирішує останній запуск задачі до злиття |
| Злиті PR: рецензії (п. 3, п. 5) | Вердикт — рядок, що починається з `Verdict:` або `Security verdict:` (можна як заголовок `##`, жирним, значення в «»), значення `Not ready` чи `Changes requested` рахується з будь-яким текстом після нього («Verdict: Not ready — see B1») і в будь-якому регістрі й написанні мітки та значення («Security Verdict : Not-Ready»), щоб негативний вердикт ніколи не губився; лише значення `Ready` мусить закінчувати рядок (далі — розділовий знак, «…», пробіл чи NBSP і закриття розмітки) або бути закритим жирним (`**Verdict: «Ready»**. …`): «Verdict: Ready once B1 is fixed» — не вердикт. У рецензії діє останній такий рядок. Не рахуються рядки в цитаті `>`, у блоках коду (огороджених і з відступом) і в HTML-коментарях. Рахуються рецензії з облікового запису власника репозиторію (як і схвалення), подані до моменту злиття, крім відхилених (`DISMISSED`) і непосланих; вирішує **остання** за часом рецензія свого виду. Порушення: немає «Ready», останній вердикт не «Ready», або (для PR, злитих з 2026-11-12) «Ready» дано на коміті, старішому за злитий. Для PR, злитих раніше, останнє — «перевірити» (історію не переписуємо). Для чутливого PR (мітка `sensitive` або чутливі файли) — те саме для «Security verdict» | Автора рецензії не відрізнити (усі пишуть з облікового запису власника), тож рахується текст. Рішення власника 2026-11-12: «Ready» стоїть на коміті, що зливається; будь-який пізніший коміт — нова рецензія. Межа: текст рецензії можна змінити після подання (`submitted_at` не змінюється) — перевірка покладається на текст |
| Злиті PR: хмара і production | Потребує схвалення, якщо PR змінює робочий процес, що застосовує інфраструктуру, розгортає чи публікує (`tofu`/`terraform apply`, `id-token: write`, `environment: production` (без огляду на регістр) — і рядком, і блоком з `name: production` у будь-якому місці, `docker push`, `docker/build-push-action` з `push: true`, `cosign sign`, будь-який секрет, крім `GITHUB_TOKEN` (контекст `secrets` у будь-якому виразі й регістрі — `secrets.*`, `secrets[…]`, `toJSON(secrets)` — і `secrets: inherit`), або назва файлу з `deploy`, `release`, `apply`, `promote`, `production`), або в `infra/` (крім `infra/local/`, крім Markdown і рядків-коментарів) — довіру OIDC, сховище секретів production (`oci_vault_secret`) чи записи DNS. Робочий процес оцінюється за повним текстом на коміті злиття; зміна, яку GitHub не повернув (великий diff без `patch`), потребує схвалення. Схвалення (рішення власника 2026-11-12) — одне з двох: (а) коментар до злиття з облікового запису власника репозиторію з окремим рядком **«Схвалюю»** або **«Approved»** (не в цитаті, коді чи HTML-коментарі); схвалення, написане до останнього коміту, — «перевірити»; (б) рішення власника з чату, записане в описі PR рядком **`Рішення власника (YYYY-MM-DD): схвалено …`** (рядок починається так, не в цитаті чи коді; заперечення чи відмова після «схвалено» — «не», «ні», «відхилено», «скасовано», «відкликано», «not», «no», «never», «rejected», «denied», як у «схвалено не буде», — робить рядок не схваленням; пункт списку `- Рішення власника …` не рахується). **Межа обох форм:** агенти й власник пишуть з одного облікового запису, тож будь-яка сесія агента технічно може написати і коментар, і рядок в описі; перевірка доводить лише, що рядок є. Це правило процесу (AGENTS.md, крок 7), а не технічний контроль. Дата в рядку з датою злиття не порівнюється. Опис читається таким, яким він є під час перевірки (історію правок REST API не дає; редагування після злиття видно в історії PR). Код інфраструктури без застосування (як `infra/start`, KMS як код) схвалення не потребує | Облікові записи агента й власника збігаються, тож розпізнається точна фраза; агенти рядка «Схвалюю»/«Approved» ніколи не пишуть, а рядок у описі — лише для рішення, яке власник справді дав (AGENTS.md, крок 7) |
| Зміни правил і вимог (п. 3, пункт 1) | Мапа `OWNER_DECISION_PATHS`: `AGENTS.md`, `CLAUDE.md`, `.claude/**` (skills і налаштування), `docs/requirements/**`. Зміна вимоги лише в рядку «Перевіряється» (шляхи тестів) не рахується. `docs/plans/**` не входить: плани — робочі нотатки ведучого, не правила й не вимоги. Мітка `owner-decision` ставиться тією ж задачею `sensitive-label`. Щоденна перевірка позначає «перевірити», якщо злитий PR змінює такі файли, а в описі немає рядка «Рішення власника …» і немає тексту під `## Owner decision` до наступного заголовка того самого чи вищого рівня (підзаголовки — частина розділу, але самі по собі, без тексту, нічого не записують; після вилучення коментаря шаблону сам заголовок незаповненого шаблону не рахується) | Агент, що зливає, бачить мітку; власник — звіт. Порушенням не вважається: чи запис справді відповідає рішенню, вирішує власник |
| Межі й захист від обходу | Назва основної гілки береться з репозиторію; константа `DEFAULT_MAIN` — єдине місце, де написано `main`. Перелік API, обрізаний на межі, — помилка; файли без `patch` — нечитані (fail closed). Дані з PR (назви файлів, заголовки) у звіті й журналі очищуються від переносів рядка, `::` і `##[` | Перевірка не повинна мовчки пропускати |
| «stop» власника | Коментар власника з окремим рядком «stop» / «стоп» у злитому PR — «перевірити»: чи відповів власник до злиття | Відповідь власника від відповіді агента за обліковим записом не відрізнити |
| Вік гілок (п. 1) | Гілка, у якої найстаріший коміт, якого немає в `main`, старший за 3 дні, — «довідково», з номером і станом її PR. Сама по собі issue не відкриває | Після squash-злиття гілка лишається; її видалення — рішення власника |

## Наслідки

- Агент, що зливає, порівнює SHA, названий у кожній рецензії, з головою PR; після будь-якого нового коміту — повторна
  рецензія. Рецензенти пишуть рядок вердикту окремо, не в цитаті й не в коді.
- Агент, що відкриває PR, заповнює шаблон: без розділів, рядка критерію чи відмітки чутливих змін задача
  `traceability` червона. Редагування опису перезапускає лише її.
- Обов'язкові задачі CI ті самі, що в AGENTS.md; нова задача в `pr-checks.yml` чи `pr-description.yml` стає
  обов'язковою для щоденної перевірки автоматично (тест порівнює їх з AGENTS.md).
- Пізніше: п. 3.2 і критерій 5 — розгортання лише образу, зібраного з коміту злитого PR із зеленим CI, з перевіркою
  підпису (CICD-07, перший PR розгортання); тоді ж робочий процес розгортання потрапить під правило схвалення власника.
