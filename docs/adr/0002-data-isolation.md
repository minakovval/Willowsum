# ADR-0002: ізоляція просторів, схема даних, міграції, аудит і синтетичні дані

**Створено:** 2026-11-06 · **Оновлено:** 2026-11-06 (рецензії PR #75: ролі-власники модулів, страж ізоляції (тригер подій), межа поза схемами модулів, одноразовий bootstrap, рішення власника про власний PostgreSQL)

**Статус:** Прийнято (рішення ведучого, PR ARC-03). **Вимоги:** ARC-03@PoC. Доповнює
[ADR-0001](0001-backend-stack.md), не змінює його рішень.

## Контекст

ARC-03 вимагає двох рівнів ізоляції просторів (фільтр у коді і політики рядків у базі, що діють для ролі
застосунку), сум NUMERIC(38,18) із кодом валюти, часу в UTC, регіону і власного ключа простору, міграцій
«розширити → перенести → звузити» з тестом «старий код + нова схема», журналу аудиту лише на дописування і
синтетичного набору даних. Модуля `household` ще немає (ACC-08 — хвиля 2).

| Хто виконує SQL міграцій (корінь) | Роль-власник модуля `ws_own_<схема>`: NOLOGIN, NOINHERIT, без суперкористувача, BYPASSRLS і CREATEROLE; USAGE і CREATE лише на схемі свого модуля (схемою володіє роль запуску); володіє всіма об'єктами схеми; член жодної ролі. Виконавець у транзакції міграції робить `SET LOCAL ROLE ws_own_<схема>`, створює від її імені SECURITY DEFINER-обгортку `ws_run_migration(sql)` у схемі модуля, виконує в ній SQL міграції і видаляє її; усередині SECURITY DEFINER-функції PostgreSQL забороняє SET ROLE, RESET ROLE і SET SESSION AUTHORIZATION, тож повернутися до ролі запуску не можна. Безпеку рядків і політику вмикає теж роль-власник (вона власник таблиць), у тій самій транзакції. Типові права ролі-власника дають ролі модуля `ws_mod_<схема>` лише DML. Роль запуску тримає роль-власника лише з SET (без INHERIT) | Правила, тригери, функції й представлення, які створює міграція, діють із правами ролі-власника, а не ролі запуску; проте власник таблиці завжди може вимкнути FORCE, змінити політику чи додати правило — від цього захищає страж (наступний рядок); поза своєю схемою вона нічого не створить і функцій платформи не замінить (рецензія PR #75, раунд 2) |
| Страж ізоляції (тригер подій) | `db:bootstrap` від суперкористувача ставить тригер подій `ws_module_guard` (`ddl_command_end`, власник — суперкористувач) із функцією `platform_guard.guard_ddl()`. Після кожної DDL-інструкції, яку виконала роль-власник модуля (`current_user` = `ws_own_<схема>`: SQL міграції виконується в її обгортці), він викликає `platform_guard.check_module(<схема>)` (SECURITY DEFINER суперкористувача). Та 1) одразу ізолює нову таблицю з `household_id` (ENABLE і FORCE, політика `household_isolation`) — від суперкористувача, тож страж не перевіряє власних кроків; 2) відхиляє інструкцію, якщо в схемі є таблиця з `household_id` без увімкненої й примушеної безпеки рядків або з іншою політикою чи зміненою стандартною, таблиця без `household_id` з безпекою рядків чи політиками, матеріалізоване представлення, правило перезапису (крім `_RETURN`) або представлення без `security_invoker`. Без справного стража (немає, вимкнений, змінений) міграції від несуперкористувача зупиняються й називають `db:bootstrap` | Рецензія PR #75, раунд 3: NO FORCE / DISABLE, ALTER POLICY, DROP + CREATE POLICY, CREATE RULE, CREATE MATERIALIZED VIEW у міграції падають одразу, до наступної інструкції, тож скопіювати рядки іншого простору неможливо. Обмежувальна політика теж заборонена: її вираз бачить рядки всіх просторів до фільтра простору |
| Код і вирази в схемах модулів (рецензія безпеки 5801405103) | Сервер виконує вирази над рядками всіх просторів під час DDL (перевірка CHECK, побудова індексу, обчислення збережених згенерованих колонок, `ALTER COLUMN … TYPE … USING`), де політика рядків не діє. Тому `platform_guard.module_problems(<схема>)` (його викликають страж після кожної DDL і `check:schema`) відхиляє: 1) будь-яку функцію, процедуру чи агрегат у схемі модуля, крім тригерних функцій без SECURITY DEFINER (тригери виконуються під час роботи від ролі, що викликає, під політикою) і обгортки виконавця міграцій; оператори й приведення типів; 2) традиційне успадкування таблиць (батьківська таблиця без політики показала б рядки нащадків) — лише декларативні розділи, і розділена таблиця мусить бути таблицею клієнтів; 3) у CHECK (також доменів), виразах і предикатах індексів і збережених згенерованих колонках — будь-яку функцію чи оператор, крім незмінних (IMMUTABLE) з `pg_catalog` (ідентифікатори читаються з дерев виразів, бо залежності від `pg_catalog` не записуються); типові значення колонок дозволені — вони не бачать інших рядків. Окремий тригер подій `ws_module_rewrite_guard` (`table_rewrite`) до перезапису відхиляє зміну типу колонки ролями-власниками (з `USING` чи без, також у `DO`-блоках): тип змінюють через нову колонку (розширити → перенести → звузити). `check_module` перевіряє стек викликів і працює лише з тригера подій, тож роль модуля під час роботи його не викличе | Інструкція з порушенням падає, і транзакція міграції відкочується разом з усім, що встигло записатися транзакційно |
| Межа поза схемами модулів (другий рубіж) | Після міграцій у кожному запуску (`assertIsolatedRoles`, під тим самим замком) — усі правила `check:schema` (`schemaProblems`: безпека рядків, точна політика, суми, час, регіон, ключі, представлення), не лише межа, тож розгортання не залежить від того, чи пройшов CI; і `boundaryProblems` (`isolation.ts`): ролі модулів, `ws_probe` і `ws_context` нічим не володіють; роль-власник володіє лише об'єктами своєї схеми, і кожен об'єкт схеми модуля належить їй; явні права ролей модуля і власника — лише на свою схему, CONNECT до бази і дозволений список (USAGE на `platform_context` і `platform_types`, EXECUTE на `platform_context.current_household()`), глобальні типові права для них заборонено; жодне відношення поза своєю схемою і системними каталогами не доступне їм (з правами на колонки й послідовності та правами PUBLIC); SECURITY DEFINER-функцій немає в жодній схемі, крім двох функцій платформи, які мусять збігатися з її визначенням (текст, налаштування, власник), а в `platform_context` і `platform_types` немає нічого іншого; немає правил перезапису (крім `_RETURN` представлень), тригерів подій (крім стража, який перевіряється так само, як функції платформи) і розширень (крім plpgsql); у схемі public немає таблиць; `household_id` поза схемами модулів заборонено | Ловить те, що міг би створити привілейований користувач вручну чи помилкою; правила, тригери з SECURITY DEFINER-функцією і заміна функції платформи — проби рецензії PR #75 |
| Ключі таблиць клієнтів | Унікальні ключі й зовнішні ключі таблиці з даними клієнтів містять `household_id`; виняток — унікальний ключ з однієї колонки uuid | Помилка дубліката чи зовнішнього ключа інакше показала б, що рядок є в іншому просторі, а зовнішній ключ міг би вказати в чужий простір; випадковий uuid нічого не відкриває тому, хто його не знає |
| Розміщення PostgreSQL | Рішення власника 2026-11-06 («Власний PostgreSQL на VM»): staging і production PoC — власний PostgreSQL на VM в OCI (профіль «Старт»); суперкористувач є лише для одноразового `db:bootstrap` кожної бази, міграції далі — від власника схем без суперкористувача, з BYPASSRLS; WAL-архівування і резервні копії — наші (pgBackRest, CICD-07, NFR-16) | Керовані сервіси часто не дають суперкористувача, а `lo_*` у `pg_catalog` змінює лише він |

## Наслідки

- Роль запуску міграцій — власник бази з CREATEROLE (або суперкористувач); BYPASSRLS їй не потрібен, бо
  SQL модулів вона не виконує. Ролі, які вона створює, PostgreSQL 16+ дає їй лише з ADMIN (без INHERIT і
  SET); ролі-власники модулів вона тримає з SET, без INHERIT. Перевірка ізоляції допускає саме це.
- Перенесення даних (backfill), що стосується всіх просторів, від ролі-власника не побачить жодного рядка
  (безпека рядків примушена й для неї). У PoC таких міграцій немає; коли знадобляться, для них потрібен
  окремий механізм із рецензією (поза звичайними міграціями модулів).
- Одноразовий bootstrap кожної нової бази (CICD-07): `DATABASE_URL=<суперкористувач> pnpm --filter
  @willowsum/api db:bootstrap` — закриває `lo_*` і ставить страж ізоляції. Без нього перший запуск міграцій без суперкористувача зупиняється з
  поясненням, що робити (без значень). Перевірено тестом `apps/api/test/bootstrap.it.test.ts`.
- Інфраструктура дає ролі `ws_context` LOGIN і пароль зі сховища секретів (`WS_DB_CONTEXT_PASSWORD`).
- Прийнятий низький ризик: роль модуля може записати `application_name` свого з'єднання, а інша роль
  прочитати його з `pg_stat_activity` (текст запиту прихований). Це канал між модулями поза схемами того
  самого класу, що й великі об'єкти, але він потребує двох змовлених модулів, а код модулів проходить
  рецензію; закривати його немає простого способу без розширень.
- Прийнятий низький ризик: нетранзакційні канали під час однієї DDL-інструкції, яка однаково буде
  відхилена, — значення послідовностей (`setval` у виразі з функцією `pg_catalog`), налаштування сеансу
  з'єднання міграцій і текст помилки, що потрапляє в журнал запуску міграцій (не до ролей модулів). Це
  потребує навмисно шкідливого коду міграції, а він проходить рецензію PR.
- `CREATE TABLE AS` і `SELECT INTO` із таблиці клієнтів відхиляються (копія втрачає NOT NULL у
  `household_id`); нову таблицю клієнтів створюють звичайним `CREATE TABLE`.
- Статичне правило міграцій не бачить усього (зміна типового значення, нові унікальні індекси й тригери
  на наявних таблицях, видалення політик і індексів, DDL у `DO … EXECUTE`); це ловить крок «старий код
  + нова схема» у CI, наскільки його покривають тести модулів попередньої версії.
- Кожна транзакція модуля робить один додатковий запит від `ws_context` (прив'язка). Таблиця прив'язок
