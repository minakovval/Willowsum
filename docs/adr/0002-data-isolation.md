# ADR-0002: ізоляція просторів, схема даних, міграції, аудит і синтетичні дані

**Створено:** 2026-11-06 · **Оновлено:** 2026-11-06

**Статус:** Прийнято (рішення ведучого, PR ARC-03). **Вимоги:** ARC-03@PoC. Доповнює
[ADR-0001](0001-backend-stack.md), не змінює його рішень.

## Контекст

ARC-03 вимагає двох рівнів ізоляції просторів (фільтр у коді і політики рядків у базі, що діють для ролі
застосунку), сум NUMERIC(38,18) із кодом валюти, часу в UTC, регіону і власного ключа простору, міграцій
«розширити → перенести → звузити» з тестом «старий код + нова схема», журналу аудиту лише на дописування і
синтетичного набору даних. Модуля `household` ще немає (ACC-08 — хвиля 2).

## Рішення

| Що | Вибір | Чому |
| --- | --- | --- |
| Таблиця з даними клієнтів | Колонка `household_id uuid NOT NULL`; виконавець міграцій у тій самій транзакції, що й міграція, вмикає і примушує (`FORCE`) безпеку рядків і створює політику `household_isolation`: `household_id = (SELECT platform_context.current_household())` для читання і запису | Таблиця ніколи не буває видимою без політики; автор модуля не може її забути |
| Хто обирає простір | Платформа, не SQL модуля. `ModuleDatabase.inHousehold(id, …)` перед транзакцією записує прив'язку «з'єднання модуля → простір» окремим пулом від ролі `ws_context`, яка може лише виконати `platform_context.bind(pid, простір)`; роль з'єднання `bind` бере з `pg_stat_activity` і прив'язує лише ролі `ws_mod_*`. Роль модуля може тільки читати прив'язку (`current_household()`, SECURITY DEFINER) | Межа довіри — у базі: ні `set_config`, ні запис у таблицю прив'язок, ні `SET ROLE ws_context`, ні завершення транзакції всередині роботи не дають модулю обрати інший простір. Змінна сеансу (`app.household_id`) відкинута: її може змінити будь-який SQL. Модулі не можуть відкрити власне з'єднання (заборона драйвера БД, check:modules) |
| Фільтр у коді | `HouseholdQueryRunner.householdId`; SQL модуля фільтрує `WHERE household_id = $1` | Перший рівень ізоляції; другий — політика |
| Транзакція без простору | `ModuleDatabase.transaction(…)` прив'язує «жоден простір»: таблиці клієнтів порожні й не приймають рядків | Безпечне типове значення |
| Перевірка схеми в CI | `pnpm check:schema` (`src/platform/db/schema-rules.ts`): кожна таблиця модуля має `household_id` або стоїть у `apps/api/schema-exemptions.json` із причиною; у таблиці клієнтів безпека рядків увімкнена й примушена, є стандартна політика і немає інших дозвільних; NUMERIC лише (38,18), без float і `money`, сума `*_amount` має `*_currency`; лише `timestamptz`; `data_region` — тип `platform_types.data_region`; представлення лише з `security_invoker`, без матеріалізованих представлень і SECURITY DEFINER-функцій у схемах модулів | Критерій «таблиця без політики — 0»; обходи політики (представлення від власника) теж ловляться |
| Тест ізоляції | `apps/api/test/isolation.it.test.ts` знаходить усі таблиці з `household_id` у схемах модулів, заповнює їх синтетичними рядками двох просторів і перевіряє від ролі модуля без фільтра: лише свої рядки, 0 чужих, 0 без прив'язки, чужий рядок не вставити, не змінити, не видалити. Таблиця без генератора синтетичних даних — помилка тесту | Критерій «дані іншого простору — 0» для кожної таблиці автоматично |
| Час | Кожна транзакція модуля і міграції — `SET LOCAL TimeZone = 'UTC'`; у схемі лише `timestamptz` | ARC-03 п. 1 |
| Регіон і ключ | Домен `platform_types.data_region` (лише `'eu'`), константа `DATA_REGIONS`; перевірка схеми вимагає від таблиці `household.households` колонок `data_region` і `encryption_key_ref text NOT NULL` | Таблицю створить ACC-08; правило вже чекає на неї |
| Міграції | 1) `pnpm check:migrations`: операції, що можуть зламати попередній код (DROP, RENAME, зміна типу, SET NOT NULL, NOT NULL без DEFAULT, нове обмеження, TRUNCATE, DROP TRIGGER), дозволені лише в міграції з `-- ws:contract <NNNN_expand.sql> <причина>`, де названа міграція-розширення вже є в базовій версії; застосовані міграції базової версії не змінюються й не зникають. 2) CI «старий код + нова схема»: тести модулів базової версії (`.base`) запускаються на базі, яку будують виконавець і міграції PR (`WS_COMPAT_SCHEMA_FROM`) | Правило дає швидку й пояснювану відмову; тест старого коду ловить те, чого правило не бачить. Обидва прості: без окремого інструменту міграцій |
| Аудит | Модуль `audit`: таблиця `audit.entries` (простір, автор, час UTC, сутність, поля «до/після», канал); роль модуля має лише INSERT і SELECT; тригери відхиляють UPDATE, DELETE і TRUNCATE для будь-якої ролі; значення чутливих полів маскуються до запису, кожна зміна явно позначає `sensitive` | ARC-03 п. 5, П-10 |
| Синтетичні дані | `tools/synthetic` (`@willowsum/synthetic`): детермінований генератор (sfc32, зерно — рядок), простори «Synthetic household N» у регіоні «eu» з власним посиланням на ключ; кожен модуль реєструє генератор своїх таблиць у `src/modules/<module>/synthetic.ts`; вихід — CSV або psql-скрипт `COPY` | П-9; обсяг 10 000 активів і 100 000 транзакцій на простір перевірено тестом розміру; генератори активів і транзакцій додадуть їхні модулі |
| Великі об'єкти | EXECUTE на серверні функції `lo_*`, `loread`, `lowrite` відкликано від PUBLIC; `assertIsolatedRoles` зупиняє міграції, якщо роль модуля, `ws_probe` чи `ws_context` може їх виконати або має власні налаштування (`pg_db_role_setting`) | Посилення з ADR-0001 |

## Наслідки

- Роль-власник схем, що запускає міграції, — суперкористувач або має BYPASSRLS: безпека рядків примушена
  для всіх інших ролей, і перенесення даних у міграції без цього мовчки не побачило б жодного рядка;
  виконавець перевіряє це на старті. Ця роль не використовується кодом застосунку.
- Інфраструктура дає ролі `ws_context` LOGIN і пароль зі сховища секретів (`WS_DB_CONTEXT_PASSWORD`);
  власник схем, що запускає міграції, має право відкликати EXECUTE на `lo_*` (суперкористувач або власник
  бази з цим правом), інакше міграції зупиняються з поясненням.
- Кожна транзакція модуля робить один додатковий запит від `ws_context` (прив'язка). Таблиця прив'язок
  `UNLOGGED`, один рядок на з'єднання.
- Запис аудиту поки окремою транзакцією модуля `audit`; атомарність «зміна + аудит» прийде з подіями
  і outbox (ARC-04).
- Що додадуть пізніші вимоги: ACC-08 — таблицю `household.households` із `data_region` і
  `encryption_key_ref` і генератор просторів; ARC-06 — ключі шифрування простору в KMS (посилання
  стане ідентифікатором ключа); окреме розгортання іншого регіону з довідником «логін → регіон» — разом з
  інфраструктурою (CICD-07); генератори активів (10 000) і транзакцій (100 000) — модулі
  `asset-registry` і `transactions`; завантаження синтетичних даних у staging — з CICD-07.
