# ADR-0014: черга задач і вихідні події в PostgreSQL

**Створено:** 2026-11-13 · **Оновлено:** 2026-11-13

**Статус:** Прийнято (рішення ведучого, PR ARC-04; власник не схвалював). **Вимоги:** ARC-04@PoC (п. 1–5), ARC-02@PoC
(п. 1, 2), NFR-05@PoC (п. 6). Доповнює [ADR-0002](0002-data-isolation.md) і [ADR-0006](0006-observability.md), не змінює
їхніх рішень.

## Контекст

ARC-04 вимагає черги в PostgreSQL без брокера, подій у тій самій транзакції, що й зміна, ідемпотентних задач, повторів
до 8 спроб із чергою невдалих і одного ліміту важких задач. За ADR-0002 роль модуля бачить лише свою схему, а таблиця з
`household_id` — лише рядки прив'язаного простору; SECURITY DEFINER-функцій у схемах модулів немає. Тож спільної таблиці
черги, у яку модулі писали б у своїй транзакції, бути не може.

## Рішення

| Що | Вибір | Чому |
| --- | --- | --- |
| Де черга | Кожен модуль, що публікує події або виконує задачі, додає міграцію `src/platform/queue/queue-tables.sql` дослівно: таблиці `outbox_events` і `jobs` у власній схемі, з `household_id` і стандартною політикою простору | Подія і задача пишуться в транзакції модуля (п. 2); ізоляція просторів і перевірки схеми діють без винятків; так само, як `idempotency_keys` (ADR-0003) |
| Інтерфейс | Модулі викликають лише `publishEvent(q, подія, дані)`, `enqueueJob(q, задача, ключ, дані)` і свої обробники (`defineJob`, `defineJobHandler`); воркер працює через інтерфейс `JobStore` (`postgresJobStore` — реалізація на PostgreSQL) | Керована черга замінить `JobStore` без змін у модулях (п. 1); тест запускає воркер і обробник над сховищем у пам'яті |
| Доставка подій | Воркер читає нові події модуля, кладе для кожного підписника (`EventSubscription`: подія і версія → задача модуля-споживача) задачу з ключем = id події і позначає подію відправленою | Збій між кроками повторює передачу, а ключ дає одну задачу (0 втрачених і 0 подвійних) |
| Ідемпотентність | Унікальний ключ `(household_id, name, dedupe_key)`; обробник виконується в транзакції простору модуля, і в тій самій транзакції задача стає `done` | Невдалий чи перерваний запуск не лишає слідів, повтор дає той самий результат (п. 3). Зовнішні дії (лист, провайдер) обробник робить ідемпотентними сам (ключ ідемпотентності провайдера, ARC-05) |
| Оренда | Воркер бере задачу `FOR UPDATE SKIP LOCKED` з орендою (типово 5 хв, задача може задати свою); задачу, чий воркер зник, бере інший після кінця оренди; завершення перевіряє власника оренди, інакше відкочує роботу | Будь-який екземпляр воркера можна зупинити, вбити або додати (ARC-02 п. 2) |
| Повтори | Спроба рахується при взятті; затримка 10 с × 2^(n−1), не більше 1 год (10 с … 640 с); після 8-ї невдачі (або коли 8-ма спроба загинула з воркером) — стан `dead` (черга невдалих) і подія логу `job.dead_lettered` рівня ERROR: модуль, назва задачі, клас помилки, кількість спроб — без простору, ключа й даних. Невдала спроба, що буде повторена, — `job.failed` рівня WARN | П. 4; NFR-05 п. 6 |
| Важкі задачі | `heavy: true` у визначенні задачі; воркер бере важкі задачі лише до `heavyLimit` (типово 1) разом для всіх просторів і модулів, решта місць (`concurrency`, типово 4) — легкі | П. 5. Розподіл між просторами можна додати у `claimAndRun`, не змінюючи модулів |
| Зупинка | `stop()` перериває обробники (`AbortSignal`); перервана задача повертається в чергу без витрати спроби (ARC-02 п. 5) | |
| Аварійний вимикач | Задачі модуля з увімкненим вимикачем (CICD-06) не беруться | ADR-0004: «події й задачі воркера мають перевіряти той самий `isModuleAvailable`» |
| Простори | Воркер проходить простори зі списку модуля `household` (`spaceIds`), щоразу починаючи з іншого | Роль модуля без прив'язки не бачить рядків черги; для PoC (одна родина) прохід дешевий |

## Наслідки

- Жоден модуль ще не має таблиць черги; перший — `ledger` (подія «проводку записано», ARC-11, рядок 3 плану хвилі 2).
  Модуль, що додає таблиці, додає генератор синтетичних рядків для тесту ізоляції і їх видалення з простором
  (`data-erasure`, NFR-12).
- Прохід по всіх просторах робить 2 запити на простір і модуль за прохід (раз на секунду без роботи). Для багатьох
  просторів (PoC v2+) — індекс «є робота» без даних простору або окрема роль воркера; рішення — тоді.
- Ліміт важких задач — на екземпляр воркера; кілька воркерів множать його. У PoC воркер один.
- Виконані задачі й відправлені події лишаються в таблицях; прибирання за строком — окремою задачею пізніше.
- Щоденні задачі планувальника (ADR-0010) поки не йдуть через чергу.
