# ADR-0007: захисні заголовки, ліміти частоти, перевірка Origin і загальні засоби NFR-15 у платформі HTTP

**Створено:** 2026-11-07 · **Оновлено:** 2026-11-12 (розміри сторінки — рішення власника 2026-11-12; раніше — 2026-11-07, рецензії PR #86: `changedFields` від `base`, поля `readable`, обробник помилок клієнта, межа версії, перевірка CSP, сховище під потоком, `ip:port`, суворі значення фільтрів, вимога до розгортання за проксі)

**Статус:** Прийнято (рішення ведучого, PR NFR-14). **Вимоги:** NFR-14@PoC (п. 1–6, 8–10, критерії 1, 3, 4, приймання 1–3;
п. 7 — частково, примітив), NFR-15@PoC (загальні засоби платформи: п. 5, 13, 15, 17; п. 16 уже виконано в ARC-09).
Доповнює [ADR-0003](0003-api-contract.md) (нові коди проблем і порядок перевірок), [ADR-0004](0004-feature-flags.md)
(перевірки до аварійного вимикача) і [ADR-0006](0006-observability.md) (новий лічильник і атрибут); рішень ADR-0001…0006 не змінює.

## Контекст

NFR-14 вимагає таблицю заголовків на кожній відповіді API з пріоритетом значення маршруту (п. 1), заголовки й CSP вебу
(п. 2–4), ліміти за IP у фіксованих хвилинних вікнах — публічні 60, завантаження 30, решта 600 (п. 5) — з 429
`RATE_LIMITED` і `Retry-After` (п. 6), IP лише від довірених проксі (п. 8), увімкнення за замовчуванням у staging і
production (п. 9) і спільне сховище лічильників, якщо екземплярів більше одного (п. 10). NFR-15 додає cookie сесії й
перевірку Origin (п. 5), 409 `VERSION_CONFLICT` (п. 13), білі списки фільтрів і сортування (п. 15) і технічні ліміти з
`LIMIT_REACHED` (п. 17). Сервера статичних файлів вебу в репозиторії ще немає: розгортання — CICD-05/07.

## Рішення

| Що | Вибір | Чому |
| --- | --- | --- |
| Заголовки API | `platform/http/security-headers.ts`: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin`, `Cache-Control: no-store`; HSTS `max-age=31536000; includeSubDomains` — лише коли `buildServer({ hsts: true })`, тобто `WS_TELEMETRY_ENVIRONMENT` = `staging` / `production` (`config.deployed`). Ставить хук `onSend` у `buildServer` (до маршрутів) — він проходить кожну відповідь Fastify: маршрути, проблеми, 404, 413/415/400, 503 вимикача і зупинки, 429, проби `/health/*`. `frameworkErrors` (URL, який Fastify не декодує, задовгий параметр) викликає `applySecurityHeaders` сам. Запити, які не розбирає вже Node (метод малими літерами, погана назва заголовка, задовгі заголовки — 431, наприклад завеликою cookie; тайм-аут — 408), отримують відповідь власного `clientErrorHandler` — теж із цими заголовками (і HSTS, коли він увімкнений) (рецензія безпеки PR #86) | П. 1 «кожна відповідь»; тести по кожному виду відповіді |
| Пріоритет маршруту | `defineRoute({ headers })` — лише `cache-control`, `content-security-policy`, `x-frame-options`, `cross-origin-resource-policy`, `referrer-policy`; значення без переносів рядка (перевірка при оголошенні). Діє лише на успішну відповідь маршруту (і повтор за ключем ідемпотентності); проблема того самого маршруту має типові заголовки — помилка не кешується. `nosniff` і HSTS маршрут не змінює | П. 1 (приклади з таблиці: `SAMEORIGIN` для вбудованого переглядача, `sandbox` для підписаних файлів, `private, max-age=300`) |
| Заголовки й CSP вебу | `apps/web/security-headers.ts` — єдине джерело: `webHeaders(path)` (HSTS, nosniff, `strict-origin-when-cross-origin`, закрита `Permissions-Policy`, COOP `same-origin`, `X-Frame-Options: DENY`, CSP з таблиці, `Cache-Control`: оболонка й нехешовані файли `no-cache`, `assets/*-<hash>.*` — `public, max-age=31536000, immutable`). `vite preview` застосовує його плагіном; dev-сервер — ні (гаряче перезавантаження вставляє вбудовані скрипти). Через HTTP (локальний preview) немає HSTS і `upgrade-insecure-requests`. Вбудований скрипт теми (DS-11 п. 7) винесено в `public/theme-init.js` — блокувальний скрипт у `<head>`, тож тема так само застосовується до першого малювання, а CSP лишається `script-src 'self'` без хешів. Перевірка CSP у CI (критерій 4) — тест `apps/web` у задачі `web`: 0 джерел `http:` / `ws:`, без `'unsafe-eval'` / `'wasm-unsafe-eval'`, без `'unsafe-inline'` у `script-src` і `default-src`, без шаблонів (`*`, `https:`, `wss:`, `*.host`, `https://*.host`), без `data:` у `script-src` | П. 2–4. Розгорнутого сервера немає — сервер або CDN staging/production мусить надсилати рівно `webHeaders`; перевірку на staging (критерій 2) робить CICD-07 |
| Класи лімітів | `defineRoute({ rateLimit })`: `public` (60) — типовий для публічних маршрутів; `upload` (30); `default` (600) — типовий для захищених. Маршрут може бути лише суворішим за свій типовий клас (перевірка при оголошенні). Невідомий шлях рахується в `default` | П. 5 |
| Порядок перевірок | `onRequest` усього застосунку, до всього іншого: ліміт (публічний маршрут — його клас; захищений і невідомий шлях — `default`) → Origin запису → далі як було (404 невідомого шляху, вимикач, сеанс, прапорці). Захищений маршрут класу `upload` рахується ще й у `upload`, але лише після сеансу й прапорців: прихована прапорцем функція відповідає 404 і не виказує себе раннім 429 (DAT-05 п. 7). Проби `/health/*` не обмежуються (це не API: їх кличе оркестратор) | Захищений маршрут і невідомий шлях мають один лічильник, тож 429 їх не розрізняє |
| Примітив | `createFixedWindowLimiter({ limit, windowMs, store })` — фіксоване вікно на ключ (вікна від кратних `windowMs`), відхилений запит теж рахується. `RateLimitStore.hit(key, windowStart, windowMs)` — інтерфейс сховища. ACC-01 використає цей самий примітив для п. 7 (5 невдалих входів за 15 хв на акаунт, реєстрації 5 за годину з IP, step-up у тому самому лічильнику, токен провайдера 5 за 15 хв) зі сховищем, яке переживає перезапуск | П. 7 належить ACC-01: тут лише примітив |
| Сховище (п. 10) | У PoC — пам'ять процесу (`memoryRateLimitStore`, `shared: false`): прострочені вікна видаляються; понад 200 000 живих ключів нові ключі рахуються в одному лічильнику переповнення **свого класу** (потік із дуже багатьох адрес обмежується разом, пам'ять не росте, а переповнений `default` не вичерпує бюджет `public`). Під потоком мапа повна ключами поточного вікна, які прибирати рано, тож повне прибирання — не частіше одного разу на початок вікна (і раз на 10 000 звернень), а не на кожен новий ключ. Переповнення видно в телеметрії: лічильник `ws.rate_limit.overflow` (клас) і подія `rate_limit.overflow` (WARN, раз на клас на вікно) — без адрес. `WS_API_INSTANCES` (типово 1) — скільки екземплярів API запущено; при > 1 з увімкненими лімітами роль `api` не стартує й називає змінну. Таблицю в PostgreSQL не обрано: кожен запит API давав би запис у БД (на безкоштовній VM «Старт» — подвоєння навантаження на базу), а платформна схема поза модулями потребує власної ролі, міграцій і винятку з ізоляції — це окремий чутливий шматок, доречний разом із профілем, де екземплярів кілька. Спільне сховище (PostgreSQL або Redis) реалізує той самий `RateLimitStore` і знімає заборону | Профіль «Старт» (ARC-08) — один сервер і один контейнер API. Лічильники — короткоживучий захисний стан, не дані (ARC-02 п. 2): перезапуск лише обнуляє вікно (≤ 1 хв) |
| IP клієнта (п. 8) | `WS_TRUSTED_PROXY_HOPS` (0–5, типово 0) → `trustProxy` Fastify: 0 — адреса сокета, `X-Forwarded-For` і `X-Forwarded-Proto` ігноруються; n — n-й вузол праворуч (те, що допише клієнт ліворуч, не враховується). Ключ лічильника: IPv4 як є (також відображена в IPv6), IPv6 — мережа /64 (абонент зазвичай має всю /64); адреса, яку проксі записав як `ip:port` (`203.0.113.7:4711`, `[2001:db8::1]:4711`), рахується без порту; решта — `unknown`. **Вимога до розгортання (CICD-07):** довіра за кількістю вузлів довіряє сусіду сокета, хоч би який він був, тож порт API має бути досяжний лише через проксі (API слухає лише мережу проксі або брандмауер пропускає лише проксі); інакше клієнт напряму підробить `X-Forwarded-For` | Підробити свою адресу заголовком неможливо, поки API досяжний лише через проксі; ротація адрес у межах /64 не обходить ліміт |
| Вимкнення (п. 9) | `WS_RATE_LIMITS` = `on` (типово всюди) або `off-load-test`; у production `off-load-test` відхиляється. Вимкнені ліміти — подія логу `rate_limits.disabled` при старті | Інших способів вимкнути немає |
| 429 | Проблема `RATE_LIMITED` (429) з `Retry-After` = цілі секунди до кінця вікна, округлені вгору (44,5 с → 45; ≥ 1); у контракті — відповідь 429 із заголовком у кожній операції | П. 6, критерій 3 |
| Телеметрія | Лічильники `ws.rate_limit.rejections` з атрибутами `ws.rate_limit.class` (закритий перелік) і `http.route` та `ws.rate_limit.overflow` (лише клас); адреса не є атрибутом і в фільтрі її немає. 429 — не 5xx (спан не помилковий, бюджет не спалює) | ADR-0006, NFR-17 |
| Origin (NFR-15 п. 5) | Для POST, PUT, PATCH, DELETE під API: `Origin` має бути в `WS_ALLOWED_ORIGINS` (точні origin через кому; https, http лише для localhost; у staging/production — лише https). Інакше 403 `ORIGIN_NOT_ALLOWED` до вимикача, сеансу й тіла (і для невідомого шляху так само). `Origin: null`, порожній чи кілька — відхиляються. **Без `Origin`** — пропускається: так пишуть мобільний застосунок, сервери й CLI, а браузер надсилає `Origin` з кожним записом (і того самого сайту); виняток — браузер сам позначив запит `Sec-Fetch-Site: cross-site` або `same-site`. Не задано: локально — сервери Vite (`http://localhost:5173`, `:4173`); у staging/production — жодного (усі записи з браузера відхиляються, доки origin вебу не налаштовано). Читання не перевіряються | Захист від CSRF разом із `SameSite=Lax`; не ламає небраузерних клієнтів |
| Cookie (NFR-15 п. 5) | `platform/http/cookies.ts`: `sessionCookie` — `HttpOnly; Secure; SameSite=Lax; Path=/`, без `Domain`; на HTTPS ім'я з `__Secure-` (HTTPS — завжди в staging/production, інакше протокол запиту від довіреного проксі). `readSessionCookie` на HTTPS приймає лише ім'я з префіксом і не довіряє дублю. Ім'я й значення перевіряються (без `;`, переносів рядка). Сесійну cookie поставить identity (ACC-01) лише через ці функції | `__Secure-`: браузер прийме таку cookie лише з `Secure` від захищеного origin |
| 409 (NFR-15 п. 13) | `defineVersionedTable({ table, fields, readable })` + `updateVersioned(q, table, id, expectedVersion, changes, base)`: `UPDATE … SET …, version = version + 1 WHERE household_id = $1 AND id = $2 AND version = $3`; якщо 0 рядків — `SELECT version, col IS DISTINCT FROM $n …`: немає запису → 404; інакше 409 `VERSION_CONFLICT` з `currentVersion` і `changedFields`. **`base`** — значення, які клієнт прочитав на `expectedVersion`, для полів, які він показує чи редагує; `changedFields` — оголошені поля з `base`, чиє збережене значення тепер IS DISTINCT FROM базового (порівняння в SQL з типом стовпця, тож `100` = `100.000…`), тобто те, що змінив інший автор. Лише назви полів, ніколи значення. Порівнюються лише поля набору **`readable`** таблиці: поле, яке абонент може писати, але не читати, інакше підтверджувало б вгадане значення (рецензія безпеки PR #86); записи `base` для інших полів ігноруються; чи може цей абонент читати поле — рішення модуля (він передає `base` лише для таких полів). Поле, якого клієнт не включив у `base`, не повідомляється, навіть якщо змінилося. Маршрут перевіряє `base` тими самими схемами, що й зміну. `expectedVersion` — 0…2 147 483 647 (стовпець `integer`): більше — 400, а не помилка БД. Ідентифікатори — лише з оголошення (перевірка), значення — лише параметри | Рішення координатора після рецензії PR #86 (перша версія повідомляла поля, які надсилає сам користувач, а не змінені іншим); клієнт показує, що змінилося, і перечитує запис за `currentVersion` |
| Фільтри (NFR-15 п. 15, 17) | `defineListQuery({ filters, sorts, defaultSort })`: поле → стовпець, тип PostgreSQL (`text`, `uuid`, `integer`, `numeric`, `date`, `timestamptz`, `boolean`), zod-схема значення, дозволені оператори (`eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `in`). На дроті `filter=<поле>.<оператор>:<значення>` (повторюваний), `sort=поле,-поле` (≤ 3 ключі). SQL — `"col" >= $n::date`, `"col" = ANY($n::text[])`. Невідоме поле, оператор, тип чи сортування — 400 `VALIDATION_FAILED` без повтору введеного. Понад 50 фільтрів (або значень в `in`) — 422 `LIMIT_REACHED` з `limit`. **Для DAT-01:** `in` ділить значення комами, тож текстове значення `in`-фільтра не може містити кому. **Значення** — суворі розбирачі `filterValue`: `int4({ min, max })` (десяткове ціле без `+`, нулів попереду, пробілів і hex, у межах int4), `int8()` (як текст), `decimal({ integer: 20, fraction: 18 })` (NUMERIC(38,18), рядок), `isoDate()` (справжній календарний день), `timestamp()` (ISO 8601 зі зсувом), `uuid()`, `boolean()` (`true` / `false`); `z.enum([...])` — для закритого переліку слів. Наприклад: `{ column: "item_count", cast: "integer", value: filterValue.int4({ min: 0 }), operators: ["eq", "gt"] }`. `z.coerce.number()` не годиться: приймає `""`, `" "` (обидва 0) і `0x10` (16), а значення поза типом стовпця дійшло б до приведення в PostgreSQL і дало б 500 замість 400 | Малий примітив, на якому DAT-01 збудує свої списки |
| Технічні ліміти (п. 17) | `TECHNICAL_LIMITS` (фільтрів 50, масова дія 500, чернетка 100 КБ, чернеток 20, збережених виглядів 50) і `requireWithinLimit` → 422 `LIMIT_REACHED` з `limit`. Це не ліміти плану (ті — 402 через plan-catalog). Тіло запиту — до 1 МіБ (`bodyLimit` Fastify явно), маршрут може задати менше (`bodyLimitBytes`), більше — ні; понад — 413 `PAYLOAD_TOO_LARGE` | 422 — запит коректний, але перевищує межу сервісу; розміри сторінок — див. відкрите питання |
| Контракт | Нові коди `ORIGIN_NOT_ALLOWED` (403), `VERSION_CONFLICT` (409), `LIMIT_REACHED` (422), `RATE_LIMITED` (429); поля `currentVersion`, `changedFields`, `limit`; 429 із `Retry-After` у кожній операції, 403 у кожному записі. `contract:compat` проти `main` — сумісно (перелік кодів розширюваний) | ADR-0003 |

## Відкриті питання власнику

- **Розміри сторінки.** NFR-15@PoC п. 17: «розмір сторінки — 25, 50 або 100»; DAT-01@PoC п. 6 казав «10, 25, 50 або 100».
  Рішення власника 2026-11-12: 25, 50 або 100 (DAT-01 і CMP-13 виправлено). Платформа поки лишає межу пагінації ARC-07
  (`limit` 1–100, типово 25); перелік допустимих розмірів вводить рушій списку (DAT-01).

## Наслідки

- Новий маршрут отримує заголовки, ліміт і перевірку Origin без жодного коду; публічний маршрут — клас `public`;
  маршрут завантаження файлів оголошує `rateLimit: "upload"`.
- Модулі з версійованими записами додають стовпець `version integer NOT NULL DEFAULT 1` і оновлюють лише через
  `updateVersioned`; списки з фільтрами — через `defineListQuery`.
- Розгортання (CICD-05/07): `WS_ALLOWED_ORIGINS` — origin вебу й адмін-панелі; `WS_TRUSTED_PROXY_HOPS` — кількість
  проксі перед API; `WS_API_INSTANCES` — фактична кількість; сервер статичних файлів надсилає `webHeaders`; порт API
  досяжний лише через проксі (інакше `X-Forwarded-For` можна підробити); формат адреси клієнта, який пише проксі, —
  IP або `ip:port`.
- Пізніше: ліміти автентифікації (ACC-01), тип файлу за вмістом і антивірус (NFR-15 п. 18, модуль файлів), екранування
  CSV (п. 19, експорт), перелік IP адмін-панелі (п. 20), перевірка заголовків на staging (CICD-07), спільне сховище
  лічильників перед другим екземпляром API.
