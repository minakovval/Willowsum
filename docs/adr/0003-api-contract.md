# ADR-0003: HTTP API, контракт OpenAPI і типізований клієнт

**Створено:** 2026-11-06 · **Оновлено:** 2026-11-06 (третій раунд рецензії безпеки: префікси плагінів; рецензії PR #80: `ctx.db` без простору, страж маршрутів `/v1`, межа сторінки, шляхи помилок, scope)

**Статус:** Прийнято (рішення ведучого, PR ARC-07). **Вимоги:** ARC-07@PoC, NFR-05@PoC (п. 1–2). Доповнює
[ADR-0001](0001-backend-stack.md) і [ADR-0002](0002-data-isolation.md), не змінює їхніх рішень.

## Контекст

ARC-07 вимагає один задокументований HTTP API для всіх клієнтів під `/v1`, контракт OpenAPI 3.1 із тих самих
схем, що перевіряють запити, згенерований клієнтський пакет, лише сумісні зміни в межах версії (видалення —
після позначки «застаріле» і 6 місяців), помилки «problem details» із машинним кодом, ключі ідемпотентності на
створення, серверну пагінацію і перевірку прав і плану на кожному маршруті. ADR-0001 уже обрав Fastify 5 і
zod 4.

## Рішення

| Що | Вибір | Чому |
| --- | --- | --- |
| Опис маршруту | `defineRoute` (`apps/api/src/platform/http/route.ts`): метод, шлях `/v1/…`, `operationId`, схеми zod для параметрів шляху, запиту й тіла, схема відповіді, `access` — дозвіл (access-scope) і ключ функції (plan-catalog) або причина, чому маршрут публічний; `create` (ідемпотентність), `list` (пагінація), `deprecatedSince` | Одне місце, з якого беруться і перевірка, і контракт; маршрут без перевірок не оголосити |
| Порядок перевірок запиту | Сеанс (401) → роль і scope (403) → план (402 `PLAN_LIMIT_REACHED`) → вхід за схемами zod (400) → ідемпотентність (409 або повтор відповіді) → обробник → відповідь, розібрана схемою відповіді | Права перевіряються лише на сервері (NFR-05 п. 2); поля поза контрактом не виходять із сервера (відповідь проходить `parse`) |
| Простір запиту | Із сеансу (`Principal.householdId`); код маршруту бачить дані лише через `ctx.inHousehold`, який прив'язує цей простір (ADR-0002). `ctx.db` дає лише `transaction` без простору (тип `HouseholdFreeDatabase` і заморожений об'єкт під час роботи), тож `inHousehold(<id із запиту>)` маршрут викликати не може. Сеанси дасть identity (ACC-01); до того `authenticate` повертає «не ввійшов», і кожен захищений маршрут відповідає 401 | Закриває відкрите питання ADR-0002 «простір із сеансу, а не з коду» |
| Генерація OpenAPI | Власний генератор (`openapi.ts`, ~150 рядків) поверх `z.toJSONSchema` (JSON Schema 2020-12 — діалект OpenAPI 3.1), без нової залежності. Доступ маршруту записано в розширенні `x-willowsum-access` | Сторонні мости zod → OpenAPI відстають від zod 4 і Fastify 5; JSON Schema дає сам zod |
| Перевірка контракту в CI | `pnpm contract:check`: закомічений `packages/api-contract/openapi.json` і `src/schema.ts` збігаються зі згенерованими; `contract:compat` порівнює контракт із базовою гілкою PR власним порівнювачем (`scripts/lib/contract-compat.ts`) | Критерії «розбіжність контракту й реалізації — 0» і «несумісна зміна в межах версії — 0». `oasdiff` — бінарник на Go, окремий інструмент у CI; потрібних правил (6 місяців від дати позначки) він не має |
| Правила сумісності | Несумісно: видалений шлях, операція, параметр, поле запиту чи відповіді, успішна відповідь; нове обов'язкове поле чи параметр запиту, необов'язкове стало обов'язковим; звужений тип запиту (тип, значення enum, довжина, діапазон, шаблон, формат, заборона додаткових полів); розширений тип відповіді (новий тип чи null, поле не завжди є, нове значення enum, крім позначених `x-extensible-enum`). Видалення дозволене, лише якщо базова версія мала `deprecated` і `x-deprecated-since` щонайменше 6 місяців тому; нова позначка має дату дня, коли її додано (± 7 днів), і не змінюється. Умову для мобільних клієнтів (< 1 % старих версій) перевіряє процес релізу мобільного застосунку (v1-mobile), не CI | ARC-07 п. 3 |
| Типізований клієнт | `packages/api-contract`: типи генерує `openapi-typescript` 7 (MIT, dev-залежність), виклики — `openapi-fetch` 0.17 (MIT, ~6 КБ, без залежностей) | Найпоширеніша пара для TypeScript; клієнт не знає шляхів поза контрактом (виклик не компілюється — NFR-05 п. 1); той самий пакет для вебу, адмін-панелі й мобільного |
| Помилки | RFC 9457, `application/problem+json`: `type` (URN `urn:willowsum:problem:<код>`), `title` (фіксований для коду), `status`, `code` (машинний, `x-extensible-enum`), необов'язкові `detail` (фіксований текст маршруту), `errors` (для 400: де і код помилки zod, без надісланих значень), `supportId` (гачок для ARC-09: ідентифікатор траси). 500 — лише `INTERNAL`, без повідомлення, SQL і персональних даних | ARC-07 п. 4, AGENTS.md «Privacy» |
| Ідемпотентність | Заголовок `Idempotency-Key` (1–128 видимих символів ASCII, необов'язковий) на маршрутах `create`. Ключ зберігається в схемі модуля маршруту, таблиця `idempotency_keys` (шаблон `platform/http/idempotency-keys.sql`, модуль додає його міграцією дослівно; тест перевіряє) під політикою рядків простору: простір + ключ, SHA-256 канонічного JSON запиту, стан, статус і текст відповіді, 24 год. Той самий ключ і запит → збережена відповідь із `Idempotent-Replayed: true`; інший запит → 409 `IDEMPOTENCY_KEY_REUSED`; ще виконується → 409 `IDEMPOTENCY_REQUEST_IN_PROGRESS`; збій обробника звільняє ключ | Таблиця з `household_id` поза схемами модулів заборонена (ADR-0002); у каталозі ARC-01 немає модуля «ідемпотентність», тож ключ живе там, де й дані, які він захищає. Якщо процес упаде між створенням і записом відповіді, ключ лишається «виконується» до кінця строку: повтор отримає 409, але не друге створення |
| Пагінація | Курсор (непрозорий base64url ключа сортування) + `limit` 1–100, типово 25; відповідь `{ items, nextCursor }`, `nextCursor = null` на останній сторінці; підроблений курсор — 400 `INVALID_CURSOR` | ARC-07 п. 4; розміри сторінок інтерфейсу (10/25/50/100, DAT-01) вкладаються в межу 100 |
| Права і план | Модуль `access-scope`: матриця ролей (Owner, Admin, Editor, Viewer, Advisor) з 00-general §0.3, учасник зі scope лише читає. Модуль `plan-catalog`: каталог ключів функцій і інтерфейс `isEnabled(простір, ключ)`; джерело матриці — конфігурація `WS_PLAN_ENTITLEMENTS=all-enabled` (у PoC усе ввімкнено, П-24); невідомий ключ — помилка, не «так» чи «ні». API не стартує, якщо маршрут називає дозвіл чи ключ, яких немає | П-21, П-24; тест проходить кожну роль на кожному маршруті |
| Що поза контрактом | Лише перевірки оркестратора `/health/live` і `/health/ready` (ARC-02): не мають даних і не для клієнтів | Решта — під `/v1` |
| Маршрути `/v1` поза шаром API | Хук `onRoute` (`guardApiRoutes`), який `buildServer` ставить до будь-якого маршруту, а `registerApi` — якщо його ще немає, відхиляє кожен маршрут без мітки шару API (приватний `Symbol` у `config`), що може відповісти на запит під `/v1`: перший сегмент шляху — `v1` у будь-якому регістрі або містить `:`, `*` чи `(` (параметр, шаблон, регулярний вираз: `/*` як запасний маршрут статики, `/:version/debug`); хук `onRegister` так само відхиляє будь-який плагін, чий префікс може обслуговувати `/v1` (`/v1`, `/:tenant`), бо його власний обробник «не знайдено» чи помилок відповідав би на запити `/v1` без перевірок; шар API плагінів не реєструє. Буквальні маршрути поза `/v1` (`/health/*`, `/v10-…`) дозволені. Тест порівнює повний набір маршрутів сервера (`printRoutes` після `ready`) з оголошеними маршрутами плюс дві перевірки | Сирий маршрут обійшов би сеанс, роль і план і контракт (рецензії PR #80, два раунди) |
| Шляхи помилок 400 | `errors[].path` містить лише імена, які оголошує схема (ключі об'єктів і індекси масивів); інший сегмент — ключ, обраний клієнтом (наприклад, запису `z.record`), — замінюється на `*` | Ключ запису може бути значенням (email) і не повертається клієнту |
| Межа сторінки | `cursor` і `limit` у запиті будь-якого маршруту — лише власні поля `pageQuery` (перевіряється за ідентичністю схеми), тож межа 100 не обходиться власним `limit` | Рецензії PR #80 |
| Межі модулів | Модулі не імпортують Fastify (правило `no-http-framework-in-modules` у `check:modules`); маршрути оголошуються в `adapters/http/` модуля і експортуються в `routes` опису модуля | Перевірки неможливо обійти власним маршрутом |

## Наслідки

- Порівнювач сумісності перевіряє форму контракту, а не поведінку: зміна `x-willowsum-access` (наприклад, суворіший
  дозвіл маршруту) проходить його навмисно. Таку зміну розглядає рецензія PR, бо вона змінює, хто може викликати
  маршрут, а не те, що клієнт надсилає й отримує.
- Повтор ідемпотентної відповіді — у межах простору, а не користувача: інший учасник того самого простору з тим
  самим ключем і запитом отримає збережену відповідь (права на маршрут перевіряються для нього до повтору). Коли
  з'явиться шарінг простору, це записується в документацію модулів, які мають маршрути `create`.
- Маршрути читання теж відповідають 402, коли функція плану вимкнена. У PoC усе ввімкнено, тож це не діє; перед
  появою планів (SUB) це треба переглянути: після пониження плану дані лишаються доступними для читання
  (00-general, AGENTS.md «Plans»), тож маршрути читання мусять мати ключ, що лишається ввімкненим, або перевірку
  плану лише на створенні.
- Учасник зі scope може мати лише роль Editor, Viewer чи Advisor (00-general «Область доступу»); «обмежений» Owner
  чи Admin неможливий, і `can()` йому нічого не дозволяє.
- Хуки на кшталт `onRequest`, `preHandler` чи `onSend`, додані на рівні застосунку, бачать і запити `/v1`; страж
  маршрутів їх не перевіряє (вони не маршрути й не мають префікса). Такий хук у коді платформи — питання рецензії
  коду: він не має відповідати на запит замість маршруту API.
- `openapi-fetch` і `openapi-typescript` використовуються лише в `packages/api-contract` (ESLint
  `no-restricted-imports` і правило `check:modules`).

- Після зміни маршруту — `pnpm contract:write` і коміт `openapi.json` та `src/schema.ts`.
- Модуль із маршрутом `create` додає міграцію з `idempotency_keys`. Очищення прострочених ключів — задачею
  планувальника, коли з'явиться черга (ARC-04); до того прострочений ключ просто перезаписується.
- Сеанси й автентифікація — ACC-01 (реалізує `authenticate`). Адмін-панель на окремому домені з окремою
  автентифікацією персоналу і списком IP (ARC-07 п. 6) — інфраструктура, пізніше (ADM, CICD-07).
- Журналювання внутрішніх помилок і `supportId` — ARC-09.
